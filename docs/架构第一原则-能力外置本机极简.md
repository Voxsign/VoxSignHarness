# 架构第一原则：能力外置，本机极简

> **提出**：Peter，2026-10-03
> **地位**：本原则优先于任何实现细节。与它冲突的设计一律重做。
> **一句话**：**本机不装技能、不装插件、不囤资料。能力全部通过外部接口获得，给一个 key 就够。**

---

## 1. 原话

> 「未来本机不要装技能，我所有的技能都是通过外部……来解决，就类似于**模型中心不在这里做**一样。
> 所以我把所有的技能不在本地做，这个要特别重要，本机不要有安装乱七八糟的东西，全部去掉。
> 所以所有的东西都非常简单简化，**越简化越好**。
> 外面的不够的技能，我通外部来解决，然后他来调用接口来解决——
> 我这个接口会满足他的需求，我会给他一个东西，**就像给他一个 key 一样，他自己去解决**。
> 这是个核心思想。我不可能把这个 harness 搞得很复杂。」

---

## 2. 这条原则解决什么问题

**反面参照**：通用 agent harness 的典型形态是"本机装一切"——
插件目录、技能包、依赖树、抓下来的资料。实测某商业 harness 的打包产物里，
`node_modules` 有 **12,416 个文件**。

**代价**：
- 本机变重、启动变慢、升级要动本地；
- 能力散落在本机各处，**换机就重建**；
- 本机状态成了隐性契约，出问题说不清是谁的；
- **最要命的**：能力不在你自己的服务里，就**不能持续改进、不能版本化、不能归因**。

**本项目的选择**：本机只保留**闭环本身**，其余全部外置。

---

## 3. 分层：什么在本机，什么在外面

| 层 | 位置 | 内容 |
|---|---|---|
| **本机（极简）** | Go 单二进制 | 输入容错 → 意图 → 域/权限门禁 → 执行 → 独立校验 → 回执 |
| **外部（接口 + key）** | peterzou.com / 模型中心 | 模型推理、**技能**、判断原语、资料检索 |

**判定准则（一条就够）**：

> 如果某样东西**可以放到外面**，那它就**必须**放到外面。

本机只保留"**不放到外面就没有意义**"的部分——因为它们是关于**这台机器上正在发生的事**的：
文件系统状态、git 状态、进程、域权限、回执落盘。

---

## 4. 与既有设计的关系

| 既有决策 | 在本原则下的解释 |
|---|---|
| **模型中心外置** | 已经是这条原则的一个实例。本原则把它**推广到技能**。 |
| **域 = 权限交集，默认拒绝** | 门禁必须在本机——它管的是"这台机器上能不能做"，外置就没有意义。 |
| **独立校验器读文件系统** | 同上：校验的是本机真实状态，不能外置。 |
| **REGISTER_TOOL（自举充分条件）** | **要重新定义**：注册的不是"本机的一段代码"，而是"**外部服务的一个接口调用**"。注册结果是本机记下"我有权用哪个 key 调哪个能力"，不是把实现装到本机。 |
| **零第三方依赖（`go.mod` 只有 module + go 1.22）** | 是这条原则的**自然结果**，不是独立的美德。 |

---

## 5. 对具体实现的硬约束

1. **本机不得出现：插件目录、技能包、`node_modules` 式的依赖树。**
2. **本机不得囤外部资料。** 需要外部内容时**当场取**（接口），不落盘成"离线副本"。
3. **能力升级不得要求改本机。** 升级 = 外部接口版本变化 + 本机侧一张 key/配置。
4. **本机只存"关于本机的事实"**：轨迹、回执、域声明、缓存（可重建的短期物）。
5. **每一个外部能力都必须可归因**：谁调的、用了哪把 key、花了什么、为什么。

> 反模式实例（本仓库真实存在，已清理）：
> `doc-fetch-resources/` 与 `docs/doc-fetch-resources/` 里囤了 6 个抓下来的 HTML，
> 提交信息写着「8 份飞书文档本地化为 Markdown，**供 Codex 离线阅读**」——
> 这正是"把外面的东西囤到本机"。正确做法是**让外部接口可取**，而不是留副本。

## 7. 这条原则怎样被验证（不许只写在文档里）

按技能文档 §3「判据先于实现」，本原则必须变成可执行的判据：

| # | 判据 | 怎么测 |
|---|---|---|
| **P1** | 本机依赖树不得增长 | `go.mod` 只有 `module` + `go`；出现任何第三方依赖即红 |
| **P2** | 本机不得囤外部资料 | 仓库中不得存在"抓取的外部内容副本"目录；发现即红 |
| **P3** | 能力升级不要求改本机 | 模拟"外部接口版本变化"，本机侧只应改配置/key |
| **P4** | 每个外部调用可归因 | 轨迹里每次外部调用都有 key 标识与用途 |

**这四条建议作为 LHT-0002 的下一批架构不变式（P1–P4）下发。**
在它们变成红灯之前，本原则只是**声明**，不是**约束**。

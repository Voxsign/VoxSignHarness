**方法**：web_search + web_fetch 广度调研，覆盖 2024–2026 论文、厂商工程博客、生产失败研究

## 1. 核心发现（5 条）

### 发现 1｜长任务的失败，**主因是规划而不是执行**
HORIZON 基准（3,357 条轨迹，4 个域：Web / OS / Database / Embodied，GPT-5 系列与 Claude-4）用 7 类失败分类法做归因，结论是 **"Planning Error dominates across all domains"**；且失败构成会随 horizon 增长**发生结构性偏移**——规划类与记忆类失败（catastrophic forgetting）占比上升。作者明确说：**"scaling base models alone is insufficient"**。
🟢/🟡 [arXiv:2604.11978](https://arxiv.org/abs/2604.11978) · [HORIZON leaderboard](https://xwang2775.github.io/horizon-leaderboard/)
> 为什么重要：这否定了"等更强的模型就好了"的路线。规划失败是长任务的主要死因，而它同时需要**方法层面**（规划结构 + 记忆 + 执行期控制）的改进。

### 发现 2｜"规划指导的内容"只值 **+7.17 个百分点**；而一个**廉价的只读验证器**值更多
这是本次调研里**最可操作**的一篇。作者用「预写任务专用计划（Fixed）」vs「打乱顺序但字数匹配的政策文本（Sham）」做对照，**干净地隔离出"规划指导内容"本身的贡献**：
- 265 个匹配单元，oracle 验证成功率 **+7.17pp**（90% task-clustered bootstrap CI **1.15–13.36**），**增益集中在高复杂度任务**；
- 一个**只读终端验证器**能拒掉 **61%** 的 oracle-invalid episode，同时**误扣 17%** 正确的 episode，**额外成本 < 1 美分/episode**；
- **关键结论**："which component matters more depends on the loss assigned to erroneous acceptance"——低责任场景下规划增益占优；**高责任场景下验证器避免的 false pass 占优**；而且**"a standalone verifier captures nearly all the false-pass benefit of the full planning-plus-verification stack at a fraction of its cost"**。
🟡 [arXiv:2609.20474](https://huggingface.co/papers/2609.20474)（2026-09-17）
> 为什么重要：**先建验证器，再建规划器**。这直接反驳"把规则式规划器升级成通用规划器"的直觉。

### 发现 3｜**plan-then-execute 至少不输交织式，而且省 2–3× token**；但计划本身必须被当作消耗品
- Megagon Labs 的受控实验（KBQA + Multi-hop QA，隔离 planning horizon 这一个变量）：**full-horizon planning + lazy replanning 在准确率上与 single-step 交织式持平**（跨不同 depth / breadth / tool robustness），**token 用量少 2–3×**。作者结论：对定义良好的数据型任务，"eager step-wise monitoring is often unnecessary"。
  🟢 [arXiv:2605.08477](https://arxiv.org/abs/2605.08477)（CAIS 2026，DOI [10.1145/3786335.3813129](https://dl.acm.org/doi/full/10.1145/3786335.3813129)）
- **但**：LLM 生成的计划**平均只有前 2.65 步是可执行的**（符号化生成计划平均长 8.4 步）；一个"NLP 分析 + 修复 + 符号规划器补全"的流水线只把成功率从 **21.9% → 27.5%**；且**可执行性与有效性之间没有一致关系**。
  🟡 [arXiv:2508.01300](https://arxiv.org/abs/2508.01300)
- 两者合起来：**默认用 plan-then-execute（省钱且不输），但必须自带 lazy replanning 的触发机制**，因为计划大概率在第 3 步就失效了。"lazy replanning"= 按需重规划，不是每步都监控。

### 发现 4｜**输入质量（欠规定 underspecification）是最大的单一杠杆，而且它的表现是"猜"而不是"失败"**
- UnderSpecBench（69 个任务族、2,208 个 prompt 变体、5 组 agent×model 配置，含 Claude Code / Codex / OpenCode，oracle 基于副作用）：**55.8–67.8% 的运行至少违反一个动作边界**。结论句极为精准：**"underspecification does not mainly make agents fail; it makes them guess."** 另外：**target underspecification 严重拉低动作质量**，而 **blast-radius 提示几乎不能降低越界倾向**。
  🟡 [arXiv:2607.02294](https://huggingface.co/papers/2607.02294)（2026-07）
- LHAW（Scale AI，285 个受控欠规定变体，横跨 TheAgentCompany / SWE-Bench Pro / MCP-Atlas）：在一个完整指定的任务上**删掉 1 段信息**，MCP-Atlas 上 Opus-4.5 从 **100 → 60.5**、Gemini-3-Pro 50.0、GPT-5.2 44.7；删 2 段 → 38.7 / 43.5 / 40.3。给 agent 一个 `ask_user` 工具后恢复 **+10.6 到 +41.9pp**。
  🟡/🟢 [arXiv:2602.10525](https://ar5iv.labs.arxiv.org/html/2602.10525)（Scale AI）
- LHAW 的欠规定分类法只有 **4 维**：**Goal / Constraint / Input / Context**——可直接当 checklist 用。
- ⚠️ **反直觉的一条**：LHAW 发现 **vaguify（含糊化）比 delete（删除）更危险**——"含糊指代如 'the file'、'an appropriate color' 会让 agent **自信地做出错误假设**，而完整删除反而让 agent 意识到信息缺失并求助。"
  🟡 同上

### 发现 5｜harness 主要买的是**成本与可靠性**，不是准确率——但取决于任务可并行度
- **The Scaffold Effect**（ICML 2026 workshop + Zenodo 预印本，同一组工作）：Qwen 3.6 Plus 与 MiniMax M2.5 两个模型 × Goose / OpenCode / OpenHands-SDK 三个 harness，跑 Terminal-Bench Pro 的 50 任务分层子集：
  - harness 选择造成 **高达 40× 的"每个已解决任务的 token 消耗"差异**；
  - 但**同一模型内的 pass-rate 差异只有 0–8pp**（Zenodo 版写 2–10pp），除最大的一对差距外**配对 bootstrap 置信区间都包含 0**；
  - 且**同样的 harness 特征失败指纹在两个模型上独立复现**（Goose 以 REASON 为主、OpenHands-SDK 是 VERIFY 和 MAX_TURNS、OpenCode 是 idle-loop/TIME）→ **"这些是 scaffold 属性，不是模型属性"**。作者主张把 **harness-model 对**而非 model 名作为比较单位（no-action turns 是"每任务的等待税"，不只是 token 税）。
  🟡 [ICML 2026](https://icml.cc/virtual/2026/82739) · [Zenodo 2026-04-27](https://zenodo.org/records/19819492)
- **但架构效应在可并行任务上可以极大**：Anthropic 称其多智能体研究系统（Opus 4 主导 + Sonnet 4 子 agent）在内部研究 eval 上**比单 agent Opus 4 高 90.2%**。**同一篇里更重要的数字**：在 BrowseComp 上，**token 用量单独解释了 80% 的性能方差**，另外两个因素是 tool call 次数和模型选择（三者合计 95%）。
  🔵 vendor claim，不可独立验证 [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
  > ⚪ **我的推断**：把这两条放在一起读——"架构带来的 +90.2%"很可能**主要是一次 token 预算增益的重新表述**。多智能体 = 花更多 token。所以不要指望"加 agent"本身有魔力。

## 2. 要素分解：规划能力到底来自哪里？

### 2.1 模型 —— 提供**上限**，且当前有一个**硬性前向规划深度限制**
| 证据 | 数字 |
|---|---|
| PlanBench，600 个 3–5 块 Blocksworld | o1-preview **97.8%**；但**同语义混淆版**（Mystery Blocksworld）只有 **52.8%**；随机混淆版 **37.3%** |
| 同上，扩大到需 ≥20 步的问题（110 例） | o1-preview **23.63%** |
| 同上，不可解实例识别 | 只有 **27%** 正确判定不可解；54% 直接编出一个不可能的计划 |
| 成本 | o1-preview **$42.12 / 100 实例** vs GPT-4o **$0.65**；而经典规划器 Fast Downward **100% 正确、0.265 秒、几乎免费** |
| 香草 LLM | 最好的 LLaMA 3.1 405B 在原生 Blocksworld 只有 62.6%；**所有 LLM 在 Mystery Blocksworld 上都 <5%** |
🟢 [arXiv:2409.13373](https://ar5iv.labs.arxiv.org/html/2409.13373)

- SokoBench（Sokoban，刻意剥离状态保持以隔离长程规划）：**超过 25 步后规划性能系统性下降**，提示存在 **"a fundamental constraint on forward planning capacity"**；而且给模型接上 **PDDL 解析/验证/求解工具只带来 "modest improvements"**，作者判断这是 **"inherent architectural limitations which might not be overcome by test-time scaling approaches alone"**。
  🟡 [arXiv:2601.20856](https://arxiv.org/abs/2601.20856)（2026-01）

⚪ **我的推断**：模型轴的真实图景是"**对人类觉得简单的符号规划很强，但一换表层形式、一拉长到 25+ 步、一遇到不可解就崩**"。这不像通用规划能力，像**近似检索 + 有限的模式外推**。这一轴的改善只能靠换模型，harness 修不了。

### 2.2 输入 —— **最大且最便宜的可控杠杆**
实测效应量（注意：不同基准，不可加）：
- 欠规定 → **55.8–67.8% 违规率**（UnderSpecBench）
- 删 1 段信息 → 成功率 **100 → 44.7–60.5**；删 2 段 → **38.7–43.5**（LHAW, MCP-Atlas）
- 提供澄清通道 → 恢复 **+10.6 到 +41.9pp**（LHAW）
- 成本侧：**每个问题问出去都有代价**。LHAW 引入 **Gain/Q**（每问一个问题的性能增益）并发现模型行为分化：**GPT-5.2 过度澄清，Gemini 系列欠澄清**。
🟡 [arXiv:2602.10525](https://ar5iv.labs.arxiv.org/html/2602.10525)

⚪ **我的推断**：这是唯一一条"**改一句话就有效**"的轴，投入产出比最高。而且它的失效模式最阴险——**不是报错，是自信地做错事**。

### 2.3 Harness —— 提供**结构、信息位置、验证、成本控制**；准确率增益是**个位数 pp 级**
可拆成四件具体的事，各项有独立证据：
1. **规划指导内容** → +7.17pp（CI 1.15–13.36），高复杂度任务才明显。🟡 [2609.20474](https://huggingface.co/papers/2609.20474)
2. **独立验证器** → 拒 61% 无效 / 误扣 17% 正确 / <$0.01。🟡 同上
3. **计划持久化 + 跨 context handoff**：Anthropic 的 harness 用 `claude-progress.txt` + git log + `feature_list.json`（**JSON 比 Markdown 更不易被模型改写**）+ init.sh；且明确要求 **"It is unacceptable to remove or edit tests"** 这类强硬措辞。关键洞察：**"每一 feature 一开始都标记为 failing"**，这样后续 agent 有明确的完成度轮廓。🟡 [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
4. **成本/可靠性**（非准确率）：40× token 差异、失败指纹是 scaffold 属性。🟡 [Scaffold Effect](https://zenodo.org/records/19819492)

### 2.4 环境模型 / 世界模型 —— **收益真实但条件苛刻**，是四条轴里证据最弱的一条
- ACL 2026 三层次框架（fidelity/consistency → scalability/robustness → agent utility），5 个文本环境："sufficiently trained world models capture coherent environment dynamics… unlock tangible agent improvements"：
  - **action verification 让 GPT-4o 在 WebShop 上 +5.5%**；
  - **warm-started RL 在 SciWorld 上 +15%**；
  - **但**："these benefits **hinge on behavioral coverage and environment complexity**"。
  🟢 [ACL 2026](https://aclanthology.org/2026.acl-long.366/)
- 反面：HORIZON 的分类法里第一类就是 **Environment（Environment Disturbance & Unable to Detect Environment Change）**——agent 会**假设环境已变而其实没变**、或**基于过期的 schema 快照继续生成 SQL**。这说明在真实系统里，**环境模型不准时的破坏力大于它准时的收益**。
🟡 [arXiv:2604.11978](https://arxiv.org/abs/2604.11978)

⚪ **我的推断**：环境模型的投入应该**仅限于"能廉价、确定性地查询真值"的那部分**（例如直接读 schema / 读文件系统 / 读 DB 状态），**不要**去训练或推理一个概率性的环境模型。上一条环境失败模式（用过期快照）的最便宜修法就是**每次重新读一次真值**，而不是维护一个模型。

### 2.5 直接回答："规划能力有多少来自模型 / harness / 输入？"

**没有实证的统一分解。** 我能负责地说的是**排序**（基于上述分轴证据）：

| 轴 | 对"任务成功"的效应量级 | 证据强度 | 可控性 |
|---|---|---|---|
| **输入质量** | 最大：欠规定可致 40–60pp 损失；澄清可恢复 10–42pp | 🟡 强（两个独立大规模研究） | **高**（改 prompt / 加澄清） |
| **模型** | 决定上限；**~25 步后系统性退化**，混淆形式下崩溃 | 🟢 强 | 低（只能换模型） |
| **harness·规划内容** | +7.17pp（CI 1.15–13.36） | 🟡 中（单篇，2026-09） | 高 |
| **harness·验证器** | 拒 61% 无效（高责任场景下价值最高） | 🟡 中（单篇） | 高 |
| **harness·成本/可靠性** | 40× token；pass rate 仅 0–8pp | 🟡 中（preprint + workshop） | 高 |
| **环境模型** | +5.5%（action verification, WebShop） | 🟢 但窄 | 中 |

⚪ **我的总体判断（无实证，是推断）**：在**当前模型能力下**，对"个人 harness 的自我规划"这个场景，**输入质量 > harness 结构 > 模型 > 环境模型**。理由：输入是唯一能拿到两位数 pp 的杠杆；harness 的规划内容只有个位数 pp；模型不可控；环境模型只在窄条件下有效。
**但这是排序，不是配比。**

## 3. 可操作设计建议（针对「语音驱动的个人 harness 自我规划」）

> 场景约束（来自项目现状）：语音输入、中文为主、规则式规划器已覆盖 15 条判据但只覆盖有限词表、SenseVoice **没有真实置信度**（合成置信度固定 0.80）、本地 M1 16GB 内存受限。

### P0-1｜先建「只读验证器」，不要先升级规划器
- 依据：发现 2——独立 verifier 拿到**几乎全部的 false-pass 收益**，成本 <$0.01/episode。(🟡 2609.20474)
- 落地：一个**只读、无副作用**的检查层，在动作执行前回答"这一步是否推进了当前计划？目标状态是否已达成？"。**绝不**让它有写权限。
- ⚠️ 注意 verifier **会误扣 17% 正确 episode** → 必须区分两种拒绝：
  - **拒绝执行**（安全侧，可以做激进）
  - **拒绝继续对话**（体验侧，必须保守，否则用户每 6 次就被打断一次）
- 对语音场景：验证失败的默认动作是**"说出来"而不是"停下来"**——语音用户对静默失败的容忍度极低。

### P0-2｜在规划**之前**做欠规定检测，用 4 维分类法
- 依据：发现 4。UnderSpecBench 的 55.8–67.8% 越界率 + LHAW 的 4 维分类法（Goal / Constraint / Input / Context）。
- 落地：把 4 维做成**规划前置的 checklist**，每一维问"这一维缺不缺？缺了会不会致命？能不能从上下文猜到？"（LHAW 用 `priority = criticality × (1 − guessability)` 排序，可直接借用）。
- ⚠️ **两个反直觉要点**：
  1. **优先检测 "vaguify" 而不是 "缺失"**——"最新的数据集""合适的格式""合理的航班"这类**看起来具体实则含糊**的措辞比直接缺失更危险，因为它让 agent 自信地猜错。（LHAW）
  2. **blast-radius 警告没用**——UnderSpecBench 明确发现"blast-radius cues barely reduce action propensity"。所以**不要指望"这是危险操作"的提示能阻止越界**，要靠**结构约束**（如动作白名单、目标实体必须显式解析）。
- **成本控制**：LHAW 的 Gain/Q 思路 → 给个人 harness 设一个**澄清预算**（例如每个任务最多 N 问，且只在 outcome-critical 维度上问）。GPT-5.2 式过度澄清会毁掉语音体验。

### P0-3｜架构默认：plan-then-execute + **lazy replanning**
- 依据：发现 3——准确率持平，token 省 2–3×。(🟢 CAIS 2026)
- 落地：
  - 生成**完整计划**后再执行，**不做**每步 eager 监控（那是 2–3× 白花的 token）；
  - **但必须实现重规划触发器**，因为计划平均只有前 2.65 步可执行 (🟡 2508.01300)。
- ⚪ 具体触发器设计（**我的推断，无直接实证**）：不要用"置信度阈值"（见 P1-2 原因）。用三条**结构性**触发器：
  1. **前置条件失效**：计划的下一步所需的前置状态与实际观测不符；
  2. **动作被拒/报错**：执行层返回不可恢复错误；
  3. **目标已达成或已不可能**：周期性地（而不是每步）重问"目标还成立吗 / 还可能吗"。
- 关键：**"已不可能达成"是当前模型最弱的一环**——PlanBench 里 o1 只有 27% 能正确判定不可解，54% 会编出一个不可能的计划。所以**必须用确定性检查而不是靠模型判断不可解**。

### P1-4｜规划产物必须落盘、可跨 context 存活、且是**高层约束**
- 依据：Anthropic 两篇工程博客 + 发现 1（记忆类失败占 3/7）。
- 落地（直接可抄）：
  - **计划存外部文件**，不留在对话里。Anthropic 的 lead researcher 明确"把计划存进 Memory，因为 context 超过 200k 会被截断"。
  - **用 JSON 而不是 Markdown** 存待办/特性清单——**"模型更不容易不当地修改或覆写 JSON 文件"**（Anthropic 原话）。
  - **每个条目初始标记为 failing/未完成**，形成明确的完成度轮廓，防止 agent"看到有进展就宣布完工"（这是 Anthropic 观察到的第二大失败模式）。
  - **context reset + 结构化 handoff** 优于单纯 compaction：compaction 保留连续性但不给干净的起点，**"context anxiety"（接近自认为的上下文上限时提前收尾）仍然存在**。
- ⚠️ 规划层次的**关键权衡**（Anthropic 原话的意译）：planner **不要**预先指定细粒度技术细节——**"如果 planner 试图提前指定细粒度技术细节并且搞错了，spec 里的错误会级联到下游实现"**。所以：**约束 deliverable（交付什么 + 怎么算完成），让执行者自己找路径。**
- 对语音场景：这意味着计划 artifact 必须是**人类可读、可被打断后续接**的——语音会话天然会被打断、跨设备、跨天。

### P1-5｜分离"生成"与"评判"，并且评判者要**悲观**
- 依据：Anthropic 明确观察到 **"被要求评估自己产出的 agent 倾向于自信地称赞自己的工作"**，即使在人看来质量明显平庸；而且 **"调一个独立的悲观 evaluator 比让生成者批判自己容易得多"**。
  🔵 [Anthropic harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- 落地：规划者 ≠ 验证者，两个不同 prompt / 不同 context，甚至可以是不同模型。规划者**不参与**验收。
- ⚠️ **成本要动态判定**：Anthropic 明确说 evaluator **不是固定的是非题**——"当任务超出当前模型能独立可靠完成的范围时，它才值这个成本"。在 Opus 4.6 上，很多任务不再需要 evaluator，它就是纯开销。
  → 对个人 harness：**按任务复杂度开关验证层**，不要无条件全开。

### P1-6｜记忆与错误复合 → resume，不要 restart
- 依据：HORIZON 7 类失败中 3 类与记忆相关（History Error Accumulation / Catastrophic Forgetting / Memory Limitation）；Anthropic："agents are stateful and errors compound… 我们不能从头重启，restart 昂贵且让用户沮丧"。
- 落地：checkpoint + 从断点恢复 + **把工具失败显式告知 agent 让它自适应**（Anthropic 说这"surprisingly well"）。

### P2-7｜用 7 类失败分类法做诊断，别只看成功率
- HORIZON 的分类法可直接复用为**日志归因 schema**：
  `Environment Disturbance / Instruction (Ill-defined/Partial Understanding) / Planning Error / False Assumption / History Error Accumulation / Catastrophic Forgetting / Memory Limitation`
  🟡 [arXiv:2604.11978](https://arxiv.org/abs/2604.11978)
- ⚪ **我的推断**：对**语音**场景，预计主导类别会是 **Instruction（语音欠规定）** 和 **Environment Disturbance（听错 / 环境变了没察觉）**，而不是 HORIZON 在文本场景测到的 Planning Error。**这个预测需要你自己实测验证**——这正是规则式规划器 15 条判据该被替换成的东西：**不是更全的词表，而是失败归因**。
- 理由：Anthropic 反复强调"read its traces on realistic problems"——**观察真实轨迹是唯一可靠的调参输入**，比加判据有效。

### P2-8｜对 VoxSign 的**关键接缝警告**：不要做"置信度驱动的澄清"
- 事实：SenseVoice **没有真实置信度**，当前是合成的固定 0.80（项目约束，不可擅改）。
- ⚪ **我的推断**：这意味着**任何基于 ASR 置信度阈值的澄清/重规划触发都是伪信号**——0.80 是常数，阈值永远不触发或永远触发。必须改用**结构性信号**：
  - 槽位完整性（动作所需参数是否都解析出来了）
  - 领域约束（解析结果是否落在合法值域内）
  - 动作边界（是否越出目标实体范围——UnderSpecBench 的 target underspecification 是最强信号）
  - 跨轮一致性（同一实体在相邻轮是否被解析成不同东西）
- 这一条是把本报告的通用结论**落到 VoxSign 现状**上最重要的一处。

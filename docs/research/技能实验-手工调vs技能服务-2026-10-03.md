# 技能实验：手工调 vs 技能服务（arch-design 应用于本项目）

> 2026-10-03 · Peter 要求："你先手工调，然后用 harness 调这个 skill，两者做个对比研究。"
> **结论先行：技能服务这条路是通的、质量高；但本次实验暴露了一个更重要的东西 ——
> 技能的质量上限 = 输入事实的质量，而这次输入事实是我（DSH）给错的。**

## 一、写 Key：我错了整整几轮

```
我前几轮报给 Peter：POST /api/keys/write-grant → 403 not_eligible
                  「caller=voxsign-harness, role=agent，需你去 AIOps 提权」

实际原因：body 格式错 —— 少了必需的 `purpose`，`ttl_min` 应为 `ttl_minutes`
指南原文（ops/aiops/docs/arch-design-skill-guide.md §3）：
  {"purpose":"<≤200字符>","ttl_minutes":30,"permissions":[{"domain":"skill","action":"run","target":"skill"}]}
  并明确写：role=agent 的读 Key write_eligible=true

按正确格式 ⇒ HTTP 200，签发成功（key 43 字符，expires_in_sec=7200）
```

**⇒ 我把它当成"外部阻塞"报了几轮，那是我自己造成的。**
**而正确格式白纸黑字在指南里 —— 我没读指南就先试了。这是"猜"的又一次代价。**

## 二、手工调：三步三次失败

```
① 技能全文(30条) + 项目结构 ⇒ HTTP 504 · 60.32s   ← nginx 60s 墙
② 缩到判据三条 + max_tokens 1600 ⇒ HTTP 200 · 17s
③ 但 content = 0 字符：finish_reason=length，completion_tokens=1600
   **全被 reasoning 吃光**（reasoning_content 3351 字符）

而 reasoning_content 里是：**模型在猜**
  "也许是 plan 与 route/recog/modelcenter 之间缺统一契约？"
  "可能的架构缺陷…" / "或者…" / "缺陷可能是…"
  ⇒ **正是该技能 cautions 第一条禁止的"臆造假设"**
```

## 三、技能服务 remote：一次成功

```
POST /api/skill/skills/ai-native-architecture-design/invoke
{"version":"1.1.0","inputs":{"task":...,"要求":...}}
→ HTTP 200 · 18.18s · source=remote · **6900 字符**
产出：口径声明 + C4 图 + 3 候选方向 + 加权决策矩阵 + 4 条 ADR + 风险登记册 + 6 个提问
它开篇自述：「不做外部推断。凡属推断处均显式标注 [推断]，凡属缺失信息处列入第 5 节提问，不臆造。」
```

| | 手工调（贴 prompt） | 技能服务 remote |
|---|---|---|
| 结果 | **0 字符** | **6900 字符** |
| 耗时 | 504 @60.3s → 200 @17s | **200 @18.2s，不撞 60s 墙** |
| cautions | **被无视，模型在猜** | **被遵守（口径声明 + [推断] + 提问）** |

**⇒ 同一技能文本、同一模型，一个在猜、一个守规矩。差别不在技能，在"谁在执行它"。**
**把技能贴进 prompt ⇒ 技能是"参考资料"；平台把 knowhow 注入 system prompt 并约束角色 ⇒ 它才是"技能"。**

## 四、⭐ 本次最重要的发现：**我给的前提是假的**

**我在任务里写"已知事实（不要臆造）"**：
> 「plan/ tools/ space/ 被 asr/ 或 cmd/ 引用的次数 = 0 ⇒ 规划器/工具注册表/域门禁从来没有服务入口」

**真相（`go list -deps`）：**
```
./cmd/vhs-asr/     依赖执行内核的包数: 4   ← plan/tools/space/verify 全在
./cmd/vhs-ledger/  依赖执行内核的包数: 4
plan   ← cmd/vhs-asr/main.go · asr/server.go · asr/task.go · ref/resolver.go · route/router.go
tools  ← asr/task.go · pipeline/pipeline.go · plan/manifest.go · server/server.go · main.go
space  ← asr/task.go · pipeline/pipeline.go · ground/ground.go · plan/manifest.go
verify ← pipeline/pipeline.go · tools/executor.go · main.go
```

**假前提的来源**：早先一次 `grep "PlanWithL2|L2Enabled" asr/ cmd/` 无命中 ——
**那在当时为真（L2 确实没接线），但我过度推广成"整个包无人引用"，并作为"已知事实"喂给了技能。**

**后果**：技能据此产出**一份带 C4 图、决策矩阵、4 条 ADR、风险登记册的完整评审 —— 而核心结论全错**：
- ❌ "能力层已长成、执行层从未通电"
- ❌ C4 图把这些包全标成 dead

**⇒ 技能的质量上限 = 输入事实的质量。**

## 七、教训（写进本项目实例集）

1. **"grep 无命中" ≠ "包无人引用"** —— 前者是一次符号检索，后者是全图依赖断言。**我混淆了两者。**
2. **给模型/技能的"已知事实"必须自己先查证** —— 否则产出的严谨度会掩盖地基错误。
3. **读指南再动手** —— write-grant 的格式白纸黑字在指南里，我猜了三轮。
4. **技能服务 ≠ 贴 prompt** —— 前者以角色准则注入并约束，后者只是参考资料。
5. **`已查证优先于一方称` 已真实生效一次，且推翻的是 Lead。**

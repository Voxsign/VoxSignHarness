## 2. 产品目标与核心原则

### 2.1 核心闭环

核心流程是：

**record → discuss → control → 归因**

北极星指标是完成一轮认知闭环的速度：记录输入、讨论并归因、执行控制，最后沉淀结果，便于下一轮使用。

一次开发任务的总体路径为：

**说出意图 → 容错与理解 → 规划 → 风险分级 → 执行 → 独立校验 → 回执 → 经验沉淀**

Harness 的职责是管理契约、风险闸门和校验，不负责自行生成代码。代码可以由模型工具循环或外部编码代理生成，用户负责描述意图并验收。

### 2.2 与传统开发方式的差异

| 维度 | 传统开发 | 语音驱动开发 |
|---|---|---|
| 输入 | 精确键鼠操作或命令 | 含 ASR 错误、口语和省略的模糊语音 |
| 输出 | 直接编辑代码文件 | 意图、执行、校验结果及可审计回执 |
| 迭代 | 手写、运行、检查、修改 | 对话式循环：说、做、回执、再说 |
| 验证 | 人工查看或运行 | 独立校验器读取实际状态 |
| 经验沉淀 | 依赖人工维护文档 | 轨迹、归因和认知数据自动沉淀 |
| 记忆 | 主要依赖个人记忆 | 缓存、project-map、decisions-log 等机制 |

### 2.3 关键原则

- **接口契约独立、只增不改并版本化**：语义可以补充，但不得绕过冻结接口改变签名。
- **独立校验**：关键结果必须依据实际状态校验，不能只相信执行工具自报成功。
- **可审计、可追溯**：输入、决策、执行、校验及归因应可通过轨迹和回执追踪。
- **讨论不自动改策略**：讨论产生的归因或建议不能直接修改策略或词典，必须有人确认。
- **契约与缓存联动失效**：策略、空间注册表或工具契约变化时，旧缓存不能继续作为可信结果使用。

## 3. 架构分层

系统采用单向依赖思路，分为输入容错、认知、接口契约、执行和沉淀等职责层。

### 3.1 输入容错层

处理语音输入及其不确定性：

1. 保留 ASR 原文。
2. 清洗输入。
3. 使用词典进行纠错，例如将误识别词纠正为项目专有名词。
4. 产出意图数据，详细设计示例包含 `type`、`path`、`params`、`confidence` 等字段。

ASR 原文应作为可追溯输入保留，不应以纠错结果取代原始记录。

### 3.2 认知层

管理项目及用户偏好相关的慢变信息，包括：

- `project-map`
- `decisions-log`
- 用户偏好（prefs）

认知数据不在主执行循环中实时更新。建议由独立低频任务批量更新，例如每日或每 N 次任务后重新索引。执行前按当前路径或模块进行相关性检索，只注入与当前任务相关的内容，避免无差别注入全部认知数据。

### 3.3 接口契约层

工具能力应通过独立契约定义并进行版本管理。执行层依赖契约，不应绕过契约直接调用未授权能力。

详细设计列出的工具能力包括：

- `git`
- `file`
- `search`
- `test`
- `run`
- `verify`
- `ask`

其中 `verify` 是独立校验器契约，不能与 `run` 混为一体；闭环关键节点必须具备契约和审计能力。

### 3.4 执行层

执行层负责根据意图和计划完成风险分级、确认、执行、独立校验与回执。Harness 负责执行闸门和校验，不负责生成代码。

### 3.5 沉淀层

沉淀层保存任务轨迹、归因和可供后续检索的经验。三通道状态通过追加式 JSONL 轨迹表达，详情见「认知闭环与数据沉淀」。

## 4. 意图分类与工具契约

### 4.1 八类开发意图

| 意图 | 示例 | 风险基线 | 契约能力 |
|---|---|---|---|
| `EDIT` | 把报价模块错误提示改成中文 | 可逆、影响中 | `file`、`git`、`test`、`verify` |
| `DEBUG` | 修复一个崩溃问题 | 可逆、影响高 | `git`、`test`、`run`、`verify` |
| `QUERY` | 查询某个函数的定义位置 | 只读 | `search`、`file`、`git` |
| `TEST` | 运行测试 | 只读 | `test` |
| `COMMIT` | 提交一批变更 | 不可逆 | `git` |
| `DEPLOY` | 发布到服务器 | 不可逆 | `run`、`git`、`verify` |
| `NOTE` | 记录一个想法 | 只读 | `file` |
| `ASK` | 询问某个库的用法 | 只读 | `ask` |

意图类别基线并不能代替实际风险判定。执行前仍须结合具体任务、空间约束和工具能力进行风险分级。

### 4.2 意图数据约束

现有材料指出意图包含类型、路径、参数和置信度等信息，但 SPEC v2 中正式意图 Schema 所在内容已截断。因此，正式字段必填性、枚举、默认值和非法值处理应以完整 SPEC 与冻结接口为准；不能仅根据本文示例自行扩展或推断。

M2 新增字段应全部使用 `omitempty`。M1 类别（如 `TIME`、`FILE_*`）与 M2 类别（如 `EDIT`）需要并存；M2 管线只使用 `TaskClassifier` 产出的分类结果。

## 5. 执行链与安全闸门

### 5.1 固定执行顺序

SPEC v2 要求按以下顺序执行：

1. 接收并记录 `input_raw`。
2. 清洗输入。
3. 进行词典纠错。
4. 通过 `TaskClassifier` 识别任务。
5. 执行 refer 消解。
6. 选择 space，并进行 `space_check`。
7. 进行风险分级。
8. 获取所需确认。
9. 根据契约执行工具。
10. 执行独立校验。
11. 进行归因并写入轨迹。
12. 写入缓存四元组。
13. 输出四行回执。

不得绕过空间检查或风险分级直接执行工具。工具执行失败或校验失败时，应进入归因与异常诊断流程，而不是将失败包装为成功。

### 5.2 执行主体与 Harness 职责

- EDIT、DEBUG 等任务可由模型工具循环或外部编码代理执行。
- Harness 负责 `space_check`、风险闸门和独立校验。
- Harness 不承担代码生成职责。
- 工具调用须按其契约与能力执行，不得把未经授权的操作交给执行器。

### 5.3 确认、执行与校验

不可逆操作（如提交、部署）具有更高风险，需遵守风险分级及相应确认规则。具体确认条件和风险等级映射应以完整规格及冻结接口为准。

校验必须独立于执行主体：执行器的成功回执不能代替实际状态验证。对于校验失败，应保留失败结果并进入归因或诊断流程。

## 6. 认知闭环与数据沉淀

### 6.1 三通道轨迹

record、discuss、control 三个通道通过 JSONL 追加式轨迹表达：

- **record**：记录原始输入、纠错结果及意图。
- **discuss**：记录归因、决策理由和回写内容。
- **control**：记录执行过程、校验结果及回执。

轨迹采用 append-only 思路，保留过程记录以供审计和复盘。

### 6.2 Discuss 输出及限制

一次 discuss 至少应产生：

- 一条 `kind=attribution` 轨迹。
- 一条 `discuss-log`。

**禁止 discuss 自动修改策略或词典。** 相关变更须经过人工确认后才能生效。

### 6.3 缓存与认知更新

SPEC v2 要求写入缓存四元组，并规定策略等版本变化时旧缓存失效。详细设计另提到三元组缓存，但现有材料未说明二者的字段定义及关系；实现时必须依据完整缓存契约澄清，不能将三元组和四元组视为同一结构。

project-map、decisions-log 和偏好等认知数据属于慢变信息，应通过独立低频任务更新，并在执行前按相关性检索。

## 7. 风险策略与版本失效机制

### 7.1 策略版本

策略使用 JSON 表达，示意结构如下：

```json
{
  "policy": {
    "policy_version": 2,
    "spec": "SPEC-v2-可执行规格书.md",
    "spec_version": "v2.0",
    "invalidates": {
      "on_policy_change": true,
      "on_space_registry_bump": true,
      "on_contract_bump": true
    }
  }
}
```

### 7.2 缓存失效要求

以下任一变化都应视为旧缓存失效条件：

- 策略版本变化。
- space 注册表版本变化。
- 工具契约版本变化。

发生相应策略、域或契约变更时，应调用 `cache.BumpPolicyVersion()`，并禁止继续信任旧缓存。

### 7.3 JSON 格式约束

manifest、contract、policy 的机器可读格式采用 JSON 文件：

- `.space.json`
- `.contract.json`
- 策略 JSON

不采用 YAML，原因是标准库不提供 YAML 解析器，引入第三方依赖会违反单二进制、零第三方依赖的冻结约束。旧文档中的 YAML 仅作为示意，不是机器格式。

## 8. 异常自愈架构

### 8.1 设计目标与当前问题

现有链路对工具失败主要给出静态建议，对模型调用失败则使用固定降级文案。这种方式难以针对具体错误定位，也不能积累同类问题的修复经验。

异常自愈设计的目标是在现有执行链外增加模型中心的问题定位能力，使系统能对异常分类、判断根因、提出恢复动作，并将有效诊断沉淀为知识。

该架构当前为 v0.1 设计方向，异常模型（拟称 JEV/GAB）的最终名称、接口和生产契约仍需确认。

### 8.2 三环处理流程

1. **知识库命中检查**  
   使用错误指纹（如错误前缀、工具和意图）检查是否已有根因与修复建议。命中时复用已有建议，避免重复调用模型。

2. **问题定位模型诊断**  
   未命中时，将任务原文、意图和失败轨迹（工具、参数、错误等）提交给模型中心的异常诊断接口。设计中的 JSON 输出包含分类、根因、置信度、可恢复性、建议和动作等信息；最终 Schema 尚待契约化。

3. **自愈执行器处理**  
   根据诊断动作决定是否重试、修改参数或工具、降级、询问用户或停止。设计要求重试有上限以避免死循环。

### 8.3 诊断动作

设计中列出的动作包括：

- `retry`：按建议重试，最多 2 轮。
- `modify`：修正参数、切换工具或更换模型后重试。
- `fallback`：安全降级，例如 QUERY 降级为提示文案。
- `ask`：转回询问用户。
- `stop`：停止执行并进行归因。

失败后是否再次进入诊断模型也受轮数限制；设计目标是避免无限诊断与执行循环。

### 8.4 插入点与学习回写

异常诊断可在以下失败点触发：

- 工具执行回执 `receipt.OK=false`。
- 独立校验结果 `verify.Status=Fail`。
- 模型调用报错或返回空内容。
- 模型中心调用超时或响应过慢。

失败且有有效修复结果时，可将异常、根因和成功修复写入 `exceptions.jsonl`。归因记录应携带诊断结论，以替代泛化静态建议。

异常诊断、自愈和学习回写不能绕过原有的空间检查、风险控制、工具契约或独立校验。

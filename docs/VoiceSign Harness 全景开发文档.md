# VoiceSign Harness 全景开发文档

## 1. 文档定位与目标

本文整合 VoiceSign Harness 的可执行规格、语音驱动开发设计与异常自愈架构，作为系统整体设计与开发协作的全景文档。

VoiceSign Harness 面向语音驱动的软件开发场景：用户用自然语言描述变更意图，系统完成输入容错、意图识别、规划、风险分级、受控执行、独立校验、回执与经验沉淀。

**核心目标：**

> 用嘴说变更意图，Harness 完成容错 → 意图 → 规划 → 风险分级 → 执行 → 独立校验 → 回执 → 沉淀，让下一次交互更准确。

系统北极星是加快认知闭环：**record → discuss → control → 归因**，并让整个闭环可审计、可复现、可持续改进。

## 2. 设计原则与权威依据

### 2.1 设计原则



* **契约优先：** 接口形状以冻结契约为准；规格定义语义，不擅自改变已冻结签名。

* **只增不改：** 新增契约字段应向后兼容，M2 新增字段使用 `omitempty`。

* **独立验证：** 校验器读取实际状态，不以执行模型或工具的自述作为验证依据。

* **策略变更即失效：** 策略、域注册表或工具契约变化后，不再信任旧缓存。

* **边界清晰：** Harness 负责输入处理、风险 gate、工具调度、独立校验与沉淀；不自行生成代码。

* **活的规范：** 每条规范都应有可执行验证器；没有验证器的项目须明确标记为未完成。

### 2.2 版本与契约关系



* 可执行规格：SPEC v2.0，定义系统语义与执行约束。

* 上游接口冻结文档：`INTERFACE-FREEZE-M2.md`，定义 API 形状。

* 详细设计 v2：作为 M2 的施工设计。

* 异常自愈架构：设计 v0.1，定义异常诊断与自愈方向，仍需进一步落地和验收。

若规格、接口冻结文档与实现发生冲突，应先核对上游契约和对应版本，不应通过实现悄然改变接口语义。

## 3. 系统定位与开发模式

### 3.1 与传统开发方式的区别



| 维度   | 传统开发        | VoiceSign Harness                     |
| ---- | ----------- | ------------------------------------- |
| 输入   | 精确键鼠操作或命令   | 可能含 ASR 错误、省略和口语表达的语音                 |
| 处理   | 人工理解并操作     | 转换为结构化意图，按契约执行                        |
| 验证   | 人工查看或运行     | 独立校验器读取实际状态                           |
| 交互   | 手写、运行、观察、修改 | 说出意图，执行后接收回执，再继续交互                    |
| 经验沉淀 | 人工维护注释、文档   | 轨迹、归因、认知资料和异常知识库                      |
| 代码生成 | 开发者直接编写     | 人描述意图，模型或外部编码代理生成，Harness 负责 gate 与验证 |

核心开发循环为：**意图描述 → 模型或代理生成 → 契约执行 → 独立验证 → 可审计回执与经验沉淀**。

### 3.2 Harness 的职责边界

Harness 的职责包括：



* 保存原始输入并进行清洗、词典纠错和意图分类。

* 对执行空间与风险进行检查，并在需要时要求用户确认。

* 按工具契约执行任务，并对执行结果进行独立校验。

* 记录执行轨迹、归因与回执，维护相关缓存和知识。

* 在执行、验证或模型调用失败时，进入异常诊断和自愈流程。

Harness **不负责自行生成代码**。代码由模型工具循环或外部编码代理完成；Harness 负责执行 gate 和独立校验。

## 4. 总体架构

### 4.1 分层结构



1. **输入容错层**

* 保存 ASR 原文。

* 清洗输入。

* 使用词典纠正专有名词或识别错误，例如将 “美墅” 纠正为 “Mansour”。

* 生成结构化意图。

1. **认知层**

* 保存 `project-map`、`decisions-log`、用户偏好等资料。

* 更新采用独立、低频任务，例如每日或每 N 次交互批量 reindex。

* 主循环中不实时写入认知资料。

* 注入上下文前按当前路径或模块检索相关切片，避免无关信息进入执行上下文。

1. **接口层**

* 以独立、版本化契约描述工具能力。

* 闭环关键节点必须契约化，包括执行和独立验证。

1. **执行层**

* 负责意图规划、风险分级、执行调度、独立校验和回执。

* 执行逻辑应尽可能确定、快速，并保持单向依赖。

1. **沉淀层**

* 记录轨迹、归因、缓存和异常诊断知识。

* 支持审计、回溯、检索与后续改进。

### 4.2 工具契约

当前设计列出的工具为：



* `git`

* `file`

* `search`

* `test`

* `run`

* `verify`

* `ask`

详细设计中的 “六工具” 表述与实际列出的七项不一致；实现与验收时应以冻结契约中定义的工具清单和版本为准，不能仅凭文案中的数量判断。

其中：



* `search` 用于 QUERY 等意图的精确检索。

* `verify` 是独立校验器契约，与 `run` 分离；必须有版本和审计信息。

* 工具只能按其声明的 capabilities 执行操作。

## 5. 意图分类与执行约束

### 5.1 意图类别



| 意图       | 示例       | 风险基线   | 常见契约                         |
| -------- | -------- | ------ | ---------------------------- |
| `EDIT`   | 修改错误提示文案 | 可逆，影响中 | `file`、`git`、`test`、`verify` |
| `DEBUG`  | 修复程序崩溃   | 可逆，影响高 | `git`、`test`、`run`、`verify`  |
| `QUERY`  | 查询函数定义位置 | 只读     | `search`、`file`、`git`        |
| `TEST`   | 运行测试     | 只读     | `test`                       |
| `COMMIT` | 提交当前改动   | 不可逆    | `git`                        |
| `DEPLOY` | 发布到服务器   | 不可逆    | `run`、`git`、`verify`         |
| `NOTE`   | 记录一个想法   | 只读     | `file`                       |
| `ASK`    | 询问库或工具用法 | 只读     | `ask`                        |

意图 Schema 的完整字段定义、必填项、枚举、默认值及非法值处理，应以对应规格章节和冻结契约为准。当前可确认的意图表达包含 `type`、`path`、`params`、`confidence` 等信息。

### 5.2 高风险与不可逆操作

`COMMIT`、`DEPLOY` 等不可逆操作不能仅凭意图分类直接执行。执行前必须完成空间检查、风险分级，并按风险策略要求用户确认。执行失败或校验失败应进入诊断和归因流程。

## 6. 主执行链与状态记录

### 6.1 固定执行顺序

主链必须遵循以下顺序：



1. 接收并保存 `input_raw`。

2. 清洗输入。

3. 执行词典纠错。

4. 运行 `TaskClassifier` 生成任务分类。

5. 进行 refer 指代消解。

6. 选择执行空间（space select）。

7. 检查执行空间（`space.Check`）。

8. 进行风险分级。

9. 按风险要求取得用户确认。

10. 按工具契约执行工具操作。

11. 运行独立校验器。

12. 生成归因并写入轨迹。

13. 更新四元组缓存并生成四行回执。

不得在空间检查或风险分级之前执行工具操作。分类与执行必须使用约定的分类器产出，不得通过旁路逻辑绕过统一链路。

### 6.2 三通道与轨迹

`record`、`discuss`、`control` 是轨迹 JSONL 中的三个 stage，采用 append-only 记录：



* **record：** 原始输入、纠错结果和识别意图。

* **discuss：** 归因、决策理由及回写信息。

* **control：** 执行过程、校验结果和执行回执。

`discuss` 的输出包括：



* 一条 `kind=attribution` 的轨迹记录。

* 一条 `discuss-log` 记录。

`discuss` 不得自动修改策略或词典；任何此类更新都须经人工确认。

### 6.3 回执与可追溯性

执行结果应通过回执呈现，并可检索、撤销或追溯。回执应反映实际执行和独立校验结果，不能将工具自报成功直接视为任务成功。

规格要求输出四行回执，但现有材料未给出四行的完整字段定义；实现时应遵循冻结契约或后续正式定义，不应自行假设格式。

## 7. 版本策略、配置与缓存失效

### 7.1 JSON 配置格式

Manifest、contract 和 policy 统一采用 JSON 文件：



* `.space.json`

* `.contract.json`

* policy JSON

不使用 YAML。原因是系统要求单二进制、零第三方依赖，而 Go 标准库不包含 YAML 解析器；引入第三方 YAML 依赖不符合冻结约束。历史文档中的 YAML 示例仅作说明，机器可读格式以 JSON 为准。

### 7.2 策略失效规则

策略配置至少包含以下版本与失效信息：



```
{
  "policy": {
    "policy_version": 2,
    "spec": "SPEC-v2-可执行规格书.md",
    "spec_version": "v2.0",
    "invalidates": {
      "on_policy_change": true,
      "on_space_registry_bump": true,
      "on_contract_bump": true
    }
  }
}
```

发生以下任一变化时，必须使旧缓存失效：



* 策略版本变化。

* Space 注册表版本变化。

* 工具契约版本变化。

策略、域或契约改动后，应调用 `cache.BumpPolicyVersion()`。失效后不再信任基于旧策略或旧契约得到的缓存结果。四元组缓存的具体元素定义应以对应契约为准；当前材料未完整列出其结构。

* Go 模块名为 `voicesign-harness`，不带域名前缀。

## 9. 异常诊断与自愈

### 9.1 设计目标与适用范围

异常自愈设计针对工具执行失败、独立校验失败和模型调用失败。目标是避免只返回通用静态建议，让系统能结合实际错误定位原因、选择有边界的恢复动作，并在成功后积累可复用知识。

该部分当前标记为设计 v0.1，属于待落地的架构方向，不应误认为所有能力均已实现。

### 9.2 三环处理流程



1. **异常知识库命中检查**

* 根据错误指纹查询既有根因与修复方案。

* 指纹由错误前缀、工具和意图等信息构成。

* 命中后复用已有建议，避免重复调用诊断模型。

1. **问题定位模型诊断**

* 未命中知识库时，调用模型中心的问题定位接口。

* 设计中称为 JEV/GAB 异常模型，最终名称和接口仍需确认。

* 输入包括任务原文、意图及失败轨迹，例如工具、参数和错误信息。

* 输出为 JSON，包含错误分类、根因、置信度、可恢复性、建议和动作等信息。

1. **自愈执行器处理**

* `retry`：按建议重试。

* `modify`：修正参数，或切换工具、模型后重试。

* `fallback`：安全降级，例如 QUERY 返回降级文案。

* `ask`：将问题交还用户。

* `stop`：终止处理并归因。

### 9.3 重试边界与回写



* 单次自愈执行最多重试 2 轮，防止死循环。

* 若修复后仍失败且允许再次诊断，可再次调用诊断流程；诊断轮数上限为 2 轮。

* 成功修复后，将异常、根因和成功修复方案写入 `exceptions.jsonl`。

* 归因记录应携带诊断结论，以诊断信息替代笼统静态建议。

* 自愈流程不得绕过空间检查、风险控制、确认要求或工具契约。

### 9.4 触发场景



| 触发点      | 触发条件                      | 处理方向                             |
| -------- | ------------------------- | -------------------------------- |
| 工具执行     | 任一 `receipt.OK=false`     | 诊断具体错误，不只返回通用环境建议                |
| 独立校验     | `verify.Status=Fail`      | 结合执行轨迹定位失败原因                     |
| 模型调用     | `queryLLMAnswer` 返回错误或空内容 | 诊断预算、网络、参数等问题，再决定重试或降级           |
| 超时或无快速响应 | 模型中心调用超过阈值仍无响应或响应过慢       | 将模型名和调用信息交给诊断层，判断网络、排队、模型卡死或参数问题 |

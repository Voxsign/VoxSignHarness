# VoiceSign Harness 全景开发文档

## 1. 文档定位与目标

VoiceSign Harness 面向语音驱动开发（Voice-Driven Development，VDD），将口语化、可能含有识别错误的变更意图，转化为可执行、可验证、可追溯的开发闭环。

核心流程是：

> **容错 → 意图识别 → 规划 → 风险分级 → 执行 → 独立校验 → 回执 → 归因与沉淀**

用户描述意图，模型或外部编码代理负责生成代码；Harness 负责执行边界控制、风险门禁、独立验证和过程留痕，不自行生成代码。

本文汇总当前可见的规格、详细设计与异常自愈设计信息。文档中引用的部分上游材料存在截断，因此未提供完整定义的内容会标记为“待确认”，不以推测补齐。

## 2. 设计原则与产品边界

### 2.1 核心原则

- **可审计**：输入、意图、执行、校验和归因均形成可追溯记录。
- **独立校验**：校验器读取实际状态，不以执行方的自我报告作为通过依据。
- **先门禁、后执行**：执行必须经过空间检查和风险分级。
- **契约稳定**：接口契约版本化，只增不改；上游 API 形状冻结后，规格定义语义而不改签名。
- **规范可失效**：策略、空间注册表或工具契约发生变化时，旧缓存不得继续被信任。
- **沉淀与主循环解耦**：认知资料采用低频异步更新，避免实时修改带来不可预测行为。
- **异常可学习**：对执行或模型调用失败进行诊断；成功修复后将经验写入异常知识库。

### 2.2 Harness 职责边界

Harness 负责：

- 输入清洗和词典纠错；
- 意图分类与执行计划衔接；
- 空间选择与 `space_check`；
- 风险分级与必要确认；
- 按契约调用工具；
- 执行后的独立校验；
- 回执、轨迹、归因及知识沉淀；
- 对异常进行诊断、自愈调度和学习回写。

代码生成由模型工具循环或外部编码代理完成。Harness 不替代编码代理，也不自行生成代码。

### 2.3 产品名称与仓库约定

源材料使用“VoxSign Harness”，目标文档标题使用“VoiceSign Harness”。本文以 **VoiceSign Harness** 作为文档名称；如仓库或产品实际名称仍为 VoxSign，应在代码、模块和发布材料中统一命名。

规格记录的 Go 模块名为 `voicesign-harness`，不带域名前缀。

## 3. 总体架构

### 3.1 分层结构

| 层次 | 职责 | 主要内容 |
|---|---|---|
| 输入容错层 | 将语音输入转成稳定、可处理的请求 | ASR 原文留底、清洗、词典纠错、意图 JSON |
| 认知层 | 提供项目背景与用户决策上下文 | `project-map`、`decisions-log`、偏好 |
| 接口层 | 定义工具能力和调用契约 | `git`、`file`、`search`、`test`、`run`、`verify`、`ask` 等 |
| 执行层 | 编排意图、门禁、工具执行和校验 | 规划、空间检查、风险分级、执行、验证 |
| 沉淀层 | 记录可追溯过程并积累经验 | JSONL 轨迹、归因、异常知识库、缓存 |

### 3.2 单向依赖与契约要求

- 各层按职责单向依赖，契约放在独立文件中。
- M2 新增字段应使用 `omitempty`，保持对既有数据的兼容。
- M1 类别（如 `TIME`、`FILE_*`）与 M2 类别（如 `EDIT` 等）需要并存。
- M2 管线应使用 `TaskClassifier` 的产出，不应绕过分类器自行构造分类结果。
- API 形状以冻结接口文档为准；本规格不应擅自修改已冻结签名。

## 4. 输入与意图模型

### 4.1 输入处理

输入链路包括：

1. 保存 ASR 原始文本；
2. 清洗口语、冗余内容和格式噪声；
3. 使用词典修正常见识别错误；
4. 生成意图结构；
5. 将意图交给后续规划和门禁流程。

词典纠错示例：将语音识别错误“美墅”纠正为“Mansour”。原文应保留，以便后续审计和归因。

### 4.2 开发意图分类

详细设计列出以下八类意图：

| 意图 | 示例 | 风险基线 | 契约能力 |
|---|---|---|---|
| `EDIT` | “把报价模块错误提示改中文” | 可逆，影响中 | `file`、`git`、`test`、`verify` |
| `DEBUG` | “修一下这个崩溃” | 可逆，影响高 | `git`、`test`、`run`、`verify` |
| `QUERY` | “这个函数在哪定义” | 只读 | `search`、`file`、`git` |
| `TEST` | “跑一下测试” | 只读 | `test` |
| `COMMIT` | “提交这批改动” | 不可逆 | `git` |
| `DEPLOY` | “发布到服务器” | 不可逆 | `run`、`git`、`verify` |
| `NOTE` | “记一下这个想法” | 只读 | `file` |
| `ASK` | “这个库怎么用” | 只读 | `ask` |

风险基线只用于初始分级，实际执行前仍需经过风险分级和必要确认。

### 4.3 意图 Schema 状态

可见材料提到意图结构包含 `type`、`path`、`params`、`confidence`，但正式 Schema 的完整字段、必填规则、枚举、默认值和非法值处理位于被截断的规格内容中。

因此，以下内容仍需以权威规格或冻结契约确认：

- 各字段类型及必填条件；
- 意图类别的完整枚举；
- 默认值和非法输入的处理方式；
- 置信度阈值及低置信度时的交互规则。

## 5. 主执行链与状态流转

### 5.1 执行顺序

主链必须按以下顺序串行执行：

1. `input_raw`：保存原始输入；
2. `clean`：清洗文本；
3. 词典纠错；
4. `TaskClassify`：识别任务意图；
5. `refer`：解析指代；
6. 空间选择；
7. `space_check`：校验操作空间和边界；
8. 风险分级；
9. 必要时请求用户确认；
10. 调用工具执行；
11. `verify`：进行独立校验；
12. 归因并写入轨迹；
13. 更新缓存四元组；
14. 输出四行回执。

规格明确要求执行不得早于 `space_check` 和风险分级。上述列表包含规格中要求的处理节点；“十三步”是规格对主链的称呼，但可见清单将空间选择、空间检查及若干记录动作分别展开，实际步骤编号应以冻结流程定义为准。

### 5.2 轨迹通道

轨迹以 JSONL 追加写入，包含三个阶段：

- **record**：记录原始输入、纠错结果和识别意图；
- **discuss**：记录归因、决策理由及回写；
- **control**：记录执行、校验和执行回执。

`discuss` 输出至少包括：

- 一条 `kind=attribution` 轨迹；
- 一条 `discuss-log`。

`discuss` 不得自动修改策略或词典。相关变更必须由人确认。

### 5.3 测试状态

可见规格记录：

- `pipeline.TestPipelineOrdering`：串行顺序测试，记录为实测通过；
- `pipeline.TestPipelineWritesAttribution`：归因轨迹写入测试，记录为实测通过。

## 6. 空间、风险与执行控制

### 6.1 空间门禁

工具执行前必须完成空间选择与 `space_check`。空间注册表是影响执行范围的基础配置，其变更会导致策略版本及相关缓存失效。

### 6.2 风险分级与确认

风险分级决定操作是否可自动执行，或是否需要用户确认。尤其是 `COMMIT`、`DEPLOY` 等不可逆操作，必须按既定风险规则控制。

具体风险等级枚举、阈值和确认策略未在可见材料中完整给出，需以正式规格和冻结契约为准。

### 6.3 工具执行边界

- 执行器按照工具能力（caps）调用工具。
- Harness 负责 gate、执行编排和独立校验，不承担代码生成。
- 工具调用的参数、权限和可操作范围必须由契约约束。
- 失败执行应进入异常诊断流程，不能仅以静态通用建议结束。

### 6.4 工具数量待统一

规格和详细设计均提到“六工具”，但详细设计所列名称为 `git`、`file`、`search`、`test`、`run`、`verify`、`ask`，共七项。此处存在数量与清单不一致。

实现和测试应以冻结接口契约中的实际工具集合为准，并更新文档中的数量描述，避免按“六工具”误删或遗漏能力。

## 7. 独立校验与回执

### 7.1 独立校验

`verify` 是与 `run` 分离的独立校验能力，具有自己的契约、版本和审计要求。校验器应读取实际状态，而非读取执行方的自报结果。

闭环关键节点应契约化。执行成功不等于校验成功；校验失败必须进入异常处理和归因流程。

### 7.2 回执

每轮执行向用户提供结构化回执。规格要求输出“四行回执”，但可见材料未包含四行的具体字段格式，需从冻结接口或完整规格中确认。

回执应与轨迹、执行结果和校验状态一致，不能以未验证的执行方描述替代实际结果。

## 8. 认知层、缓存与策略失效

### 8.1 认知资料

认知层包括：

- `project-map`；
- `decisions-log`；
- 用户偏好。

认知资料属于文字型、慢变化信息，不应在主执行循环中实时写入。更新应作为独立低频任务运行，例如每日或每 N 次批量重新索引。

注入认知资料前应先进行相关性检索，只注入与当前路径或模块相关的切片。

### 8.2 缓存失效策略

策略声明示例：

```json
{
  "policy": {
    "policy_version": 2,
    "spec": "SPEC-v2-可执行规格书.md",
    "spec_version": "v2.0",
    "invalidates": {
      "on_policy_change": true,
      "on_space_registry_bump": true,
      "on_contract_bump": true
    }
  }
}
```

执行约束：

- 策略版本变化时，旧缓存全部失效；
- 空间注册表或工具契约版本变化时，旧缓存同样失效；
- 相关变更必须调用 `cache.BumpPolicyVersion()`；
- 不得继续信任旧策略、旧空间或旧契约生成的缓存。

### 8.3 缓存结构待核对

规格提到“四元组缓存”，详细设计提到“三元组缓存”。两者不一致。缓存字段、键结构和生命周期应以现行实现及冻结契约为准，并在后续规格中统一。

## 9. 契约与配置格式

### 9.1 JSON 文件约定

空间、工具契约和策略文件采用 JSON：

- `.space.json`
- `.contract.json`

## 10. 异常诊断与自愈

### 10.1 目标与触发条件

异常自愈设计目标是：出现失败时不止提供静态建议，而是由问题定位模型分析异常、建议恢复动作，并在修复成功后沉淀诊断知识。

触发条件包括：

- 任一工具回执 `receipt.OK=false`；
- 独立校验 `verify.Status=Fail`；
- 模型调用报错或返回空内容；
- 模型中心调用超时或响应过慢。

异常模型由模型中心提供，设计材料中称为问题定位模型，用户拟命名为 JEV/GAB。具体名称及接口仍需确认。

### 10.2 三环处理流程

1. **异常知识库命中检查**  
   根据错误前缀、工具和意图构造错误指纹。命中已有根因和修复方法时，直接复用建议，避免重复调用模型。

2. **问题定位模型诊断**  
   未命中知识库时，将任务原文、意图及失败轨迹（工具、参数、错误等）发送给异常模型。模型以 JSON 输出分类、根因、置信度、可恢复性、建议和动作。

3. **自愈执行器处理**  
   根据诊断结果执行受限恢复策略，并将结果回写轨迹和异常知识库。

### 10.3 自愈动作与限制

| 动作 | 处理方式 |
|---|---|
| `retry` | 按建议重试 |
| `modify` | 修正参数、切换工具或模型后重试 |
| `fallback` | 安全降级，例如 `QUERY` 使用降级文案 |
| `ask` | 将问题交还用户 |
| `stop` | 终止操作并归因 |

设计规定：

- 单轮自愈重试最多 2 轮，防止死循环；
- 失败且仍可诊断时，可返回诊断环节，但诊断次数最多 2 轮；
- 不可恢复或不安全时应停止，而不是无限尝试；
- 成功修复后，将异常、根因和有效修复方法写入 `exceptions.jsonl`；
- 归因应携带诊断结论，替代笼统的“检查环境/路径/权限后重试”。

### 10.4 超时和模型错误处理

模型调用异常不能统一降级为固定文案。诊断应区分预算、网络、参数、排队、模型无响应或模型卡死等可能原因，并据此决定重试、换模型、降级、询问用户或停止。

异常自愈设计当前标记为 v0.1。具体错误指纹规则、异常模型契约、输出 Schema、超时阈值及预算限制仍需进一步定稿。

## 11. 轨迹、归因与经验沉淀

### 11.1 轨迹留存

轨迹采用 JSONL 追加写入，记录输入、意图、执行和校验等事件。追加式记录便于审计和追溯，避免覆盖历史过程。

### 11.2 归因

归因至少应反映：

- 任务和意图；
- 执行结果；
- 独立校验结果；
- 失败原因或诊断结论；
- 用户确认或决策理由（如适用）。

详细归因 Schema 未在可见材料中完整提供，须以权威定义为准。

### 11.3 学习回写边界

- `discuss` 阶段可记录归因和决策理由；
- 自动沉淀不能绕过人工确认修改策略或词典；
- 异常知识可以在满足设计要求时写入 `exceptions.jsonl`；
- 认知层重建和索引应采用独立低频任务，避免阻塞主执行链。

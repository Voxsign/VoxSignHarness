# VoiceSign Harness 全景开发文档

## 1. 文档定位

本文汇总 VoiceSign Harness 的可执行规格、语音驱动开发详细设计及异常自愈架构，描述系统目标、主执行链、接口边界、数据沉淀和异常处理方式。

- **系统名称**：VoiceSign Harness（源设计文档中亦称 VoxSign Harness）
- **目标场景**：以代码开发为核心的语音驱动开发（Voice-Driven Development，VDD）
- **规格版本**：SPEC v2.0，日期 2026-10-02
- **设计定位**：M2 生产底座闭环的施工依据；SPEC v2 定义行为语义，不改变已冻结的接口签名
- **北极星指标**：认知闭环周期，即从 `record → discuss → control → 归因` 完成一轮的速度

## 2. 产品目标与基本原则

### 2.1 产品目标

用户通过语音描述变更意图，Harness 负责容错、识别意图、规划与风险分级、受控执行、独立校验、回执及经验沉淀。模型负责生成或协助执行任务；Harness 不自行生成代码，重点承担执行门禁和独立验证。

开发过程由传统的“手写—运行—人工检查”转为：

> 意图描述 → 模型生成或工具执行 → 契约约束 → 独立验证 → 可审计回执 → 自动沉淀

### 2.2 核心原则

- **可审计**：保留原始输入、处理轨迹、执行结果、校验结论及归因。
- **独立验证**：校验器读取实际状态，不以执行者自报结果作为验证依据。
- **策略可失效**：策略、空间注册表或工具契约变更时，旧缓存不得继续生效。
- **认知层与主循环解耦**：项目认知信息采用低频异步更新，主循环按相关性检索并注入。
- **契约版本化**：共享契约独立维护，只增不改；M2 新增字段要求使用 `omitempty`。
- **零第三方依赖**：机器可读的 manifest、contract、policy 使用 JSON 文件，不使用 YAML。

## 3. 系统架构

### 3.1 分层结构

1. **输入容错层**
   - 留存 ASR 原文。
   - 清洗语音文本，并使用词典进行纠错。
   - 将自然语言整理为意图 JSON。

2. **认知层**
   - 保存 `project-map`、`decisions-log`、用户偏好等项目知识。
   - 按每日或每 N 次任务批量 reindex，不在主执行循环中实时更新。
   - 在任务执行前检索与当前路径或模块相关的知识切片。

3. **接口层**
   - 通过版本化工具契约约束 Git、文件、搜索、测试、运行、校验和问答等能力。
   - 校验器是独立于运行工具的契约化节点，并具有版本和审计信息。

4. **执行层**
   - 根据意图形成执行计划。
   - 执行风险分级、确认门禁、工具调用和独立校验。
   - Harness 提供 gate 和验证能力，不承担代码生成职责。

5. **沉淀层**
   - 以 append-only JSONL 记录任务轨迹。
   - 记录归因、决策理由、回写信息和执行回执。
   - 对异常诊断结论及已验证的修复方案进行积累。

### 3.2 组件职责

| 组件 | 主要职责 |
|---|---|
| 输入处理 | 保存原文、清洗文本、词典纠错、生成意图 |
| TaskClassifier | 输出任务分类；M2 管线使用该分类器的产出 |
| refer 消解 | 解析意图中的指代 |
| space 选择与检查 | 选择执行空间并执行 `space_check` |
| risk 分级器 | 根据任务影响及可逆性确定风险等级 |
| tools.Executor | 按工具能力及契约执行任务 |
| 独立校验器 | 检查执行后的实际状态 |
| trajectory / discuss-log | 记录轨迹、归因和讨论决策 |
| cache | 保存四元组缓存，并服从策略版本失效机制 |
| 异常诊断与自愈 | 对执行、校验或模型调用错误进行诊断和受限恢复 |

## 4. 意图类型与工具契约

### 4.1 意图分类

| 意图 | 示例 | 风险基线 | 契约能力 |
|---|---|---|---|
| `EDIT` | 把报价模块错误提示改成中文 | 可逆、影响中 | file、git、test、verify |
| `DEBUG` | 修复程序崩溃 | 可逆、影响高 | git、test、run、verify |
| `QUERY` | 查找某个函数的定义位置 | 只读 | search、file、git |
| `TEST` | 运行测试 | 只读 | test |
| `COMMIT` | 提交当前改动 | 不可逆 | git |
| `DEPLOY` | 发布到服务器 | 不可逆 | run、git、verify |
| `NOTE` | 记录一个想法 | 只读 | file |
| `ASK` | 询问某个库的使用方式 | 只读 | ask |

风险基线用于任务分类和后续风险评估，具体确认规则应遵循冻结契约及风险策略，不应仅凭意图名称跳过门禁。

### 4.2 工具清单与契约约束

设计中列出的工具能力包括：

- `git`
- `file`
- `search`
- `test`
- `run`
- `verify`
- `ask`

接口层描述称“六工具”，但实际列出的能力为七项；实施时应以冻结契约中的实际工具定义为准，并在契约文档中消除该数量表述的不一致。

### 4.3 契约与格式要求

- 共享契约以独立 contract 文件为准。
- 契约只增不改，并进行版本管理。
- M2 新增字段均使用 `omitempty`，保持与 M1 数据结构兼容。
- M1 类别（如 `TIME`、`FILE_*`）与 M2 类别（如 `EDIT`）并存。
- manifest、contract 和 policy 的机器形态使用 JSON，例如 `.space.json`、`.contract.json`。
- 不通过引入 YAML 解析器增加第三方依赖。

## 5. 主执行流程

### 5.1 pipeline.Run 十三步

主链必须按以下顺序执行：

1. 接收并保存 `input_raw`。
2. 清洗输入。
3. 进行词典纠错。
4. 调用 `TaskClassifier` 识别意图类型。
5. 进行 refer 指代消解。
6. 选择 space 并执行 `space_check`。
7. 进行风险分级。
8. 按风险策略进行确认。
9. 调用工具执行任务。
10. 调用独立校验器验证结果。
11. 生成归因并写入轨迹。
12. 更新四元组缓存。
13. 输出四行回执。

**门禁要求**：禁止在 `space_check` 和风险分级之前执行工具。

### 5.2 输入与执行职责

- ASR 原文必须保留，便于追溯语音识别和纠错结果。
- 词典纠错后的内容用于意图识别和后续处理，但不得覆盖原始输入。
- EDIT、DEBUG 等任务的代码生成可由模型工具循环或外部编码代理完成。
- Harness 负责空间与风险 gate、工具契约执行及独立校验，不自行生成代码。

### 5.3 回执与归因

- 每次任务应输出四行回执。
- 执行、校验和失败信息应可检索、可追溯；对适用的操作应支持撤销。
- 归因应携带执行与校验结果；异常路径下应尽可能使用诊断结论替代泛化静态建议。
- SPEC 要求 discuss 阶段输出一条 `kind=attribution` 轨迹记录和一条 `discuss-log`。

## 6. 认知闭环与数据沉淀

### 6.1 三通道轨迹

三通道均采用 append-only 的轨迹 JSONL 记录：

| 通道 | 记录内容 |
|---|---|
| `record` | 原始输入、纠错信息、意图 |
| `discuss` | 归因、决策理由及回写信息 |
| `control` | 执行、校验与回执 |

轨迹用于审计和后续认知积累，不应因后续状态变化而覆盖原始记录。

### 6.2 discuss 阶段约束

- discuss 输出包括 `kind=attribution` 轨迹和 `discuss-log`。
- discuss 可以形成归因和决策理由。
- **禁止** discuss 自动修改策略或词典；相关变更必须经人工确认。

### 6.3 认知信息更新

- `project-map`、`decisions-log`、偏好等信息属于变化较慢的认知数据。
- 采用每日或每 N 次任务的独立批量更新机制。
- 主循环只检索与当前任务相关的内容，不实时全量重建认知数据。

## 7. 策略版本与缓存失效

### 7.1 Policy 失效机制

策略文件采用版本化 JSON，例如：

```json
{
  "policy": {
    "policy_version": 2,
    "spec": "SPEC-v2-可执行规格书.md",
    "spec_version": "v2.0",
    "invalidates": {
      "on_policy_change": true,
      "on_space_registry_bump": true,
      "on_contract_bump": true
    }
  }
}
```

### 7.2 失效规则

发生以下任一变化时，旧四元组缓存不得继续使用：

- policy 版本变化；
- space 注册表版本变化；
- 工具契约版本变化。

变更时应调用 `cache.BumpPolicyVersion()`，并同步推进相应注册表或契约版本。四元组缓存的具体字段定义应以冻结接口为准。

## 8. 异常自愈架构

### 8.1 设计目标与触发条件

异常自愈用于替代只给出静态通用建议的失败处理方式。触发场景包括：

- 任一工具执行回执 `OK=false`；
- `verify.Status=Fail`；
- 模型调用报错或返回空内容；
- 模型中心调用超时、响应过慢或无快速响应。

异常诊断不取代主执行链，而是在相关失败点接入诊断和恢复流程。

### 8.2 三环自愈流程

1. **异常知识库命中检查**
   - 根据错误前缀、工具和意图形成错误指纹。
   - 若命中已有根因和修复建议，直接复用，避免重复模型调用。

2. **问题定位模型诊断**
   - 未命中时调用模型中心的问题定位模型。
   - 输入包括任务原文、意图及失败轨迹，例如工具、参数和错误信息。
   - 输出 JSON 应包含分类、根因、置信度、可恢复性、建议及动作。

3. **自愈执行器处理**
   - `retry`：按建议重试。
   - `modify`：修正参数，或切换工具、模型后重试。
   - `fallback`：安全降级，例如 QUERY 使用降级文案。
   - `ask`：转回询问用户。
   - `stop`：停止并归因。

### 8.3 重试与诊断上限

- 单次恢复流程最多重试 2 轮，以避免无限循环。
- 失败且仍可诊断时，可以再次进入问题定位模型流程，但整个诊断循环最多 2 轮。
- 超时或模型响应慢时，应将模型名称及相关上下文传入诊断层，以便区分网络延迟、预算排队、模型卡住或参数不当。

### 8.4 学习回写

- 异常诊断后，若获得根因及成功修复方案，应写入 `exceptions.jsonl`。
- 后续遇到同类错误时，先通过错误指纹查询知识库。
- 归因记录应包含诊断结论，减少重复出现通用的“检查环境、路径、权限后重试”建议。

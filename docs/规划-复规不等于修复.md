# 规划：复规 ≠ 修复（`Replan` 的语义边界）

> 记录 `VHS-PLAN-001` RV-1 的一条**区分**，避免后来者误读 `Plan.Changes`。

## 结论

`Replan` 只做一件事：**在一步失败后产出一个新的、可继续/可审计的计划**。
它**不修复**失败原因，也不保证新计划能成功。

具体地，当前规则式实现：

1. **移除失败步**（不再盲重试同一步 —— RV-1）；
2. **插入一个只读诊断步**（优先 `git.status`，其次 `search.text`），用于收集失败上下文；
3. 在 `Plan.Changes` 里写明"原第 N 步不可行，改为 …"（RV-2）。

因此 `Changes` 非空 **只表示计划变了**，**不表示问题解决了**。

## 为什么不做"自动修复"

- 修复需要**领域知识**（为什么失败、如何回退），当前属于未知；
- 自动"修复"容易变成**盲目重试的变体**，正是 RV-1 要禁止的；
- 域门禁拒绝时（RV-3）**根本不允许修复**：计划作废，交人裁决。

## 什么时候算"真的修好"

按 `ASR-MODEL-02` §3 的"学到"定义同源：**要看下一次同类执行是否成功**，
而不是看计划文字是否变漂亮。步骤重排本身不构成修复证据。

## 2. 提议的模型：一个真相源 + 写者隔离 + 机械门禁

### 2.1 唯一真相源

**GitHub `smithpeter/voicesign-harness` 的 `main` 是唯一真相源。**
本地目录降级为"临时工作副本"，不再是真相。

判据（可机械检查）：**任何人 `git clone` 后，`go vet ./... && go test ./... && gofmt -l .` 必须全过。**
——这条就是 D1/D2 的防回归，我建议做成 CI 的第一个 job。

### 2.2 一个任务 = 一个分支 = 一个 worktree（写者隔离）

```
main ──┬── task/A-codex-orchestrate     ← worktree /tmp/vhs-codex
      └── task/B-dsh-longtask-harness   ← worktree /tmp/vhs-dsh
```

**禁止两个写者共用一份工作区。** 现在正是反例：Codex 与我在同一目录，
他跑一次 `git add -A` 就会把我的文件卷进他的提交，反之亦然。

配套规则：
- **写域声明**：每个任务在 PR 描述里写明"我只会改这些路径"（如 `e2e/`、`server/`）；
  写域重叠即**串行**，不重叠可并行。
- **不共享可变资源**：`~/.voicesign`、`data/asr_logs`、日志目录都不许共用（文档本身也要求测试只用 `t.TempDir()`）。

### 2.3 合并模型

```
feature 分支 → PR → 机械门禁(CI) → 人批准(builder ≠ approver) → squash merge 到 main
```

**为什么必须走 PR 而不能直接 push main**——这不是洁癖，是文档已经写死的红线：

- `CICD-BOUNDARY-001:107`「**禁止本次变更自行降低门槛**」（须用变更前策略判定）；
- `:326`「**不能信任作者填入的 `approved_by: Peter`**」；
- `opc-104`：**builder ≠ approver**，最终合并权唯一属人。

### 2.4 冲突与串行合并规则（回答"别测完了没法合"）

| 情形 | 规则 |
|---|---|
| 两个 PR 改**同一文件** | 先合者赢；后合者必须 **rebase 到新 main 并重跑门禁**，不得强推覆盖 |
| 两个 PR 改**不同文件** | 可并行；仍按顺序合并，先合者触发后者 rebase |
| 冲突落在**测试文件** | **以更严格的一方为准**（断言多者胜）；两者都保留，重名加写者后缀 |
| 冲突落在**判分器/金标准集** | **由人裁决**，且必须升版 + 保留旧哈希（`fr-25` 反博弈） |
| 分支过期 | 合并前必须 rebase；**禁止 merge commit 污染历史** |

**关键点**：测试结果**不是**合并的障碍物。见 §3。

## 3. 测试结果放哪（这是"测完了没法弄"的真正答案）

**结论：测试的原始产物不进代码库，进"证据归档"；代码库只留可复算的摘要与哈希。**

| 资产 | 放哪 | 理由 |
|---|---|---|
| 测试代码 | 仓库（分支 → PR → main） | 是资产，要评审、要版本化 |
| **红测试（已知缺口）** | 仓库，**用 build tag 隔离**（`asrsimgap`，已落地） | 主干必须绿；缺口显式可跑 |
| 运行产物（冻结轨迹、日志、回执） | **CI artifacts / 对象存储**；仓库只留 `sha256` + 摘要 | 体积与隐私；`CICD-BOUNDARY-001:369` 要求原始客户材料/凭据不入 Git |
| 预注册文件（PREREG） | 仓库（**append-only，冻结后只读**） | 防篡改锚点 |
| 结算摘要（三态 + 六层读数 + 归因） | 仓库 `eval/results/<run_id>.json`（小文件） | 可被无上下文者复用（`auto-002` P4 Artifact-first） |
| 金标准集 | 仓库，**只读 + 哈希冻结** | 评测集只读防 Goodhart |

**版本锚点（回答"测的是哪一版"）**：每次运行绑定**四元组**——
`commit_sha` + `rubric_hash` + `prereg_hash` + `模型/路由版本`（吸收 `VS:201`）。
**没有四元组的测试结果，不得作为任何结论的依据。**

## 3.5 版本 tag 规范（回答"版本之后在哪里"）

**每一个可被测试的版本，必须有唯一、可复现的标识。** 分三层：

### 3.5.1 代码版本（Git）
- `main` 上每个合并点就是一个版本；**tag 格式**：`v0.<minor>.<patch>`（V0 阶段恒为 `v0.*`，不装 1.0）。
- tag **只打在 main 的合并提交上**，不在分支上打。
- tag 内容 = 该合并提交的 sha。**tag 与实际测试对象必须同源**：测的分支和合的提交不是同一个，验证即失效（`CICD-BOUNDARY-001`「审核 A 版本发布 B 版本 = 验证失效」）。

### 3.5.2 评测版本（四元组）
一次运行必须绑定：
```
commit_sha   ← git rev-parse HEAD（= tag 指向的 sha）
rubric_hash  ← eval/tasks/<id>/rubric-*.md 的 sha256
prereg_hash  ← eval/tasks/<id>/PREREG.md 的 sha256
model_version← "rule-only(none-llm)" 或具体模型 id
```
**缺任一 → 结论降级为"证据不足"，不得作为任何依据**（已由 `eval/runner` 的 `FourTuple.Complete()` 强制，并有单测覆盖）。

### 3.5.3 变更版本（rubric / PREREG / cases）
- 这三个是**只读资产**：改动 = 升版（`rubric-v0 → rubric-v1`），**保留旧文件与旧哈希**。
- 历史判定**不回溯修改**——旧分数按旧标准解释，并注明标准版本（`fr-25` 反博弈要求）。
- `eval/cases.jsonl` 是**人签署**的真值库：agent 只能提议，`ratified_by` 为空即"提案"，不得据此宣称能力通过。

### 3.5.4 谁打 tag
按 `builder ≠ approver`：**实现者不打 tag**。由批准合并的人（人）在合并后打；自动化只负责把四元组写进结算文件。

## 4. CI/CD 放哪（你说"没有决定到底 CI/CD 怎么放"）

### 4.1 建议：两阶段，先 GitHub Actions，不建新域名

- `CICD-DOMAIN-001:4` 的结论是「**现在不新增 CI/CD 子域或全新域名，仍然成立**」。
- 所以阶段 1 **不要**去碰 AIOps 网关 / `model.peterzou.com`，那属于治理域变更，要走 Peter/AIOps 授权。

### 4.2 阶段 1：仓库内三个 job

```
job 1: gate          （阻断）  go vet + go test ./... + gofmt -l + ./build.sh 的等价检查
job 2: reproducible  （阻断）  全新 clone → go build ./... && go test ./...   ← D1/D2 的防回归
job 3: gap-board     （非阻断）go test -tags asrsimgap ./e2e ./server → 结果贴 PR 评论
```

- **job 1/2 失败 = 不许合并**。
- **job 3 允许红**——它是 M8 进度看板，不是门禁。但**必须每次都贴出来**，
  否则缺口会重新变成"没人知道"（`fr-08` 的教训：审查层失效，任务却全被标 done）。

### 4.3 阶段 2（以后再说）

需要真实部署时，再按 `CICD-BOUNDARY-001` 的分级规则加：
S0/S1/S2 阶段 + C0–C3 风险分类 + `failed/cancelled/timeout/unknown 均不视为通过` + 审批绑定对象摘要。
**在阶段 1 之前不要碰部署链。**

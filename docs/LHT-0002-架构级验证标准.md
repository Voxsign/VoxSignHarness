## 0. 为什么需要"更高架构标准"的桩

LHT-0001 与本会话已修的 G1–G9 全部落在**输入层**（分类器判得对不对）。
但项目的 12 条设计决策里，有若干条是**架构承诺**，它们无法由"某句话判对了"来证明：

| 决策 | 原文 | 能否用行为测试证明 |
|---|---|---|
| #7 自举充分条件 | 「契约注册机制可被语音调用……此链路通之前 **2.0 不存在**」 | ❌ 需要端到端跨模块 |
| #6 独立校验器 | 「读文件系统实际状态**不读执行器自报**；**回执≠验证**」 | ❌ 需要注入故障 |
| #3 域交集 | 「有效权限=交集，**默认拒绝**」 | ❌ 需要未授权路径 |
| #11 组织者机制 | 「确定性编排引擎接管，回执可预测/可白名单/**可幂等**」 | ❌ 需要重放 |
| #10 异常自愈 | 「不是简单降级/静态建议，而是定位模型判断+自愈动作+**学习回写**」 | ❌ 需要真实失败注入 |

本桩把这些**已承诺的架构性质**变成可执行判据。**红色 = 承诺未兑现**，不是"功能没做"。

## 2. A1 详述（✅ 已转绿，保留为本轮首灯与复验记录）

**决策 #7 原文**：
> 「自举充分条件不是'有独立校验器'，是'契约注册机制可被语音调用'：
> 说'加一个工具把 md 转 pdf'→REGISTER_TOOL→模型生成契约→风险分级→人确认→注册→下次可用。
> **此链路通之前 2.0 不存在。**」

**本轮起点实测（红灯）**：

```
"加一个工具把 md 转 pdf"            → REGISTER_TOOL ✅
"给我加个工具，能把 markdown 转成 pdf" → REGISTER_TOOL ✅
"注册一个命令，用来压缩图片"          → UNKNOWN      ❌
```

**为什么这是架构问题而不是措辞问题**：用户说"注册一个**命令**"，而分类器只认"工具/注册工具"这类词。
但北极星原话是「我要的就这么简单个东西」——**用户不会迁就系统的词表**。
自举入口对措辞敏感，等于自举链条在真实口语下断链。

**验收标准（可机械判定）**：
1. 上述三句全部判 `REGISTER_TOOL`；
2. 不得因新增触发词而把正常 `EDIT`/`QUERY` 误判为 `REGISTER_TOOL`（需回归保护）；
3. 既有 20 条样例仍 20/20。

**转绿记录**：实现方 `63f6375`（`fix(input,pipeline): A1 自举入口断链 + llmIntentFallback 结构性豁免`）
修复，并附 `input/registertool_regression_test.go`、`pipeline/intentfallback_regression_test.go` 回归保护。
本桩复跑 `TestArchA1RegisterToolByVoice` → **PASS**（异源判分，非自述）。

## 3. A4 详述（✅ 已落地：真实 git 夹具，双向反例）

**M8 自报缺口 #3**：「LLM 输出非确定性：重跑同任务可能因措辞微变产生新 commit；**严格幂等仅逐字节相同时触发**」。

### 3.1 判据（可机械判定）

```
同一长任务经完整 pipeline.Run 跑两次：
  观测 = git rev-list --count HEAD（外部事实，不读回执自报）
  ① 不该收却收了：第二次运行后 count 必须不变，且第二次最后回执 OK=true、Ask 为空；
  ② 该收未收：源文档内容变更后再跑，count 必须恰好 +1（防"永不提交"假绿）。
```

### 3.2 夹具形态（本节新增，替代原"建议夹具"）

原 SKIP 理由是"需要真实 git 仓库 **+ 模型 provider**"。实测**不需要 provider**：
`execOrchestrate` 在 `llmSummarize` 失败（providers=nil）时回退 `deterministicSummary`，
仍产出真实文件与真实提交 —— 所以本判据可**完全离线确定性**执行。

夹具见 `e2e/arch_test.go`：

| 构件 | 形态 | 作用 |
|---|---|---|
| 项目仓 | `t.TempDir()` → `git init -q` + 身份/关签名 + 基线提交（1 个） | 提供真实 `rev-list` 观测面 |
| 源文档 | `<repo>/docs/{SPEC-v2-可执行规格书.md,M7配置指南.md}` | 命中 `defaultOrchestrateSources` |
| 域 | 显式注册 `project` 域，scope 指向夹具仓 | **防止 `ensureProjectSpace` 回退到进程 cwd 把本仓库当项目根** |
| 入口 | `pipeline.Run`（分类器→确认闸→编排），非内部 `execOrchestrate` | 覆盖真实链路，不只覆盖内部函数 |
| 确认 | `ConfirmFn` 返回 true 并计数 | 断言人工确认闸确实触发 |
| 观测 | `git rev-list --count HEAD` | 外部事实，不看编排回执自述 |

### 3.3 判据灵敏度证明（mutation，先证明桩会红）

在**一次性 worktree**（`/tmp/vhs-mutate`，用后删除，未污染提交）里对实现做定向变异：

| 变异 | 期望方向 | 实测 |
|---|---|---|
| `commitTargetPath` 恒走"内容无变化"分支 | 该收未收 | 🔴 `首次编排应恰好新增 1 个提交（基线 1 → 2），实得 1` |
| `commitTargetPath` 恒不跳过（空 diff 也 commit） | 不该收却收了 | 🔴 `第二次最后回执 OK=false err="git commit: exit status 1"`、`result="FAILED：…"` |

### 3.4 仍未验证（不得当通过）

**A4-LLM**：M8 缺口 #3 的**措辞微变**路径需要有真实 provider 才能构造，离线不可判定 →
单列 ⚪ UNVERIFIED。本桩只证明**确定性编排路径**的幂等。

## 4. A6 详述（✅ 已落地：真实失败注入 + 闭环回写）

**M8 自报缺口 #7**：「jev-diagnose 当前为**模拟桩**（模型中心侧），真实 JEV 模型未上线」。

### 4.1 判据（v1.1，修正留痕）

原 v1 判据：「一次真实失败必须产生 ①带 cause 类的诊断 ②自愈动作 ③**学习回写**」。

**修正理由（判据错了，不是系统错了）**：v1 隐含"每次失败都要落盘知识"。
但把**未验证的根因**固化进知识库，正是反博弈要禁止的（等同"让被测方自填 approved_by"）。
系统当前的设计是「**仅修复验证成功才回写**」——这是**更安全**的行为，却被 v1 读成缺口。
故升为 v1.1：

```
① 真实失败必须产生诊断：category ∈ 接口标准 v1 §3 八类枚举，action ∈ 五词白名单；
② 自愈动作（只读族）重放成功 → 必须学习回写，且可按同一指纹检索；
③ 同类失败再次发生 → 命中回写、0 次模型调用；
④ 反向：不可逆工具失败不得自动重放、不得回写；模型输出不可解析不得折算成诊断。
```

这是**收紧负方向**（禁止未验证回写），不是放宽。

### 4.2 夹具形态

失败用 **真实 `tools.Executor`** 注入（非手写字符串）：

| 角色 | 构件 | 形态 |
|---|---|---|
| 真实失败① | `file read` 不存在路径 | 执行器真实返回 `OK=false`，`Stderr="open …: no such file or directory"` |
| 真实失败② | `git -C <不存在仓库> commit` | 不可逆工具的真实失败（反向反例） |
| 问题定位模型 | `archDiagStub`（实现 `provider.Provider`） | 确定性 JSON 诊断，不触网，计数模型调用 |
| 自愈执行器 | `selfheal.ToolRunner` 闭包 | 返回 OK 并计数，代表"重放成功" |
| 知识库 | 真实文件 `exceptions.jsonl` | 回写落盘可复验 |

### 4.3 判据灵敏度证明（mutation）

| 变异 | 期望方向 | 实测 |
|---|---|---|
| 删掉 `s.KB.Remember(*d)` | 回写缺失 | 🔴 `学习回写缺失…实得 0`、`第二次诊断 source="model"（期望 kb）`、`重复调用模型（1 → 2）` |
| 去掉 `IsReadOnlyTool` 守卫（允许不可逆重放） | 安全红线 | 🔴 `不可逆工具（git）失败被自动重放`、`未验证的重放不得回写知识（1 → 2）` |

### 4.4 仍未验证（不得当通过）

**A6-JEV**：真实 JEV 模型的**诊断质量**（根因是否判对）离线不可判定 → 单列 ⚪ UNVERIFIED。
本桩只证明 harness 闭环：失败 → 诊断 → 动作 → 回写 → 复用。

## 5. X1：一条从三次真实事故里长出来的结构性守卫

本会话修 G1–G9 时，**同一类缺口踩了三次**：

| 事故 | 新分支 | 被谁绕过 |
|---|---|---|
| G1-P4 | 否定仲裁（negation） | `llmIntentFallback` 清空 Ask |
| G3-P3 | 元指令仲裁（meta） | 同上 |
| G5-P0-1 | 多动作仲裁（multi_action） | 同上 |

三次都是「**新增一条靠 Ask 拦住的分支，却忘了登记下游会清空 Ask 的路径**」。
所以 X1 不再逐个登记，而是立一条结构性不变式：

> **任何 `Conflict` 非空的意图，其 `Ask` 必须非空。**

这样新增仲裁时自动受保护。**建议实现方同样改写 `llmIntentFallback` 的豁免逻辑——
从"白名单 switch"改为"Conflict 非空即豁免"**，否则还会有第四个实例。

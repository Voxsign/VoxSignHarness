## 2. 项目定位与核心目标
VoiceSign 个性化 ASR 后台是一套用 Go 编写的独立后台服务，接收手机端传来的语音转写文本及原始音频，完成“纠错 → 理解 → 个性化增强 → 输出标准化意图”，并在使用过程中持续学习用户口语、专名、习惯与偏好，越用越懂用户。

与 VoiceSign Harness 的关系：
- 本模块是纯粹独立后台，不并入 Harness 二进制，也不与其耦合。
- ASR 后台 = 语音输入理解层，负责把用户说的变成机器能执行的意图。
- Harness = 任务执行层，负责把意图变成真实结果。
- 两层职责不同、迭代节奏不同，必须解耦。
- ASR 后台通过标准接口对外输出意图 JSON，Harness 只是消费方之一。
- 未来任何语音入口均可复用同一个 ASR 后台。
- 两套代码独立仓库、独立部署、独立数据目录；仅共享一套“意图 JSON 契约”。
- 契约版本化、只增不改。

北极星目标：
- 越来越懂你：系统在使用中持续沉淀口语说法、专有名词、指代习惯、项目背景与偏好，个性化能力逐日增强，不依赖一次性配置。
- 语音能力很强：纠错、标点、意图理解、控制语义、语音文字双通道可用可靠，体验对标豆包语音体系。
- 响应极快：本地规则优先，模型兜底，处理链路微秒到毫秒级，语音说完即出结果。
- 面向未来全双工：架构从第一天就为全双工实时语音交互预留接口与数据模型，支持边说边理解、随时打断、实时反馈。

## 3. 核心设计思想：个性化三层递进
“越来越懂你”由三层能力逐层递进，每层都沉淀数据，数据反过来增强下一层。

| 层级 | 要解决的问题 | 沉淀的个性化数据 |
|---|---|---|
| L1 听清：文本纠错层 | 语音转写错字、同音字、口语碎片、专名错误。例：“季总”实际是“冀总”；“那个 module”实际是某个项目名。 | 自定义词典、纠错经验库、语音置信度标记。 |
| L2 听懂：语义理解层 | 一句话意图是什么？“它”指什么？“那个文档”是哪个？需结合上下文与历史理解。 | 指代消解缓存、对话上下文记忆、意图置信度。 |
| L3 懂你：个人画像层 | 同一个词在不同人嘴里含义不同，同一件事在不同人场景下期望不同。需结合偏好、项目知识、决策历史做个性化理解。 | 用户偏好 prefs、项目地图 project-map、决策日志 decisions-log、领域知识、使用模式统计。 |

核心公式：个性化 = 数据 × 规则 × 反馈闭环。
- 数据：每一次语音输入、用户确认、纠错都留痕，append-only，形成私有复利资产。
- 规则：本地规则优先，包括词典、缓存、模式，零模型调用，保证速度与确定性。
- 反馈闭环：用户改一个字、确认一个指代、纠正一次识别，系统立即学习并固化，下次直接使用，越用越准。

## 4. 系统架构与处理管线
总体链路：
手机端 App → 系统级/第三方 ASR 引擎（豆包/系统语音转文字）→ 转写文本 input_raw → VoiceSign 个性化 ASR 后台 → 意图 JSON（HTTP/WS）→ VoiceSign Harness 或其他消费方。

后台处理管线固定为 8 步：
1. 留底：保存 input_raw。
2. 清洗：去除语气词、重复词、口误碎片。
3. 词典：执行个性化纠错。
4. 上下文：做相关性检索与注入。
5. 指代：执行指代消解。
6. 意图：解析意图。
7. 域建议 + 控制语义：输出域建议，识别打断/暂停/撤销。
8. 输出标准化意图 JSON。

个性化数据层包括：
- custom-dictionary
- context-memory
- user-profile
- project-knowledge
- exceptions-knowledge

分层设计原则：
- 单向依赖：管线 1→8 顺序固定，每层只依赖前一层输出，不反向调用。
- 本地规则优先，模型兜底：只有本地规则无法解决时才调用模型中心。
- 模型调用带超时，超时即降级，绝不阻塞。
- 个性化数据与代码分离：全部个性化知识存 JSON/JSONL 文件，代码只提供处理逻辑，两者独立演进。
- 输出契约稳定：对外只输出标准意图 JSON，任何消费方按契约接入。

## 6. L1 个性化词典 P0
条目结构：`{raw_speech: 口语/错词, target: 标准写法, scope: 全局|项目, priority: 优先级, source: 来源}`。

典型场景：
- 人名纠错：如“季总 → 冀总”。
- 项目名、专有名词。
- 口头禅映射。
- 方言口音修正。

能力要求：
- 支持语音指令动态增删改：用户说“记住，冀总是冀中的冀”“删掉这个词”，后台解析为词典操作并落盘。
- 匹配策略：全词优先、最长匹配优先；同词多条命中取最高优先级；命中后标记纠错来源与置信度。
- 纠错安全：高置信纠错直接替换；低置信纠错输出“疑似纠错”标记，交上层回问，绝不静默改错。
- 词典可导出/导入，版本可回溯，采用 append-only + 快照。

## 7. 文本清洗与纠错 P0
- 去除 ASR 常见语气词、重复词、口误碎片，如“嗯”“那个”“就是就是”，同时保留语义。
- 标点恢复：为转写文本补全标点，提升下游意图解析准确率。该事项为 M7 真机遗留项，必须闭环。
- 识别置信度标记：对 ASR 引擎返回的低置信片段打标，进入纠错或回问流程，不直接执行。
- 清洗全过程保留原始输入，输出带清洗说明，包括改了哪里、为什么。

## 8. L2 指代消解 P1
层级机制：
- 第一层：词典/实体库。处理“它=最近提到的实体”“这个项目=当前域项目”，使用本地实体索引，零模型调用，100% 确定才替换。
- 第二层：上下文规则。读取最近 N 轮对话上下文，四元组缓存为 `{意图, 域, 权限, 指代}`，按规则匹配指代对象。
- 第三层：模型兜底。仅前两层无法解决时调用模型推断，输出带置信度。

确认与缓存：
- 低置信度指代输出 `need_disambiguate` 标记，触发回问确认。
- 回问遵循“一屏一决策，只问一次”。
- 用户确认后自动固化进缓存，下次直接复用。
- 缓存带过期策略，如 7 天，并设容量上限。
- “打断/暂停/撤销”三个控制语义必须识别，并优先于普通指代处理。

## 9. L3 上下文个性化记忆 P1
数据源：
- user-preferences.json：偏好。
- project-map.json：项目地图。
- decisions-log.jsonl：历史决策。
- 领域知识库。

用法：
- 根据当前输入做相关性检索，只把相关片段注入解析过程，绝不全量加载历史。
- 检索结果只做理解增强，不直接改写原始输入。
- 输出 JSON 中携带命中的上下文来源。
- 异步低频更新：偏好/项目知识变更后增量更新索引，不阻塞实时请求。
- 使用模式统计：高频说法、常见意图、活跃时段、确认率，反哺词典权重与确认策略。

## 10. 意图解析与标准化输出 P0
输出标准化意图 JSON：
`{type, path, params, confidence, need_disambiguate?, domain_suggestion?, control?}`。

意图类型对齐 Harness 现有 8 类 + ORCHESTRATE：
EDIT / DEBUG / QUERY / TEST / COMMIT / DEPLOY / NOTE / ASK / ORCHESTRATE，兼容现有消费方。

控制语义：
- 独立输出。
- 识别到“停/暂停/撤销”等，直接返回控制意图，不进入业务执行。

分类策略：
- 规则优先分类，使用关键词、词典、模式。
- 模型兜底。
- 置信度低于阈值时，回问或转 ASK。

## 11. 域（Space）建议 P1
- 根据意图与资源路径输出候选域建议，如 project / sandbox / vault-notes / global。
- 交由上层权限门禁裁决。
- 原则：默认拒绝；未知意图落到 global 只读域，绝不猜测高权限域。
- ASR 后台只建议、不授权。
- 权限校验永远在消费方执行，即 Harness 的 Space.Check。
- 本服务不绕过权限校验。

## 15. 处理管线实现步骤
1. 留底：保存 input_raw，append-only，不可篡改。
2. 清洗：去除语气词、重复词、口误碎片，恢复标点，标记低置信片段。

8. 输出：标准化意图 JSON，通过 HTTP/WS 给消费方。

每一步均写入轨迹 JSONL，带耗时与命中来源，可完全复现。

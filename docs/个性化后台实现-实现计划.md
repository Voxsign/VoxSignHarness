# 个性化后台实现-实现计划

> 文档性质：ASR 个性化后台服务（独立 Go 服务）的全景开发文档与实现计划
> 需求基线：需求规格 v3
> 整理来源：VHS 测试线 / VoxSign Harness 长程实现任务输入文档

本服务的目标是让 ASR 识别结果具备**个性化纠错与学习闭环**能力：用户教过的词（词典）、标错的词（黑名单）、确认过的映射（反馈）被服务持久化记忆，并在后续每一次纠错中生效，形成"越来越懂你"的效果。

## 一、目标与范围

构建一个**独立运行的 Go 后台服务**，对 ASR 识别出的中文文本做个性化后处理，包含三条主线：

1. **词典学习**：用户主动新增词条（标准词 + 变体），服务写入词典并持久化。
2. **纠错应用**：对输入文本应用词典映射（如 `曼苏 → Mansour`），同时受黑名单约束，输出纠正后的文本与应用明细。
3. **反馈闭环**：记录用户对纠错结果的接受/拒绝（拒绝必须带原因），以 append-only 方式落盘，作为后续学习与回溯依据。

服务同时提供意图分类能力（`NOTE/QUERY/EDIT/…`），与纠错结果一并返回，使下游可直接消费结构化结果。

不在本期范围内：模型训练、在线学习算法、多用户账号体系、数据库依赖。

## 二、技术约束

| 约束项 | 要求 |
|---|---|
| 语言与依赖 | Go，**仅标准库，零第三方依赖** |
| 可独立运行 | 通过 flag 或环境变量配置监听地址（默认 `127.0.0.1`）与数据目录（默认 `./data`） |

| 代码质量 | 不留 TODO / 占位 / 伪代码，自包含，可直接 `go build` 通过 |

## 三、P0 能力清单

以下能力全部必须实现，并逐条验收。

| # | 端点 | 行为 | 数据文件 |
|---|---|---|---|
| 1 | `GET /v1/health` | 健康检查 → `{"ok":true}` | 无 |
| 2 | `GET /v1/dict` | 返回全量词典 JSON（`terms` 数组：`term` / `variants` / `category` / `source`） | `dictionary.json` |
| 3 | `POST /v1/term` | 增词（body：`term` / `variants` / `source`），写回词典并持久化 | `dictionary.json` |
| 4 | `POST /v1/correct` | 个性化纠错：输入 `{text}`，应用词典映射与黑名单拦截，返回 `{corrected, applied:[…]}` | 读 `dictionary.json` / `blacklist.json` |
| 5 | `POST /v1/process` | 意图分类 + 纠错：输入 `{text}`，返回 `{intent, corrected}`，`intent ∈ NOTE/QUERY/EDIT/…` | 读 `dictionary.json` / `blacklist.json` |
| 6 | `POST /v1/feedback` | 反馈学习：输入 `{raw, corrected, accepted, reason}`，**追加** `feedback.jsonl`（append-only；`accepted=false` 时必带 `reason`） | `feedback.jsonl` |
| 7 | `POST /v1/blacklist` | 黑名单：输入 `{term, note}`，写入 `blacklist.json`；"这个改错了"的纠错在后续被跳过 | `blacklist.json` |
| 8 | 鉴权（可选） | 环境变量配置 token 时，校验请求头 `Authorization: Bearer <token>`；未配置则关闭鉴权 | 无 |

## 四、接口契约细化

### 4.1 通用约定

- 所有端点均返回 JSON，响应体中文不乱码。
- 请求体为 JSON，字段名小写下划线/单词形式与上表一致。
- 建议统一错误响应结构（如 `{"error":"..."}`）与合适的状态码（400 参数错误、401 鉴权失败、405 方法不符、500 内部错误）。

### 4.2 健康检查

- `GET /v1/health` → `{"ok":true}`，不读写任何数据文件。

### 4.3 词典读写

- `GET /v1/dict`：读取 `dictionary.json`，返回 `{"terms":[{term, variants, category, source}, …]}`。
- `POST /v1/term`：接收 `{term, variants, source}`，追加或合并进词典后立即落盘；同一 `term` 重复提交时按合并变体处理，避免重复条目。

### 4.4 纠错

- `POST /v1/correct`，输入 `{"text":"你好 曼苏"}`。
- 处理流程：遍历词典映射 → 对文本中命中的变体替换为标准词 → 命中黑名单的词跳过替换 → 汇总本次实际生效的映射。
- 输出 `{"corrected":"你好 Mansour","applied":[…]}`。

### 4.5 意图分类 + 纠错

- `POST /v1/process`，输入 `{"text":"…"}`，输出 `{"intent":"NOTE","corrected":"…"}`。
- 意图取值至少覆盖 `NOTE` / `QUERY` / `EDIT`，未知情形落到默认意图而非报错。

### 4.6 反馈

- `POST /v1/feedback`，输入 `{"raw":…, "corrected":…, "accepted":…, "reason":…}`。
- 以 **append-only** 方式向 `feedback.jsonl` 追加一行（一行一条 JSON 记录），不修改历史行。
- `accepted=false` 时 `reason` 为必填，缺失应返回参数错误。

### 4.7 黑名单

- `POST /v1/blacklist`，输入 `{"term":…, "note":…}`，写入 `blacklist.json`。
- 语义：该词被认为"改错了"，后续纠错时跳过该词条，不再对其应用映射。

### 4.8 鉴权

- 环境变量配置了 token 时启用，校验 `Authorization: Bearer <token>`；未配置则完全关闭，不影响其他端点。

## 五、数据模型与持久化

| 文件 | 格式 | 写入方式 | 关键字段 |
|---|---|---|---|
| `data/dictionary.json` | JSON | 覆盖写（读改写） | `terms[].term` / `variants` / `category` / `source` |
| `data/blacklist.json` | JSON | 覆盖写（读改写） | `term` / `note` |
| `data/feedback.jsonl` | JSONL | **append-only** | `raw` / `corrected` / `accepted` / `reason` |

实现要点：

- 数据目录由配置项决定，默认 `./data`；启动时若目录或文件不存在则自动创建。
- 进程启动时加载词典与黑名单到内存，写入时同步更新内存并落盘，保证重启后数据仍在。
- `feedback.jsonl` 只追加、不重写，保证审计可回溯。
- 中文以 UTF-8 原样写入，不做转义变形。

## 七、验收判据（真装配，不许桩）

1. `go build` 零错误（仅标准库）。
2. 服务启动后 `GET /v1/health` 返回 `{"ok":true}`。

6. 重启服务后词典与黑名单仍在（持久化跨重启）。
7. 所有端点返回 JSON 响应，中文不乱码。

## 九、风险与注意事项

- **零依赖约束**：路由需用标准库 `net/http` 自行分发，避免引入任何第三方 mux。
- **写入一致性**：JSON 文件为覆盖写，需保证读改写串行化，避免并发请求下词典/黑名单丢条目。
- **黑名单优先级**：纠错流程中黑名单必须优先于词典映射生效，否则"改错了的词"仍会被替换。
- **append-only 纪律**：`feedback.jsonl` 禁止重写或压缩，只允许追加。
- **编码与乱码**：响应头需显式声明 `application/json; charset=utf-8`，避免中文乱码导致验收失败。
- **鉴权开关**：鉴权必须"未配置即关闭"，避免默认开启导致本地自测被 401 阻断。

## 一、核心范式（v2 相对 v1 的升级）

```
可打断流式（骨架：执行时步骤滚动/播报，随时 barge-in 说"停"）
   └─ 一屏刹车点（决策卡：回问候选 / 强确认红条 / 回执卡——只在临界点出现）
   └─ 多角色折叠（Planner→Executor→Verifier 折叠成指令卡，常驻刹车条）
   └─ 打断协议（跨通道统一：停 / 暂停 / 撤销 分离，Cancel 令牌贯穿）
```

**一句话：确认成本压缩到风险真正存在的那一刻，其余时间用户被"预判"而非被"询问"。**

## 二、五个本质原则（评审共识）

| # | 原则 | 含义 | 落地 |
|---|---|---|---|
| 1 | **意图落地** | 把话变成可执行计划/约束：明确目标、边界、完成标准；只追问影响行动的歧义 | 回问候选集按钮化（M4 项 2） |
| 2 | **状态可见（根基）** | 用户任何时候知道 Agent 在干什么、到哪一步；没有可见性则打断/确认/信任都无从谈起 | 执行中步骤滚动/播报 |
| 3 | **可打断可撤销（控制权=信任底座）** | 说"停"立即截断后续动作、显示已生效部分；动作可逆 | barge-in + Cancel 令牌 + rollback |
| 4 | **风险分级确认** | 低风险授权内直做（静默）；高风险提交前唯一刹车 | 一屏刹车点（是/否/改） |
| 5 | **证据即回执** | 结果给可用产物+验证证据（截图/diff/日志），verify 对用户不可见但系统强制 | 回执四行+展开详情 |

## 三、多角色组织（一个 App 多个角色）

**最强范式：总管单入口 + 角色折叠为任务卡**（默认体验）：
- 用户只跟"总管"对话；Planner（复述+计划）/ Executor（流式执行）/ Verifier（自检）折叠在指令卡里
- 上下文随任务延续（交接传目标/约束/产物），权限独立
- 默认只露：负责人、进度、阻塞——其余折叠可展开
- 备选范式（按场景）：工作区+角色切换（长期专业任务）、任务看板+依赖图（并行协作）

## 四、打断协议（跨通道统一，v1 最大缺陷的修复）

- **停**：barge-in 立即截断当前播报/执行，显示已生效部分（停播≠停止执行≠撤销，三者分开）
- **暂停/继续**：长任务可暂停，继续时从安全点恢复
- **撤销**：一步回滚（备份目录），权限保留到下一次高风险操作前
- **Cancel 令牌贯穿**：模型/执行/回滚三层同一令牌，说"停"直达执行器
- 跨通道统一：豆包壳说"停" 与 App 说"停"语义一致（M4 server 侧接入）

## 五、爽感三要素（评审共识：三者同时成立才爽）

| 要素 | 设计 |
|---|---|
| 速度 | 低风险静默执行（不逐级打断）；首反馈 300ms 内（开口即显转写+快速回显理解） |
| 掌控感 | 高风险点有且只有一个清晰低认知负荷刹车（是/否/改，不是十个选项） |
| 不犯错 | verify 对用户不可见但系统强制——用户感受到"它从不出错" |

**验收口径**（不看回复速度，看这四样）：首次有效反馈延迟 / 纠正次数 / 误操作率 / 停止生效时间。

## 六、与 M4 的衔接（server 侧落地项）

1. need_ask 候选集按钮化（M4 项 2）→ 意图落地原则落地
2. 任务状态持久化（M4 项 3）→ 状态可见 + 重启可 rollback
3. 执行中状态回显：server 补轻量进度事件（步骤文字滚动，先轮询后 SSE）
4. /cancel 端点 + Cancel 令牌 → 打断协议落地
5. 回执四行 + 展开详情（diff/日志）→ 证据即回执
6. 多角色折叠：指令卡数据结构（Planner 计划/Executor 进度/Verifier 证据）——iOS 壳 M5 消费

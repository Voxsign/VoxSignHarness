# 技能定义 · 校验与对齐（Validate-and-Align, VAA）

> **定位**：核心元技能——在任何长程任务/大需求/架构决策**动手之前**，先把「大东西」搞清楚。
> 名称（建议发布名）：`validate-and-align` ／ 中文名：校验与对齐
> 版本：v1.0.0 ｜ 作者：测试方（2026-10-03，L-01 实测后沉淀）｜ 状态：待发布

---

## 一、为什么存在（背景 / Why）

2026-10-03 长程任务 L-01 实测暴露：把「按需求说明书实现服务」丢给 harness，三层（意图/规划/执行）全部断链——**核心的东西没想明白，就按部就班一个个补**，改完只会"乱七八糟"。

结论：**动手前必须先做大的校验与对齐**——目标、目的、衡量标准、策略先对齐；架构先判断；关键点与里程碑先清楚。这一步想明白，后面的实现才有意义。

## 二、使用场景（When）

- 长程任务开工前（一个复杂任务要"一次搞定"之前）
- 大需求/PRD/需求说明书评审时
- 架构设计/评审/演进前
- 系统反复修不好、改动"越改越乱"时（先停下来对齐）

## 三、方法论（三步递进，顺序不可跳过）

### 第 1 步 · 大的校验与对齐（OGSM 四问）

| 维度 | 要回答的问题 | 对齐失败的表现 |
|---|---|---|
| **Objective 目标** | 这个任务最终要达成什么？（一句话，可验收） | 目标模糊："做好/完善/提升" |
| **Goal 目的** | 为什么要做？背后的 Why / 价值 | 说不出 Why，只有"别人要求" |
| **Measure 衡量** | 怎么算成功？验收标准 / 指标（必须可测） | 衡量是形容词（"体验好"）而非可测项 |
| **Strategy 策略** | 用什么路径达成？（策略层，不是方法细节） | 直接跳细节方案，跳过策略 |

**校验**：四者必须一致——目标变了，目的/衡量/策略要跟着对齐；**不一致就是未对齐，未对齐就要回问/重新对齐，不得带病进入下一步**。

### 第 2 步 · 大的架构判断

回答三个问题，回答不了就不能进入细节：

1. **大架构是什么？** 分层 / 依赖 / 边界 / 数据流——用一张图或一段话讲清整体结构
2. **我怎么判断它对不对？** 评估维度（可测）：正确性 / 边界 / 可演进 / 可观测 / 安全……每个维度怎么验
3. **核心的东西想明白了吗？** 若核心（关键机制/关键决策）没想明白 → **在此停下**，回去想核心；否则后面的实现是白做

**输出**：架构判断结论（架构形态 + 评估维度 + 是否可进入下一步）。

### 第 3 步 · 关键点与关键里程碑

- **关键架构思想**：这个方案最核心的思想是什么？（一句话）
- **关键点/核心细节**：决定成败的 2–5 个关键点（不是全部细节）
- **关键里程碑**（关键路径）：按依赖排里程碑，**每个里程碑可验证**（怎么验、验什么）
- **风险预判**：每个关键点的最大风险 + 缓解

**校验**：里程碑必须可验（有判据），否则无法判断"是否成功"。

## 四、knowhow（执行步骤，可直接给执行体）

```
steps:
  1. 对齐目标（Objective）：用一句话陈述任务最终要达成的、可验收的目标；说不清就回问
  2. 对齐目的（Goal）：陈述为什么做、价值在哪；没有 Why 则标记为待确认
  3. 对齐衡量（Measure）：列出可测的验收标准/指标（数值或真/假判据），禁止形容词衡量
  4. 对齐策略（Strategy）：陈述达成路径（策略层），不展开实现细节
  5. 校验四者一致性：目标↔目的↔衡量↔策略必须自洽；任何不一致 → 列出差异并回问，不臆造
  6. 架构判断：描述大架构（分层/依赖/边界/数据流）；给出评估维度与每个维度的验证方式；
     明确"核心机制/核心决策是否已想明白"；没想明白 → 停在架构层，不进入细节
  7. 关键点提炼：列出决定成败的 2–5 个关键点与核心细节
  8. 关键里程碑：按关键路径排里程碑，每个里程碑带验证判据与验收方式
  9. 风险与缓解：每个关键点列最大风险 + 缓解措施
  10. 输出《校验与对齐结论》：对齐项 / 未对齐项（差异清单） / 架构判断 / 里程碑 / 下一步建议
cautions:
  - 不跳过：未做第 1–3 步就进细节 = 返工，禁止
  - 核心没想明白就做第 3 步 = 白做，禁止
  - 目标/目的/衡量/策略不一致必须先对齐，禁止带病前进
  - 里程碑必须可验，否则无法判断成功，禁止"无判据的里程碑"
  - 信息不足先提 ≤3 个必要问题，不臆造假设；低风险假设显式标注
  - 输出必须让"没参与讨论的人"能看懂：结论先行，差异明示
```

## 五、一次示范（以 L-01 为实例，2026-10-03）

| 步骤 | 校验与对齐结果 |
|---|---|
| 目标 | harness 能产出「按需求说明书实现个性化 ASR 后台」的长程任务实现（L-01 全绿） |
| 目的 | 验证 harness"复杂任务能产出、持续产出、一次搞定一长程任务"的核心能力 |
| 衡量 | 第 11 章 6 条验收判据逐条真跑通过；红线 4 条不破；三态=PASS |
| 策略 | 先想明白架构（技能化长程任务）→ 按架构层次修 harness → 同一 payload 复测 |
| 架构判断 | 意图层（规则覆盖）≠ 规划层（架构：无长程维度/能力清单无实现类）≠ 执行层（架构：工具零接线）；核心未想明白 → 停在架构层 |
| 关键点 | ① 执行链闭合 ② 规划长程拆解 ③ 意图触发词 ④ 技能化注入 |
| 里程碑 | M1 执行链通（域内工具可执行）→ M2 长程规划产出实现步骤 → M3 同一 payload 复测 PASS |
| 结论 | 未对齐项：无（本轮已对齐）；核心问题 = 架构问题（A1/A2）+ 规则问题（B1） |

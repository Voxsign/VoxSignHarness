## 0. 这份计划要解决什么

现状不是"测试太少"——仓库已有 **232 个 Go 测试、20 个包全绿**，SPEC-v2 里钉死的 **81 个验证器名全部真实存在**。

真问题有两个，本计划针对它们：

1. **不知道"够不够"**：没有任何机制回答"文档承诺的契约，是否都有测试在守"。文档自己写了「规范条目 = 声明 + 可执行断言；无验证器的条目 = 未完成」（`VSL-共识…五原则:19`），但没人执行这条。
2. **测的是零件，不是会话**：现有测试几乎全是**单请求视角**——每个端点各测一遍。而产品定义的是**一整段对话**（录音→提交→running→need_ask/need_confirm→done→rollback→归因）。

第 2 点的证据是硬的：上一轮实测发现 **G8 澄清死循环**——`把这个改一下` → `need_ask` → 答 `main.go` → **逐字又追问同一句**，手机永远走不出这一屏；而对应的单端点测试 `server.TestAskResumeViaAnswer` **是绿的**。单点全绿、真机卡死，这就是缺口。

## 3. 测试策略：五层

每层回答一个不同的问题；**不重复、不越级**。

| 层 | 名字 | 打到哪 | 回答 | 现状 | 本轮要建 |
|---|---|---|---|---|---|
| **L0** | 契约一致性 | 文档 ↔ 代码 | 文档钉的验证器/红线，是否真有断言在守 | 无 | ✅ 新建 |
| **L1** | 单元/契约 | 包内函数 | 每条机械规则对不对 | 232 个，强 | 只补空白项 |
| **L2** | 管线集成 | `pipeline.Run` | 十三步串行 + 门禁 + 回执 | 中 | 补多意图/条件/否定 |
| **L3** | 手机接口模拟 | 真 HTTP + SSE | **手机收到什么字节** | 上轮建了骨架 | 扩到 SSE 与会话 |
| **L4** | **会话模拟** | 多轮驱动 | **一整段对话能不能走完** | 空 | ✅ 重点新建 |

### 为什么不把重点放在 L1/L2

L1/L2 已经很密，继续加只会边际递减。真正的风险都藏在**跨轮、跨状态**的地方——G8 就是活证据。

### 为什么不做"更多端到端真机测试"

真机依赖 iOS 构建与网络（`SPEC-v2:315` 明说 iOS 61/61 来自 shard 报告、本环境未自行编译），成本高、不可重复。**用 L3/L4 的协议级模拟覆盖绝大部分**，只把真正的体感项（打断时延、防误触、播报节奏）留给人工，并明确列进"人工清单"。

## 4. L4 核心设计：手机会话模拟器

### 4.1 为什么它能抓到单点测试抓不到的

单端点测试的隐含假设是"请求是独立的"。真实会话里：

- 上一轮的答案要变成下一轮的上下文（G8 就死在这——答案没回灌给 refer）
- 状态迁移必须单调（不能 done→running）
- 任意剧本都必须能走到终态（不能卡在中间）

这些都是**跨轮不变式**，只有会话级测试能表达。

### 4.2 架构

```
VirtualPhone（模拟手机）
├── Say(text)            提交 → 拿 task_id
├── Watch()              SSE 订阅（主）/ 轮询（兜底），产出带 seq 的事件时间线
├── Decide(policy)       在决策点按剧本作答：选选项 / 确认 / 拒绝 / 静默 / 取消
├── Finish(timeout)      等到终态；超时即判违约
└── Timeline             完整事件序列（用于断言顺序与不变量）

Script（剧本）= 一串 (触发条件 → 动作)，例如：
  S3 提交: on need_confirm(human) → 拒绝；再跑一次 → 批准
```

**关键要求**：`VirtualPhone` 只通过公开协议（HTTP/SSE）与系统交互，**不 import 内部包**。这样它测的是"手机看到的世界"，而不是"我以为的内存状态"。

### 4.3 会话级不变量（断言的对象）

| ID | 不变式 | 依据 | 现状 |
|---|---|---|---|
| I1 | 任一时刻至多一个未决决策点 | `SPEC-v2:237,257`「一屏永远只有一个决策点」 | 未测 |
| I2 | 状态迁移单调合法，不回退 | `SSE-v1:48` 顺序保证 | 未测 |
| I3 | SSE `seq` 从 1 单调递增、`?after` 重连不重不漏 | `SSE-v1:19,37` | 单点已有，会话级未测 |
| I4 | **任何剧本都能在 N 步内到终态** | 闭环本身 | 未测 ← **抓 G8** |
| I5 | 无人工确认时，绝不出现"已人工确认/已执行"的不可逆动作 | `SPEC-v2:260`、`VSL-v1:111` | 部分 |
| I6 | 同一问题不得连续重复追问（澄清必须收敛或升级） | 产品常识 + 文档「一屏一决策」精神 | 未测 ← **抓 G8** |
| I7 | 每个终态都带四行回执；撤销行不撒谎 | `SPEC-v2:143,146-156` | 单点已有 |
| I8 | `BOUNDARY_VIOLATION` 恒 deny，**用户点确认也不放行** | `SPEC-v2:60` | 单点已有，会话级未测 |
| I9 | 停/撤销/打断三命令互相独立，且禁止假报已停止 | `INTERACT-v2.1:32,34` | 未测 |

### 4.4 场景库（会话剧本）

从文档的 M3 手动 12 项 + M7 冒烟 7 项 + 已发现的 8 个缺口，转成可跑的会话：

| ID | 会话 | 来源 | 预期 |
|---|---|---|---|
| S1 | 记想法 → 看回执 → 撤销 | M3 §5⑤ | done + rollback 200 |
| S2 | 改代码（light 确认）→ 回执含 backup | M3 §5②④ | done + 备份路径 |
| S3 | 提交（human）→ 拒绝 → 再提交 → 批准 | M3 §5② | 拒绝不执行；批准后 done |
| S4 | 歧义指代 → need_ask 选项 → 点选续跑 | M3 §5⑦⑨ | 收敛到 done（**G8 会红**） |

| S6 | 不可逆 rollback → 409 | M3 §5⑥ | 409 |
| S7 | 说"停"/cancel → interrupt → canceled | M7 ④、SSE:42-44 | interrupt 先于轮询可见终态 |
| S8 | 同 request_id 重提 → 去重 | M3 §5⑩ | 同 task_id、deduped |
| S9 | 越界写 → 确认也不放行 | SPEC-v2:60 | 恒 deny |

## 6. 边界：本计划不做什么

- **不测音频链路**：VAD/ASR/标点从文本开始，不碰音频。
- **不测 iOS Swift 渲染**：真机项列入人工清单。
- **不写死不确定的东西**：模型层指代/纠错结果只断言「命中或 Ask」；LLM 延迟、缓存命中率不写死（`ARCHITECTURE.md:344` 明说真实延迟由网络决定）。
- **不追愿景指标**：如"10 倍指数"（`SPEC-v2:187` 明说是愿景不是验收）。
- **不把指导线当铁律**：如 `risk.go <150 行`。

## 9. 待讨论的开放问题

1. **会话模拟器放在哪个包**？我倾向新包 `session/`（纯黑盒、只走 HTTP/SSE），而不是塞进 `server/`。这样它不会碰内部结构，也便于将来换成真机跑。
2. **缺口的"红"要不要进 CI**？现在我按"默认绿 + 标签开红"处理。如果你希望缺口在 CI 里持续可见，可以加一个独立的非阻断 job 跑 `-tags asrsimgap` 并把结果贴到 PR。
3. **性能守卫的失败线定多少**？9.9µs 是文档目标，但机器抖动可能到 8µs+。建议失败线 9.9µs、告警线 8µs。
4. **仓库可构建性**（全新克隆因 `.gitignore` 漏了 `cache/`、`ground/` 而编译不过）要不要在本计划里一并修？它不属于测试，但不修的话，L4 的成果推上去也没人能跑。
5. **"人工清单"要不要单独立文档**？把体感项（打断时延、防误触、播报节奏、一屏认知负荷）从测试计划里分离，作为真机验收单。

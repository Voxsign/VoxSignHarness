# 模型中心：两条客户端的边界（provider/ 与 modelcenter/）

> 背景：`ASR-EXT-006` 实测 `POST /api/model/chat` 是**标准 OpenAI 兼容**。
> 直觉是"复用 `provider/` 即可"。**实际不能直接复用**，本文记录为什么，以及两条客户端的边界。
> 裁决（DSH 2026-10-03）：**不要改 `provider/`**，薄客户端保留。

## 1. 为什么没有直接复用 `provider/`

`provider/openai.go` 的 `normalizeEndpoint` 会把端点**规范成** `<base>/chat/completions`：

```go
if !strings.HasSuffix(ep, "/chat/completions") { ep += "/chat/completions" }
```

而实测端点是 `/api/model/chat`。要让 provider 打中它，只能：
- 传 `<base>/api/model/chat/completions` —— **这是在猜路径**（违反 `ASR-EXT-005` A5）；
- 或改 `provider/` 的路径规范化 —— 那是 harness 主链的**生产路径**，需它自己的判据与回归。

两者都不该由本线做。故 `modelcenter/` 用**薄客户端按实测路径原样发起**。
`provider/` **一行未改**。

## 2. 两条客户端的边界

| | `provider/` | `modelcenter/` |
|---|---|---|
| 定位 | harness 主链的生产 provider 层 | 模型中心三条通道（default/diagnose/learn） |
| 端点 | `normalizeEndpoint` 规范化 | **实测路径**原样（`/api/model/chat`） |
| 备用能力 | 重试、`response_format`、`params` 透传 | **刻意最小**：无重试、无流式，便于审计 |
| 配置 | `config.Config.Providers` | `config/model-center.json` + C1–C5 fail-closed |
| 通道语义 | 无通道概念 | 通道名固定；L2 写回令牌只在 `learn` enabled 时签发 |
| 归因 | 无 `model_id` 强制 | 每次调用记录 `model_id`（L5） |

**协议相同**：`choices[].message.content` / `finish_reason` / `usage`。

## 3. 防协议漂移的判据

`modelcenter/convert.go` 提供双向转换（`ToProviderResponse` / `FromProviderResponse`），
`modelcenter/convert_test.go` 做 **round-trip**：

- 共享字段（content / finish_reason / usage 三项）必须**无损保留**；
- 通道层属性（Channel / ModelID）按文档丢弃 —— provider 信封没有对应字段。

任一侧改了响应语义 → 该测试立刻变红。

## 4. 何时合并

若将来 `provider/` 支持"完整端点路径"且本线需要它的重试/流式能力，
再把 `modelcenter/` 收敛为 `provider/` 的一个配置档位；**在此之前两条并存是刻意设计**，不是重复实现。

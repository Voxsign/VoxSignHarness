## 一、产品行为类

### OBS-01 【真跑】`waiting_confirm` 的响应**缺 `attribution` 与 `receipt`**

**现象**
```
POST /v1/run {"text":"实现《VoiceSign个性化ASR后台需求说明书v2》"}
⇒ 任务停在 waiting_confirm，响应**只有 4 个键**：
   {"question":"人工放行（不可逆）：意图基线标不可逆 → 永远人工确认，放行？(y/n)",
    "role":"","status":"waiting_confirm","task_id":"task-…"}
⇒ 而 `done` 状态是**带** `attribution` + `receipt` 的
```

**复现**
```bash
A=http://127.0.0.1:8765
TID=$(curl -s -X POST $A/v1/run -H 'Content-Type: application/json' \
  --data-binary '{"text":"实现《VoiceSign个性化ASR后台需求说明书v2》"}' | python3 -c 'import json,sys;print(json.load(sys.stdin)["task_id"])')
sleep 5; curl -s $A/v1/tasks/$TID
```

**期望 vs 实际**
- 期望：`waiting_confirm` 也给出 `attribution`（**为什么**需要确认）—— 与其他状态一致
- 实际：**只有一句 `question`** ⇒ 调用方无法程序化解释"为何要人介入"，只能把 question 原样透传

**已排除**
- 不是"任务太慢还没填"：**3s / 8s / 15s 三次响应完全一致**

**严重度**：中（信息量不对称；影响所有需要人介入的 UI/自动化）

### OBS-04 【真跑】`/v1/run` 跑的任务**从不落盘**（代码上说不通）

⚠️ **这是本轮最重要、也最"说不通"的一条。**

**现象**
```
`~/.voicesign/harness/tasks/` 有 **23 个 task-*.json**（你/豆包写的 · 最新 14:59 · status=need_confirm · planner）
⇒ 说明 persist 机制**工作正常** ✅

而**我起的线 A**（`vhs serve` + `/v1/run`）跑的任务，**一个都不落盘**：
  · 目录计数恒为 23（POST 后 1s/2s/3s/4s/5s 都不变）
  · `[ -f "$D/<tid>.json" ]` ⇒ ✗
  · `find $HOME -name "<tid>*"` ⇒ 零结果
  · 无 `.tmp` 残留
```

**复现**
```bash
D=~/.voicesign/harness/tasks
B=$(ls $D | wc -l)
(cd <repo> && ./vhs serve &) ; sleep 8
TID=$(curl -s -X POST http://127.0.0.1:8765/v1/run -H 'Content-Type: application/json' \
  -d '{"text":"记一下想法"}' | python3 -c 'import json,sys;print(json.load(sys.stdin)["task_id"])')
sleep 5
echo "基线=$B 现在=$(ls $D|wc -l) 该文件存在? $([ -f "$D/$TID.json" ] && echo ✅ || echo ✗)"
```

**代码上应当落盘**（【读码】）
```go
server.go:559  spawnTask 里 **无条件** s.persist(ts)（持锁内 · **已读全文 · 无 early-return**）
server.go:1176 persist()  = MkdirAll → MarshalIndent → WriteFile(tmp) → Rename   // **无分支**
server.go:1172 tasksDir() = filepath.Join(s.cfg.Global.LogDir, "tasks")
server.go:167  New(cfg,·) ⇒ s.cfg = cfg      // main.go:180 传 loadCfg() 那份，**未见改写**
且 `/v1/status` 报 "tasks":23  ⇒ **服务读的就是同一个目录**（restore 成功）
```

**已排除（8 项，全部实测）**

| # | 假设 | 排除方法 | 结果 |
|---|---|---|---|
| 1 | `VHS_LOG_DIR` 覆盖导致 | 设/不设各跑一次 | 都 ✗ ⇒ 无关 |
| 2 | 只有"重任务"才落盘 | 用实现类（`waiting_confirm`） | 也不写 |
| 3 | 写到别的目录 | `find $HOME -name "$TID*"` | 零结果 |

| 5 | 权限 | 同目录别的文件在写 | — |
| 6 | `.env` 影响 | grep 全部 `VHS_*` | 无任何键 |
| 7 | cwd / 二进制陈旧 | 从仓库目录跑 · 用 `f9eb519` 重新构建 | 仍 ✗ |
| 8 | 写了又被删 | 每 20ms 监视目录 × 300 次 | 条目数**恒为 25** ⇒ 从未出现新文件 |

**🎯 根因已找到（观察期间追加实验）**
```
基线 26
① POST **/v1/run**          ⇒ 目录 26 → 26 · 文件 **✗**   ← **不落盘**
② POST **/v1/tasks**        ⇒ 目录 26 → **27** · 文件 **✅**  ← 落盘
③ POST /v1/tasks + document ⇒ 目录 27 → **28** · 文件 **✅**  ← 落盘
```
**复现**
```bash
D=~/.voicesign/harness/tasks
T1=$(curl -s -X POST $A/v1/run   -H 'Content-Type: application/json' -d '{"text":"记一下想法A"}' | python3 -c 'import json,sys;print(json.load(sys.stdin)["task_id"])')
T2=$(curl -s -X POST $A/v1/tasks -H 'Content-Type: application/json' -d '{"text":"记一下想法B"}' | python3 -c 'import json,sys;print(json.load(sys.stdin)["task_id"])')
sleep 3
echo "/v1/run   ⇒ $([ -f "$D/$T1.json" ] && echo 落盘 || echo **不落盘**)"
echo "/v1/tasks ⇒ $([ -f "$D/$T2.json" ] && echo **落盘** || echo 不落盘)"
```
**⇒ 即：同一服务、两条创建入口，持久化行为**不一致** —— 这不是环境/权限/marshal 问题，是**两条入口走了不同的代码路径****

**🎯 重启对照实验（**已补做成功 · 结论从"推断"升级为"实测"**）**
```
第一步：验证 POST 成功（避免上次"空 task_id"的失败）
  POST /v1/run    ⇒ **HTTP 202** ✅ · POST /v1/tasks ⇒ **HTTP 202** ✅
  T1 = task-1791030731655691000（/v1/run）· T2 = task-1791030731670580000（/v1/tasks）—— **都非空** ✅

第二步：落盘对照
  /v1/run    ⇒ 文件 **✗ 不存在**
  /v1/tasks  ⇒ 文件 **✅ 存在**

第三步：**干净重启**（确认端口释放后用同一 LogDir 重启）
  ① `/v1/run`   的任务  ⇒ **`{"error":"未知 task_id"}`**   ← **丢失** ❌
  ② `/v1/tasks` 的任务  ⇒ **`{"attribution":{…}}`**（正常返回）← **恢复了** ✅
```
**⇒ 结论（实测）**
```
**通过 `/v1/run` 创建的任务：重启后**确实丢失**（`restore()` 读不到它，因为盘上没有）**
**通过 `/v1/tasks` 创建的任务：重启后**确实恢复****
⇒ ⇒ **同一套任务系统，两个入口的**持久化语义不同** ⇒ 调用方无法预期，且 `/v1/run` 的丢失是**静默的****
```

**⚠️ 关于我先前的两次失败尝试（如实保留）**
```
· 第一次：我用 `VHS_ASR_DATA` 当数据目录 ⇒ **该变量对线 A 无效**（线 A 认 `cfg.Global.LogDir`）⇒ 观察无效
· 第二次：两个 POST **都返回空 task_id** ⇒ 查的是空 ID ⇒ 该次无效
⇒ ⇒ 第三次（上面这次）**先验证 POST 返回 202 且 task_id 非空**，才开始重启对照 ⇒ 有效
```

**🎯 根因链（已定位到代码位置 · 【读码】）**
```
server.go:184  mux.HandleFunc("/v1/run",   s.auth(s.**handleRun**))
server.go:259  func (s *Server) handleRun(…)
                 ⇒ **自己 `s.tasks[ts.ID] = ts`**（手动入 map）· **未调用 `spawnTask`**
                 ⇒ ⇒ **因此跳过了 `spawnTask:578` 里那句无条件 `s.persist(ts)`** ❌

server.go:179  mux.HandleFunc("/v1/tasks", s.auth(s.**handleTasksPost**))
server.go:810  func (s *Server) handleTasksPost(…)
                 ⇒ `ts := s.**spawnTask**(req.Text, req.Space, req.RequestID, req.Document, req.ConvID)`
                 ⇒ 而 `spawnTask:578` **无条件** `s.persist(ts)` ⇒ **落盘** ✅
```

**⇒ 一句话根因**
```
**`/v1/run` 的 handler 自己创建任务，跳过了 `spawnTask`** ⇒
**`spawnTask` 里那句无条件 `persist(ts)` 就没被执行** ⇒
**该入口创建的任务从不落盘 ⇒ 服务重启即丢**（而 `/v1/tasks` 走 `spawnTask` ⇒ 落盘 ⇒ 可恢复）
```

**⇒ 请注意我**只报位置，不给修法**（实现方决定是"统一走 `spawnTask`"还是"在 `handleRun` 补 `persist`"，
   因为前者可能改变 `/v1/run` 的其它语义，后者可能遗漏其它 `spawnTask` 附带行为）**

**严重度**：**高**（若线 A 真不落盘 ⇒ 重启即丢任务 ⇒ §5.1 的 `interrupted` 恢复机制在 HTTP 路径上形同虚设）

**已排除之外**：⚠️ 我**未核**那 23 个文件是**哪个入口**写的（`vhs serve`？子命令？）—— **这条对照能极大加速定位**

**严重度**：中（如果用户侧"有时很快、有时 60ms"，体验不稳定；且说明有两条路径未被区分）

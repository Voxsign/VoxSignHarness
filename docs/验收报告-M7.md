### 8.2 Codex 诊断结论（原文摘要）
> 根因判断：基本确认。refer.ResolveOptions 不区分意图，命中"这个"后候选为空便写入 it.Ask；随后 NeedsClarification() 只检查 Ask != ""，于是高置信 QUERY 也被送入 need_ask。此前清空分类器残留 Ask 的修复无法处理这个问题，因为这里的 Ask 是 refer 阶段新写入的。
> 最小改动：在 pipeline 调用 refer 前按意图门控（勿改 NeedsClarification——会把 refer 产生的 Ask 和其他阶段合法 Ask 一并吞掉）。QUERY 高置信（>=0.8）跳过 refer；NOTE/EDIT/COMMIT 保留。
> 边界：显式对象请求（"查一下这个文件的内容"）需额外判断；低置信 QUERY 保留澄清。

### 8.3 落地（pipeline.go）+ 复验发现并修的第二层根因
| 层 | 根因 | 修复 |
|---|---|---|
| refer 门控（Codex 方案） | refer 不区分意图，QUERY 高置信口语"这个"也写 Ask | `shouldResolveRefer`：QUERY≥0.8 → false；NOTE/EDIT/COMMIT → true |
| **复验发现**：规则误判 | 22:04 句规则分类器判 **NOTE 0.85**（口语长问句），fallback 原触发条件（UNKNOWN/低置信）不生效 | fallback 触发扩展：含问句特征且未判 QUERY → 一律调 LLM 复查（→ QUERY 0.85） |
| **复验发现**：口语代词 | "如果这个效果好"的"这个"非操作指代 | `shouldResolveRefer` 加口语问句特征豁免（?？吗呢怎么如何为什么哪 → false） |
| **复验发现**：JSON 壳 | queryLLMAnswer 模型输出意外 JSON `{"intent":"NOTE","confidence":0.8,"message":…}` | 解壳键加 message；prompt 强化禁 JSON/分类；解壳失败 → 降级文案不透传 |

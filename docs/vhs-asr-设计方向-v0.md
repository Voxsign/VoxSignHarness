## 1. 原话与我的理解

> 「新造一个用 **Go 语言**做的 voice-sign 原来的后台——关于 **ASR 的个性化识别**那块的东西。
> **完完全全用 Go 实现**，性能要特别高、很快。把原来那些能力重新琢磨一下，
> **变成一个服务**。先不要考虑前端，只在**后端**。
> 接下来我跟你说话的语音，你就开始跟他做……
> 相当于再做**一个新的项目**，叫 ASR 个性化识别的项目，**单独做一个这样的层**。
> 做一个这个 **ASR 识别的 harness**——怎么样更好地把它固化下来、怎么样更优化。
> **把我跟你聊天那个内容做成测试项**，看你原来那个 voice-sign harness 做得怎么样。」

**我的理解（若错请纠正）**：

1. **这不是替代 vhs**，是把 vhs 里"ASR 容错"这一块**抽出来、做大、做成独立服务**。
2. **输入是真实语音**（经 ASR 变成文本），**不是造出来的测试句**。
3. 要**双层产出**：① 一个可独立跑的 Go 服务；② 一套专测它的 harness（桩）。
4. **反过来评测**：这套桩还要能拿去量原来的 vhs，看差距。

## 2. 为什么值得单独立项

现有 vhs 的纠错能力是**三块散落的代码**：

| 位置 | 做什么 | 局限 |
|---|---|---|
| `input/clean.go` | 填充词、全角半角 | **只处理句首**（实测：`嗯那个呃记一下` → `那个呃记一下`） |
| `memory/dictionary.go` | 个人词典**精确变体** | 无同音/近音，没预置的词条无能为力 |
| `input/punctuate.go` | 标点恢复 | —— |

实测暴露的真问题（本会话 ASR 校正桩）：

```
① "帮我把这个文件出交一下"（提交→出交）→ UNKNOWN      ← 多字触发词被听错，整条链路断
② corrected = "那个呃记一下这个想法"                    ← 填充词只清了句首
```

**根本原因**：纠错是**规则层的副产品**，不是**一等能力**。它没有：
- 统一的观测点（纠对了没、纠错率多少）
- 在线学习（用户用久了应该更准）
- 性能设计（每次全表扫描）

**单独立项的理由**：它值得有自己的接口、自己的桩、自己的性能指标、自己的演进节奏。

## 3. 架构：快慢两条路

```
                 ┌──────────────────────────────────────────┐
   原始 ASR 文本 → │  ① 本机快路（Go，微秒级，零外部调用）        │ → 文本 + 纠错记录
                 │     归一化 → 热词/词典匹配 → 同音近音索引   │
                 │     → 上下文偏置打分 → 输出 top-k 候选      │
                 └──────────────────────────────────────────┘
                                  │ 低于置信阈值 或 候选冲突
                                  ▼
                 ┌──────────────────────────────────────────┐
                 │  ② 外部慢路（接口 + key，毫秒级）           │ → 重排序/裁决
                 │     模型中心 / Jev 判断原语                 │
                 └──────────────────────────────────────────┘
```

**为什么这么分**（对齐架构第一原则）：
- **本机**：个性化状态（个人词表、热词、纠错历史）+ 快速匹配引擎 ——
  它们是"关于这个人正在说什么"，**外置就没意义**，而且**必须快**。
- **外部**：模型判断 —— 它是通用能力，**外置才有复利**（可升级、可归因、可版本化）。

## 4. 关键技术决策（含理由与代价）

| # | 决策 | 理由 | 代价 |
|---|---|---|---|
| **D1** | Go 单二进制，零第三方依赖 | 与 vhs 一致；部署简单；换机不重建 | 拼音表、AC 自动机都要自己写 |
| **D2** | **拼音索引**做同音/近音 | 中文 ASR 错误的绝大多数是同音/近音（"出交"↔"提交"）；用拼音做键，一次查全 | 需要一份汉字→拼音表；多音字要处理 |
| **D3** | 多模式匹配用 **AC 自动机 / Trie** | O(n) 一遍扫描，不是每词一次 `strings.Contains` | 词表变更要重建索引（可增量化） |
| **D4** | 个性化 = **词表 + 频次 + 邻接上下文** | 只存词太弱；"上次说过这个词"是最强的个性化信号 | 需要在线更新与衰减策略 |
| **D5** | 纠错**必须可观测且可回溯** | 不知道纠了什么，就无法优化、无法归因 | 每次纠错要带证据 |
| **D6** | **不猜**：低置信一律回问 | 对齐 peterzou.com《警惕 AI 的脑补》 | 会多问，但错一次代价更大 |
| **D7** | 个性化状态**留在本机**，模型能力**外置** | 架构第一原则 | 需要清晰的边界定义 |

## 5. 接口草案（"重新琢磨"的那一步）

现有接口是 `Dictionary.Correct(text) → (text, []Correction)`，**只够做精确替换**。
重新琢磨为**三件事分层**：

```
// ① 纯函数式的单次纠正：无状态，可并发，微秒级
Correct(req CorrectRequest) CorrectResult

type CorrectRequest struct {
    Raw      string   // ASR 原始输出，必须留底
    Context  []string // 近期上下文（同一段对话的前几句）
    Domain   string   // 当前域（影响热词优先级）
}

type CorrectResult struct {
    Text        string        // 纠正后文本
    Corrections []Correction  // 每一处纠正都带证据
    Candidates  []Candidate   // 备选（置信度接近时不猜，交给外部/人）
    Latency     time.Duration
}

type Correction struct {
    Start, End int      // 在 Raw 中的字节区间（可回溯）
    From, To   string
    Kind       string   // filler | homophone | hotword | dictionary | punctuation
    Confidence float64
    Evidence   string   // 为什么这么纠（命中了哪条规则/哪个词条）
}
```

```
// ② 在线学习：把"纠对了/纠错了"喂回来
Observe(fb Feedback)

type Feedback struct {
    Raw       string
    Corrected string
    Accepted  bool     // 用户接受了吗
    Source    string   // user_edit | implicit | reviewer
}
```

```
// ③ 服务面（先只做后端）
POST /v1/correct   { raw, context, domain } → CorrectResult
POST /v1/observe   { feedback }             → ack
GET  /v1/lexicon   ?domain=                 → 当前个性化状态（可审计）
GET  /v1/health
```

**设计要点**：`Correct` 是**无状态纯函数**（好测、好并发、好回放），
个性化状态由 `Observe` 更新、由 `/v1/lexicon` 可审计。**状态与计算分离。**

## 6. 测试桩（"ASR 识别的 harness"）

### 6.1 语料：**真实对话，不是编的**

这是本项目最硬的一条：语料**取自 Peter 与 DSH 的真实交互**（手机说 → ASR → 文本）。
首批已经存在（本会话实测过的真句）：

| ID | 原始 ASR 文本 | 已知问题 |
|---|---|---|
| `real-01` | 嗯那个呃记一下这个想法 | 填充词只清句首 |
| `real-02` | 帮我把这个文件出交一下 | 多字触发词同音失真→UNKNOWN |
| `real-03` | 记一下：这次要修的是报价页那个别字 | 别字应纠"错别字" |
| `real-04` | 不要删除那个文件 | 否定不得被纠没 / 不得执行 |
| `real-05` | 查一吓库存还有多少 | 近音失真，但意图侥幸保住 |
| `real-06` | 把抱价单改成中文 | 专名同音 |
| `real-07` | 呃呃呃 | 噪声必须回问 |

**每一轮对话都往里加**——语料**随使用增长**，这是"越用越准"的度量基础。

### 6.2 判据（四类，每类双向反例）

| # | 判据 | 双向 |
|---|---|---|
| **C1** | 纠错**不该纠的不能纠**：`不要删除`→ 不得纠成"删除"；专名不得被无关词条替换 | 要测"该纠的纠了"**和**"不该纠的没动" |
| **C2** | 触发词同音容错：多字触发词被听错后仍能还原意图 | 不得因此把无关句纠成命令 |
| **C3** | 噪声不脑补：纯噪声必回问，不得纠成一个看似合理的命令 | 不得把正常短句误判为噪声 |
| **C4** | 可观测：每次纠错带 `(区间, 原因, 置信度)`，raw 原文留底 | 纠错记录为空 = 红（等于没纠） |

### 6.3 性能判据（"快"必须可测）

- **延迟**：50 字输入 p99 < **1 ms**（本机快路，无外部调用）
- **吞吐**：单核 ≥ **10k QPS**
- **内存**：常驻 < 50 MB；词表 10 万条时索引构建 < 1 s
- **零外部调用**：快路必须能在**断网**下工作（这条同时验证了架构第一原则）

## 7. 与 vhs 的关系

**不是替代，是抽层 + 反哺**：

```
vhs（控制器/执行引擎）
  └── asr 层（本项目） ← 抽出来做大
        ↑ 回哺：vhs 的 input/clean.go 改为调用 asr 服务
        ↓ 反测：asr 的桩拿去量 vhs 的 ASR 容错
```

- **短期**：asr 作为独立包/服务存在，vhs 通过接口调用（可本地进程内调用，也可 HTTP）
- **中期**：vhs 的 `input/clean.go`、`memory/dictionary.go` 变成 asr 的**薄适配层**
- **长期**：asr 就是"个性化识别"的唯一定义处，vhs 不再自己纠错

## 10. 诚实边界

- 本文档的**性能数字（1ms / 10k QPS）是目标，不是实测**；P2 之前都是假设。
- 拼音索引的**多音字**处理未设计；中文同音纠错在**人名/专名**上风险最高（纠错比不纠更糟）。
- **语料只有 7 条**，远不足以证明"越用越准"；需要靠后续真实对话持续积累。
- 本文档**没有**验证 peterzou.com 文章的正文，引用的是目录页摘要。

## 〇、一句话结论

**AIOps 平台无法通过 API 为云端 harness 设置环境变量 `VHS_TOKEN`。** 平台现有写通道仅限「技能发布（skill）」与「邮箱集成（email）」，唯一的部署机制是 git release tag 触发的 CD watcher（cicd，人工批准、只读 deploy key），**没有任何「设置容器环境变量 / 重启容器」类 API**。故本动作登记为「**待云端运维执行**」。

## 一、背景与风险（为什么必须设 VHS_TOKEN）

| 项 | 现状（2026-10-05 实测） | 风险 |
|---|---|---|
| 云端健康检查 | `GET https://voxsign.ai/v1/health` → `{"bind":"0.0.0.0:8898","ok":true,"tasks":15,"token_set":false}` | `token_set=false`：设备鉴权令牌未配置 |
| 设备注册接口 | `POST /v1/devices/register` **不带任何凭证即 200** 并注册成功（发设备 token） | **【中·生产风险】** 任意匿名方可注册设备、占用设备表、冒用通道；设备链路完全裸奔 |
| 期望态 | 设置 `VHS_TOKEN` 后，`/v1/devices/register|heartbeat` 强制 Bearer 校验（本地 main 的 deviceToken 中间件已实现该逻辑） | 无凭证→401；带正确 Bearer→200 |

> 依据：server.New() 仅云端模式初始化 devices registry；deviceToken 中间件在 `VHS_TOKEN` 存在时启用 Bearer 校验，缺失时放行。当前云端 `token_set=false` ⇒ 中间件处于放行态。

## 三、待执行动作（云端运维在主机上完成）

> ⚠️ 以下动作**只能由持有主机登录权限的云端运维执行**；本次任务受硬约束（禁止 SSH、禁止直连服务器 IP、禁止控制台凭据），仅凭 AIOps key 经平台 API，而平台无此能力——故不在本次执行，登记待办。

1. **生成强随机令牌**（64 位十六进制 = 32 字节）：
   ```bash
   openssl rand -hex 32
   ```
   输出即 `VHS_TOKEN` 值（妥善保管，仅存云端 harness 环境，绝不下发 iOS、绝不入库入日志）。

2. **写入 harness 容器环境**（二选一，按实际 compose 结构）：
   - 在 `docker-compose.yml` 的 `harness` 服务 `environment:` 段增加：
     ```yaml
     environment:
       VHS_MODE: "cloud"
       VHS_TOKEN: "<上一步 openssl rand -hex 32 的输出>"
     ```
   - 或使用同目录 `.env` 文件（compose 自动加载）写入 `VHS_TOKEN=<值>`，并确认 `.env` 已在 `.gitignore`（密钥不入库）。

3. **重启 harness 容器使环境生效**（caddy 不动）：
   ```bash
   docker compose up -d harness        # 或：docker compose restart harness
   ```
   - 注意：`docker compose restart` 仅重启容器；若改的是 `environment:` 段，需 `up -d` 让 compose 按新定义重建容器环境。

4. **日志脱敏自查**：确认 harness 启动日志、notes.md、tenants/ 下轨迹文件不回显 `VHS_TOKEN` 明文。

## 五、为什么 AIOps 平台做不了（探测证据，2026-10-05）

探测方式：短超时（--max-time 8）只读 GET，Header `X-AIops-Key`（key 值取自环境变量，不打印不落盘）。**未执行任何写操作 / 未改动云端状态。**

### 5.4 现有写通道范围（POST，与「设环境变量」无关）

| 路径 | GET 探测 | 写通道实际用途 |
|---|---|---|
| `/api/skill/create` | 404 `not_found`（POST-only；历史报告：POST→401 `write_key_required`） | **技能发布**——write-grant 流程仅服务于此 |
| `/api/keys/write-grant` | 200 html 6941（POST-only；历史报告：POST→400 `bad_purpose`「流程活着」） | 申请 **write key**，范围=技能发布，**不覆盖容器环境/部署** |
| `/api/email/status` | 400 `bad_tenant`（POST /api/email/scan|config） | **邮箱集成**（IMAP/M365），与 harness 环境无关 |

### 5.5 目录中唯一的部署机制 = cicd（CD watcher），仍不可达

服务目录 `cicd`（type=internal，status=**partial**）：
> GitHub Actions（CI 测试门禁，1365 passed）+ trelva `/opt/metasystem-watcher` 按 **release tag** 触发部署；凭据=factory **只读** deploy key（2026-10-01 装配）；watcher 连通正常，**等待首次 release tag；首次真实发布需容器接管（人工批准）**。

判定：
- 它是 **git release-tag 驱动**，不是 AIOps-key API 驱动——无法凭平台 key 触发；
- deploy key **只读**，且首次真实发布需**人工「容器接管」批准**；
- 它做的是「按 tag 整体重新部署」，**不提供「给运行中容器设一个环境变量 VHS_TOKEN」的步骤**；且 VHS_TOKEN 属密钥，不应烘焙进 git 仓库。
- 结论：**write-grant / write-key 流程不能覆盖环境变量设置或部署**；平台无此能力。

## 1. 项目是什么（北极星）

**用户原话（逐字，项目唯一锚点）**：

> 「我为什么用你这个事就是因为豆包的语音识别效率比较高，用手机比较方便。其实我要的就这么简单个东西……那我的 harness 也比豆包的 harness 要好就行了。」

**北极星一句话**：语音说 → 系统理解 → 调度执行 → 真实反馈的闭环，体验与效率 ≥ 豆包体系。

**定位**：手机=控制器（唯一交互界面，语音输入+回执阅读+确认对话），电脑/服务器=执行引擎（Go harness+模型中心+工具+校验+沉淀）。产品目标="10 倍的自己"（个人生产底座，复利来自底座），**不是**做给别人用的通用产品。设计假设：**软件越来越个性化（自建服务），硬件/智能/标准化能力（ASR/语音/消息）用基础设施**。

**竞争力来源**：不在语音层（ASR 是及格线），在 harness 层——理解→调度→执行→验证→回执→归因的闭环 + 个人上下文（project-map/decisions-log/词典/异常知识库）私有复利。**别人抄不走的是执行底座+上下文，不是手机壳。**

## 2. 设计哲学与已拍板决策链（每条均有出处）

| # | 决策 | 内容 | 拍板/评审 |
|---|---|---|---|
| 1 | **两种语言分离** | 代码语言（严格逻辑）与描述定义语言 VSL（软约束/大模型输出规范）拆开；先定义清楚再落硬代码 | 用户拍板 |
| 2 | **三环架构** | record（碎片原汁原味记录）/ discuss（建模、讨论收敛，让模型认知越来越强）/ control（执行、对比"模型错还是执行错"） | 用户拍板（"域"概念落地） |
| 3 | **域 Space** | 域=权限交集（平台∩域∩工具声明∩本次授权），默认拒绝；稳定主键；数量 3-7 个；漂移即失效 | 用户+Codex/Cursor/Claude 三模型评审吸收 |
| 4 | **指代消解×域** | 指代=画实体边界，域=画空间边界；三层消解（代码词典100%→上下文规则→模型推断）；四元组缓存{意图,域,权限,指代}；低置信回问、确认后固化 | 用户判断的高可能性点 |
| 5 | **确认策略三信号** | ①可逆性（硬规则，不可逆永远人工确认）②影响面（**静态可算**：引用数/热度/测试覆盖，不靠模型自评——Claude 架构性反对吸收）③置信度（仅用于回问）；确认疲劳防护（频率上限+每日抽查+缓存） | Claude 尖锐评审后修订 |
| 6 | **独立校验器** | verify 契约独立于 run；读文件系统实际状态不读执行器自报；校验失败→FAILED→回滚；**回执≠验证**（Codex 意见） | Codex+Claude 共识 |
| 7 | **自举充分条件** | 不是"有独立校验器"，是"契约注册机制可被语音调用"：说"加一个工具把 md 转 pdf"→REGISTER_TOOL→模型生成契约→风险分级→人确认→注册→下次可用。此链路通之前 2.0 不存在 | Claude 核心意见 |
| 8 | **伪代码层** | 逻辑性强/状态复杂/交互多的任务先写"描述定义语言+注释伪代码"再落码；UI 界面类不需要 | 用户拍板（吸收行业讨论） |
| 9 | **交互设计** | 一屏一决策、确认次数最小化（"搞个四五次啥都没结果肯定不对"）、打断/暂停/撤销三语义分离、角色折叠、ASR 不确定先纠错不执行、语音文字双通道同步 | 用户+Grok/ChatGPT/Claude Code/Cursor/AgentKit 业界模式+gpt-6-luna 11 条规则 |
| 10 | **异常自愈** | 出错不是简单降级/静态建议，而是模型中心**问题定位模型**判断异常+自愈动作+学习回写（"能自愈、不断发现问题"） | 用户拍板（拟名 JEV/GAB） |
| 11 | **组织者机制** | 复杂任务由组织者式路由编排（非 ReAct 循环），确定性编排引擎接管，回执可预测/可白名单/可幂等 | 用户明确赞赏 |
| 12 | **边界五轴** | 范围/排除/权限/验收/上下文——意图识别=画边界；模型碰 non_goals 或超 scope → 独立校验器拦截 BOUNDARY_VIOLATION；"来回五次"自动化 | 用户核心理念实施 |

**判断语义共识（VSL-v2，三模型共识）**：字段罗列描述"是什么"≠懂；机器"懂"=遇到字段没覆盖的新情况能按你的立场做出一致选择。定义块强制字段：purpose/priority/anti/cost/correct/ask。**模型=可被推翻的信念+更新规则；控制=可被验证的承诺+中断准则；共识=让理解获得行动正当依据的过程。**

**验证标准层（VSL-v3）**：没有验证标准的定义不是"待完善"，是**不可实施**。三种病态：不可判定（形容词）、可判定但不可观测（自述）、可观测但无阈值。定义块追加 verify 七字段（claim/method/evidence{level E0-E3,kind,ref}/threshold/counterexample/verdict_states[met,unverified,not_met]/approver≠builder/falsifier）。**unverified 不得折算为通过。**

## 3. 架构总览

### 3.1 分层（单向依赖，Go 单二进制，零第三方依赖，JSON 配置不用 YAML）

```
输入容错层：ASR原文留底 → 清洗 → 词典纠错(季总→冀总) → 意图JSON{type,path,params,confidence}
认知层：project-map / decisions-log / prefs —— 独立低频异步更新，注入前相关性检索（不全量塞上下文）
接口层：七工具契约 git/file/search/test/run/verify/ask（只增不改、版本化、冻结）
执行层：意图→规划→风险分级器→执行器→独立校验器→回执（可检索/可撤销/可追溯）
沉淀层：轨迹JSONL append-only / 归因六格(输入/上下文/契约/模型判断/执行/外部) / 三元组缓存 / 异常知识库
```

### 3.2 主执行链（13 步，顺序固定，不得绕过）

```
保存input_raw → 清洗 → 词典纠错 → TaskClassifier → refer指代消解 → space select
→ space.Check → 风险分级 → 需确认则确认 → 按契约执行 → 独立校验器 → 归因写轨迹 → 缓存+四行回执
```

### 3.3 意图分类（8 类 + ORCHESTRATE，规则优先+模型兜底）

| 意图 | 示例 | 风险基线 | 契约 | 实现状态 |
|---|---|---|---|---|
| EDIT 改代码 | "把报价模块错误提示改中文" | 可逆/影响中 | file+git+test+verify | 占位回执（待模型工具循环） |
| DEBUG 查bug | "修一下这个崩溃" | 可逆/影响高 | git+test+run+verify | 占位 |
| QUERY 查代码 | "这个函数在哪定义" | 只读 | search+file+git | ✅ 真执行（LLM 真实回答） |
| TEST 跑测试 | "跑一下测试" | 只读 | test | 占位 |
| COMMIT 提交 | "提交这批改动" | **不可逆** | git | ✅ 真执行（git add+commit+log） |
| DEPLOY 部署 | "发布到服务器" | **不可逆** | run+git+verify | 占位 |
| NOTE 记想法 | "记一下这个想法" | 只读 | file | ✅ 真执行（append notes.md+备份） |
| ASK 问问题 | "这个库怎么用" | 只读 | ask | ✅ need_ask 一次回问 |
| **ORCHESTRATE** | "把全部文档整理成全景文档并提交" | 不可逆（基线） | 读→LLM汇总→写→提交 | ✅ M8 真执行 |

### 3.4 域（Space）定稿表（五类模板，有效权限=交集，默认拒绝）

| 域 | 权限 | 说明 |
|---|---|---|
| global | 只读兜底 | 默认域，无写 |
| project（参数化） | 可读写+契约+认知切片 | "在 voicesign-harness 里改 X"，scope 为调用参数 |
| sandbox（单例） | 临时+过期+自动清理 | 禁止长期 sandbox |
| vault-notes（单例） | 追加 | 想法库 |
| vault-creds（单例） | 高敏只读 | 凭证库，独立强门槛 |
| external（单例） | 永远强确认 | 强确认绑定具体目标 |

原则：**默认拒绝**；切域不继承授权；单次操作按（操作类型+资源类型）独立评估；宽松域不能掩盖高风险操作（git push --force 永远高风险）；模型只建议域、代码用注册名/别名/工作位置消歧；未知→global 只读，绝不猜最像的。

### 3.5 异常自愈（三环）+ 诊断接口契约

```
① 异常知识库命中（错误指纹→已有根因，0 模型调用）
② 问题定位模型 jev-diagnose（未命中时调用；模型中心已注册，当前模拟桩）
③ 自愈执行器：retry(限2轮)/modify/fallback/ask/stop —— recoverable=false 一律 stop
失败且可再诊断→回②（最多2轮）→ 学习回写 exceptions.jsonl → 归因携带诊断结论
```

**jev-diagnose 契约（v2 定稿，模型中心 OpenAI 兼容端点）**：
- 端点 `POST https://model.peterzou.com/v1/chat/completions`，`model=jev-diagnose`，`response_format=json_object`
- 请求 user 内容：`{task, intent, traces:[{tool, params, error{code,type}, model}]}`
- 响应：`{category(8类: budget/network/param/auth/tool_missing/permission/transient/unknown), root_cause, confidence, recoverable, suggestion, action(retry/modify/fallback/ask/stop), retry_params{backoff_seconds,max_retries,cooldown_seconds}}`
- **fail-open**：诊断调用失败/超时/未配置→自动跳过，主链路兜底（/v1/fallback）继续保证 100% 有响应
- 超时/无快速响应同样进诊断（区分网络慢/预算排队/模型卡死/参数不当）

### 3.6 多步编排（M8，最近交付）

长任务（"整理…文档…保存/提交"三连信号）→ 命中 ORCHESTRATE → 编排引擎：**读 5 份源文档 → LLM 汇总（gpt-6-luna，max_completion_tokens=8000）→ 写目标文档（写前 .bak 备份）→ 定向 git add 单文件 + commit（绝不 add -A）**。配套：ensureProjectSpace（惰性注册 project 域）、commitTargetPath（幂等：无 diff 跳过提交）。**设计取舍：确定性编排引擎而非 ReAct 式模型循环——回执可预测、可白名单、可幂等。**

## 5. 差距与风险（诚实清单，供 DeepSeek 审查）

### 5.1 里程碑层面（M8 报告 §5 原样）
1. 源文档清单**硬编码 5 份**（不支持 glob/多目录/递归）
2. 跨域编排（读 A 写 B）、多目标文档、**EDIT 通用路径真写未覆盖**（EDIT 仍占位回执）
3. LLM 输出非确定性：重跑同任务可能因措辞微变产生新 commit；严格幂等仅逐字节相同时触发
4. 单次 LLM 汇总 43-45s，接近默认 60s 超时上限
5. 自动注册依赖 server 进程 cwd 位于 git 仓库内
6. 工作区存在约 300 行归属不明的未提交改动（ConflictNegation 相关），未纳入交付
7. jev-diagnose 当前为**模拟桩**（模型中心侧），真实 JEV 模型未上线

### 5.2 北极星层面（整体评估约 35-45%）
| 维度 | 现状 | 差距 |
|---|---|---|
| 意图理解（域/指代/复合意图） | 域、指代、词典、ORCHESTRATE 就绪 | 个人画像/记忆/规划建模还很浅（VSL 认知层未接入主循环） |
| 长任务执行 | 编排引擎闭环 | EDIT/DEPLOY/TEST 占位、跨域缺失 |
| 自愈/自能进化 | 诊断+兜底链路通（模拟桩） | 真实 JEV 未上线；无"自我修复代码"闭环 |
| 语音驱动底座 | iOS 壳+ASR 需求雏形 | ASR 纠错/标点/打断交互未完成；真机稳定性待证 |
| 体验超豆包 | 设计共识（一屏决策/只问一次）到位 | M7 三条真机验收未闭环；编排未上真机 |

### 5.3 项目宪章已声明的不做/红线
- 三阶段严格前置不跳步：M8 先拉到"不比豆包差"（不空壳/不乱反问/不卡死）→ M9-M10 让豆包没有的能力稳定可用 → M11+ 让"懂你"可量化可加速
- 任何新契约/新域仍需人工确认，**不做无人自治**；不追求"完全不需要人"
- 性能基线 5.7µs、go test 全绿、DevCheck 71/71、真机 XCTest 15/15 不破坏

### 5.4 未定事项（不能以推测替代契约）
意图 Schema 完整字段；四元组缓存序列化契约；四行回执完整格式；异常知识指纹规范化/冲突/过期/版本策略；自愈预算与计数边界；真实 JEV 模型接口与超时阈值——以上在 SPEC-v2 缺口表中显性登记。

## 6. 请 DeepSeek 特别审视的三个设计争议点

1. **方案 B（确定性编排引擎）vs 方案 A（模型工具循环/ReAct）**：M8 选择确定性编排（可预测/可白名单/可幂等），但牺牲了灵活性（源文档硬编码）。对"个人底座"场景，长期是否必须演进到 A，还是 B+ 显式注册即可覆盖？
2. **VSL 验证标准层（approver≠builder/falsifier 独立）**：单人团队场景下"独立判分者"从哪来？（当前答案：外部强模型异源评审）这是否会造成流程过重？
3. **北极星对标豆包**：用户明确"体验与效率 ≥ 豆包体系"但豆包是可随时打断的成熟产品。当前"一屏一决策+任务卡+角色折叠"设计是否真能追上？最短可用路径是什么？

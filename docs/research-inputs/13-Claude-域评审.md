# 域设计评审

**1. 域 vs 路径+权限列表**
好处：把 scope/perms/tools/context/acceptance 打包成可命名单元，降低每次临时拼权限的认知负担。
坑：执行引擎最终还是要落回路径匹配+ACL判断，域只是这层判断的输入数据。危险在于"域"会被**信任**为已校验的边界——一旦 manifest 与实际目录结构漂移（改名、迁移、子目录新增），它从文档退化成谎言，比裸权限列表更危险，因为裸列表没人会盲信。

**2. 粒度/数量**
按"五类+每项目一个 project 域"会线性增长到几十个，一人公司根本管不过来。建议域数量对应**认知切换点**而非项目数：sandbox/vault/external 各保留全局单例，project 域合并为一个参数化 workspace 域（scope 作为调用时参数，而非每个项目开新域）。否则域本身变成需要治理的资产，违背省心初衷。

**3. 与契约/切片/风险分级结合**
最干净方式：域 manifest 是唯一配置源，工具契约、认知切片、风险分级都是"读域"的消费者，而非反向耦合。但文档没讲清冲突优先级——project 域内发生一次 external 级操作（如域内脚本触发 git push --force）时谁赢？必须有显式"域内逃逸规则"，否则宽松的域 perms 会掩盖单次高风险操作。

**4. 一句话意图解析**
本质是 NER+校验，极易出现幻觉域名或相似域名碰撞。兜底必须是：域识别结果**显式回显确认**（至少首次/高风险时），且"未知域→退回 global 只读"，绝不能"猜一个最像的"。

**5. 实施位置/M2**
放 v2"权限与边界"一节无异议。但顺序应调整：先把 registry+执行前校验器打磨稳（纯代码路径），意图解析接自然语言入口放最后，而不是三者并行——校验器本身的 bug 比解析错更致命。

---

**最大反对意见**：怀疑"域"是伪需求式的过度设计。你真正需要的只是"配置的具名复用"（类似 .env profile / k8s namespace），把它拔高成"执行的边界单元"这一等公民概念，会诱使后续设计把精力花在域的类型学（五类怎么分、域间关系怎么建模）上，而不是运行时真正拦截了什么。如果五问的答案最终都归结为"域就是一份配置"，就不必在架构语言里新造"域"这个词——叫 profile 或 policy 即可，省掉一人团队维护一套不必要分类学的成本。

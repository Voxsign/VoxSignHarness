## 三、综合结论

### ① 用户能力谱系（三条线）

**A. AI 工程实验线（造工具/造内核）**——这是底座重设计最该继承的一条：
- 失败可靠性内核（minerva：CPU-only、policy-gated、read-only、`LLM 解释→Policy 授权→Executor 执行`三段式）。
- 感知中间件（perceptkit：YAML 声明场景、热路径规则 1.77µs + 冷路径 LLM reflector、flapping FSM、自学习提议→人工 review→YAML 沉淀）。
- 路由/分流（laya-grok-dispatcher：本地小模型预路由 + PDPL 敏感门 + 诚实指标文化，明确拒绝把本地率写成"成本下降 X%"）。
- 语音/UI 通用包（vox-kit：从业务项目反向剥离的纯逻辑模块，五层语音数据持久化 L1-L5，225 项全 mock 测试）。
- 决策框架（CEOAgent：Skill-based + ReAct + Plan-and-Execute + 多角色 AI 协作 + ADR/DECISIONS/TASKS 文档治理）。

**B. 业务探索线（在沙特落地的真金白银生意）**——当前主战场：
- SFDA 医疗器械/化妆品注册（UniFusion 合作，UDI 自动录入为第一落地，"一人+系统"模式）。
- 中沙服装 B2B（saudi-fashion-b2b + Beauty，一件代发+线下店，AI 内容自产）。
- Trelva.ai（美国假发电商，境外结构，user 不持股）。
- 求职自动化（peter-ai-job-scout，本质是"用 AI 批量生成定制简历"的工程练习）。

**C. 历史技术线（已沉淀为教训，不再投入）**：
- 2019 mamahome（AWS CodeStar）→ 2023 ScreenPlay/InsightSolver → 2024 三个 fork（AutoGPT/pyvideotrans/translation-agent）→ 2025 AutoGPTPeter/PeterEnglish → 2026 初 LarkErp/AppiumGetData。
- 这条线的特征：早期广撒网、fork 体验上游、做零散自动化；2026 年后明显收敛为"自己造内核"。

### ② 可复用资产/思路（具体到组件）

1. **minerva 的可靠性三段式**：`LLM 解释 / Policy 授权 / Executor 执行` + `observe -- <cmd>` 包装任何命令、run record 落盘 `.minerva/runs/`、policy-gated `execute-action` 默认只读——这是生产底座最该直接继承的执行范式。
2. **minerva 的本地 AI 团队循环**：`.tasks/` 看板 + `agent-loop.sh` + launchd/systemd 每 30 分钟 tick + autopilot finalizer（边界检查/污染检查/编译测试/commit/push）+ `MINERVA_AI_EXECUTOR=codex|claude` 可切换执行器——这是"一人公司"的引擎模板。
3. **perceptkit 的冷热双路 + 自学习闭环**：热路径规则毫秒级、冷路径 LLM 只做提议不自动提交、`review approve/reject` 写回 YAML、ReflectionTrace JSONL 审计——任何"该用规则还是该调 LLM"的场景都可照搬。
4. **perceptkit 的离线优先契约**：`cargo deny` 强制禁止 reqwest/hyper 等网络依赖，把"离线可用"做成编译期约束，而不是口号。
5. **vox-kit 的五层语音数据模型**：L1 原始音频 / L2 ASR / L3 修正 / L4 翻译 / L5 业务决定，追加式存储 + consent 分离 + fail-closed——这是任何语音/多模态数据持久化的参考 schema。
6. **vox-kit 的 UIPatch 五重白名单**：function calling 只执行白名单动作，动态 UI 改动要过五重校验——agent 写前端的安全范式。
7. **recovery 的单钥灾难恢复**：一个主密码解密 GPG 保险库，内含 GPG 私钥/部署密钥/Cloudflare token/recover.sh；任意 Ubuntu 联网机器一行 curl 恢复——底座重设计必须先有这一层。
8. **three-companies 的治理文档集**：OGSM-PDCA 审计/台账、DECISION-BOUNDARIES、DECISION-RULES、WORKQUEUE、heartbeat、DISASTER-RECOVERY——这是"三公司协同"的操作手册，可直接抽成底座的 governance/ 目录。
9. **laya-grok-dispatcher 的诚实指标纪律**：明确写"不再把本地率写成对 Grok 的成本下降比例"、P0 红线 zero-shot 不过就不发——底座应内置"诚实口径"模板。
10. **sfda 的监管双周扫描 cron**：signals-log.md 自动追加 + 处罚案例库 + lineage-theory（沙特学谁、滞后规律）——任何 B2B 合规业务都能复用这套监管情报骨架。
11. **saudi-fashion-b2b 的硬停清单（hard-stops）**：明确列出"必须等 Peter 决定"的 4 项（付钱拿样/锁主供/突破价带/对外承诺）——agent 协作时的人类保留权清单，底座应默认带。
12. **Brain（Obsidian vault）**：Philosophy/Understanding/Projects/Habits/Readings/Daily 六分区 + VoxSign 子目录——个人知识库的分层已经成型，底座的"记忆层"可对齐此结构。

### ③ 与生产底座重设计的相关性判断

**该继承（直接搬进底座）：**
- minerva 的 `observe --` 包装 + run record + policy-gated execute-action（执行层）。
- minerva 的 `.tasks/` + ai-team-tick + autopilot finalizer + 可切换 Codex/Claude 执行器（调度层）。
- perceptkit 的冷热双路 + 场景 YAML + review 闭环（感知/路由层）。
- vox-kit 的 L1-L5 五层数据 schema + UIPatch 白名单（语音/前端层）。
- recovery 的单钥 GPG 保险库 + recover.sh（灾备层，底座第一天就要有）。
- three-companies 的 OGSM-PDCA + DECISION-BOUNDARIES + heartbeat（治理层）。
- laya 的诚实指标 + PDPL 敏感门（口径/出口层）。

**只作教训（不搬代码，搬认知）：**
- 历史 fork 时代（AutoGPT/pyvideotrans/translation-agent/InsightSolver）：广撒网、跟上游、无自己的内核——底座重设计要避免再陷入"fork 一堆然后不维护"。
- AutoGPTPeter / PeterEnglish / AppiumGetData / LarkErp：单点脚本、无文档沉淀、push 一年即停——底座要求每个模块自带 README + 测试 + 验证等级（V0-V3，Beauty/saudi-fashion-b2b 已在用）。
- CEOAgent（2026-01）：文档极全（MASTER_PLAN/ADR/DECISIONS）但代码最后停在 1 月，说明"文档驱动≠可执行"——底座要把 MASTER_PLAN 拆成可被 ai-team-tick 消费的 `.tasks/` 卡片，而不是停在 Markdown。
- peter-ai-job-scout：50+ 个 `build_*_resume.py` 脚本平铺在根目录——典型的"脚本农场"，底座应强制按模块/场景分目录 + 抽公共 builder。

**一句话总结**：这个账号的真正资产不是任何单一业务仓库，而是已经反复试出来的一套「一人公司 AI 操作系统」零件——minerva 的执行内核、perceptkit 的感知中间件、vox-kit 的语音/UI 原语、three-companies 的治理手册、recovery 的灾备、laya 的诚实路由。底座重设计 = 把这六个零件从各自业务仓库里抽出来，拼成一个不绑定 SFDA/服装/假发任何单一业务的通用骨架。

## 1. 实测记录（DSH 2026-10-03 真实调用）

### 1.1 调通了什么

| 端点 | 结果 | 内容 |
|---|---|---|
| `GET https://peterzou.com/api/public/catalog` | **HTTP 200, JSON** | `schemaVersion: "1.0"`、`generatedAt`、`site`、`discovery`、`topics[]`、`articles[]` |
| `GET https://peterzou.com/llms.txt` | **HTTP 200** | 站点 AI 索引；列出全部文章与专题链接 |

**`catalog` 的结构**（实测所见）：
```
schemaVersion, generatedAt
site        { name, url, description{zh,en,ar}, languages, basedIn }
discovery   { sitemap, rss, jsonFeed, llms, fullText, catalog }
topics[]    { id, type:"living-research-topic", started, updated,
              title{zh,en,ar}, description{…}, coreClaim{…},
              keywords{…}, audienceQuestions{…}, canonicalUrls{zh,en,ar} }
articles[]  { id, type, published, updated,
              title{…}, description{…}, coreClaim{…},
              keywords{…}, audienceQuestions{…}, canonicalUrls{…} }
```

**关键特征**：
- **三语并行**（zh / en / ar），每个字段都是三语对象
- **`coreClaim` 是核心判断**，与 `description` 分开——**这正是可被机器消费的"判断"，不是摘要**
- `canonicalUrls` 给出每个语言的规范地址
- `discovery` 自描述其他机器可读入口

## 2. 但这条指示的**架构含义**是清楚的，而且它补上了最后一块

Peter 说的是两件事：

**① 外部能力由 harness 调用（不是 DSH 代劳）** —— 与「能力外置，本机极简」一致。

**② 缺什么工具就能"提需求、让它加上"** —— 这是一个**接口**。

把 ①② 合起来，加上本会话已立的规范，形状就完整了：

```
┌────────────────────────────────────────────────────────────┐
│ 本机 harness：只持有「关于自己的事实」                        │
│   能力清单（从代码导出）/ 域门禁 / 执行 / 校验 / 回执 / 轨迹    │
└────────────────────────────────────────────────────────────┘
        │ ① 调用已有能力（接口 + key）
        │ ② 能力不存在时 → **提需求**（不是自己造）
        ▼
┌────────────────────────────────────────────────────────────┐
│ 外部（peterzou.com / 模型中心 / Jev）                        │
│   研究内容 API · 模型（default/diagnose/learn）· 工具        │
│   收到需求 → 补上能力 → 下次本机即可调用                      │
└────────────────────────────────────────────────────────────┘
```

> **这就是 `REGISTER_TOOL` 的正确形态**：
> **注册的不是"装到本机的实现"，而是"外部某个能力的调用权"。**

这也终于解释了 `VHS-PLAN-001` 里那个判据为什么重要：
**能力清单必须准确** —— 因为模型只能组合清单内的东西，
而清单的更新来自**外部**（提需求 → 外部补上 → 清单更新），**不来自本机安装**。

## 3. 接口设计草案（待 Peter 确认端点后细化）

### 3.1 调用已有能力
```
GET  <catalog-endpoint>                     → 能力/内容目录（本机定期缓存元数据，不囤正文）
GET  <capability-endpoint>?id=…&lang=zh     → 取单个能力的结构化结果
```
**本机侧要求**：只缓存**元数据与规范地址**，**不囤正文**（对齐「本机不囤外部资料」，
本会话已清理过一次 `doc-fetch-resources/`）。

### 3.2 **提出"缺什么工具"**（Peter 说的新接口）
```
POST <tool-request-endpoint>
{
  "requested_by": "vhs",              // 谁提的
  "need":          "把 md 转 pdf",     // 要什么能力（自然语言即可）
  "why":           "任务 X 的第 3 步需要", // 为什么需要（**必须有，否则是乱提**）
  "evidence":      "轨迹 <id> 第 3 步失败",  // 证据来源
  "blocking":      true               // 是否卡住当前任务
}
→ { "request_id": "...", "status": "accepted|rejected|duplicate" }
```

**三条硬要求**（与 `ASR-MODEL-02` 的 L2/L3 同源）：
1. **必须带 `why` 与 `evidence`** —— 无证据的工具需求 = 幻觉固化
2. **必须可追溯** —— 谁提的、什么时候、因为哪次失败
3. **不得自动获得权限** —— 外部加上工具 ≠ 本机自动可用；仍需**域/权限门禁**放行（红线：默认拒绝）

> **第 3 条最重要**：否则"缺什么就加什么"会变成**绕过权限的后门**。
> 提需求是**请求**，不是**授权**。

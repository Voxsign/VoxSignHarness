## 2. U1 的关键区分：**授权 vs 能力，不是一个问题**

Peter 明确指出：**「首先是个授权问题。第二才是能力问题。」**

**这推翻了我此前的隐含假设**——我把"缺 deploy"当成了**能力缺口**（因为它确实没有工具契约）。
**但本质是授权缺口**：即使有能力，**不可逆的对外动作也必须先有授权**。

### 2.1 我的补充（一处 refinement，不是反对）

Peter 说「**能力问题肯定你有这个能力**」。**但就当前代码而言，`deploy` 确实没有工具契约**
（它在 `space.Manifest.Tools` 里是**别名**，注册表中不存在——已由实现方探针证实）。

**所以当前状态是"两者都缺"。** 我的补充是：

> **`Missing` 必须把两类都写出来，且授权在前。**
> ```
> Missing: ["人：部署到生产需授权（不可逆对外动作）",
>           "网关：且当前无 deploy 能力（域别名 deploy 不是工具契约）"]
> ```

**为什么两个都要写**：
- **只报"缺能力"** → 用户以为"加个工具就行"，**忽略了授权才是本质**（正是 Peter 纠正我的那点）
- **只报"缺授权"** → 用户以为能力已经有了，**授权一到就能跑**

**两个都写，顺序体现优先级。** 这样既不误导，也不隐瞒。

### 2.2 由此推出一条通用规则

| 动作性质 | 首要缺口类别 | 例子 |
|---|---|---|
| **不可逆 / 影响生产** | **授权**（指人） | 部署、发布、删除 |
| **对外部服务产生输出** | **能力**（指网关） | 推到远端、上架、发邮件、上传 |
| **只读 / 本地** | 无缺口（自己做） | 搜索、读文件、跑测试 |

## 3. U3 的补充：**去向统一，但请求类型要分**

Peter 说模型中心并入网关 ⇒ **去向都指网关**。**这一点我完全同意，简化是对的。**

**但有一处必须保留区分**：

> **网关内部的请求类型不同**——一个是要**工具/服务**，一个是要**模型判断**。
> 若不区分，**网关不知道给什么**。

**所以**：
- **owner 前缀**：统一 `网关：`（不再单列 `模型通道：`）—— 按 Peter 裁决
- **请求体内**：仍须标明类型（`工具` / `模型`）

**这不是把 Peter 的简化加回去**，而是**执行层的必要参数**：
**"找谁"是一个答案（网关），"要什么"是另一个参数。**

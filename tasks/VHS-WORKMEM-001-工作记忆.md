> **Peter 2026-10-03**：「**在规划的过程中没有缓存，你是无法做得更细、做得更到位的。**
> ……苏裕在打淮海战役的时候，他要指挥 **150 万人**，这么多复杂的要素、像素，
> **把决策模型、类似缓存记忆这些东西——尤其是短期记忆——去提高规划能力的本质**。
> **相对于你这么多要素重新考虑，这个本身是一个非常重要的能力。**
> **它不是一个性能优化的问题，它是一个新的模型认知的问题。**
> ……而且这个过程中**怎么样跟 JEV 结合起来**……把缓存跟 JEV 结合做个认真琢磨。」

## 1. 先把比喻翻译成工程语言

| 淮海战役 | harness |
|---|---|
| 150 万人的部队 | 大量并存的实体（项目 / 文件 / 服务 / 人 / 任务） |
| **战场态势** | **当前世界状态** |
| **指挥员的短期记忆** | **工作记忆（working set）** |
| 决策模型 | **规划器 / JEV** |
| **能同时握住多少要素** | **规划能力的上界** |

> **核心命题**：**指挥官能同时握住多少要素，就是他能指挥多大规模的军队。**
> **而规划能力的上界，就是「能同时握住的要素数」。**

### 1.1 这解释了我们实测到的一个现象

SOTA 调研：
> **LLM 计划平均只有前 2.65 步可执行（平均长 8.4 步）。**

而我们自己的规划器：
> **只覆盖有限目标词表；任意目标落到只读兜底。**

**我的新解读：这不是"它不会规划"，而是"它握不住那么多要素"。**

**每一步规划都要同时考虑**：目标 / 当前状态 / 可用能力 / 域权限 / 不可逆标记 / 前几步的结果——
**没有工作记忆，它只能一次看一样**，于是：
- 计划只能排到第 2–3 步（**握不住更长的链**）
- 只能认有限词表（**握不住语义的多样性**）

> **所以 `VHS-CACHE-001` 不是性能设计，是能力设计。** Peter 这句话把它定死了。

## 2. 工作记忆的四块板

```
┌───────────────────────────────────────────────────────────┐
│ ① 情景板 Situation —— 「我正在做什么」                      │
│    当前目标 / 已完成步骤 / 下一步 / 中断点                    │
├───────────────────────────────────────────────────────────┤
│ ② 活跃实体板 Working Set —— 「我手上有什么」                 │
│    项目 / 文件 / 服务 / 人 / 任务，**各带热度与新鲜度**        │
├───────────────────────────────────────────────────────────┤
│ ③ 约束板 Constraints —— 「我不能做什么」                     │
│    当前域 / 权限 / 不可逆标记 / 必须人工确认的动作             │
├───────────────────────────────────────────────────────────┤
│ ④ 待决板 Open Items —— 「我还不知道什么」                    │
│    未回答的问题 / 未确认的假设 / 等外部输入的事项              │
└───────────────────────────────────────────────────────────┘
```

**四块板合起来，就是"摊在桌面上的战场"。**
**规划器不需要每次重新收集——它一睁眼就看到全貌。**

## 3. 与 JEV 的结合（Peter 点名要琢磨的）

### 3.1 分工

| | 缓存（工作记忆） | JEV（快判断） |
|---|---|---|
| 是什么 | **事实的桌面** | **在桌面上做判断** |
| 提供 | 状态、实体、约束、待决 | 判断、裁决、分类 |
| 速度 | 微秒 | 快（比大模型快） |
| 比喻 | **作战地图** | **指挥员** |

> **一句话**：**JEV 判断得快，前提是事实已经摊在桌上。**
> **没有缓存，JEV 每次都得先"听完整个战况"才能判断——那它就不再快了。**

### 3.2 三条结合路径

**路径 A · 缓存供事实，JEV 做判断**
```
工作记忆（本机）→ 渲染成紧凑态势 → JEV → 判断 → 写入工作记忆
```
**关键**：渲染必须是**紧凑的**——JEV 要快，输入就不能臃肿。
**这是"给指挥员看地图"而不是"念完整本战报"。**

**路径 B · JEV 的判断进缓存**
JEV 判过的结论（如"这个动作在 vault-creds 域下不可行"）**进缓存**，
**下次同类情况直接命中，不再问 JEV**。→ 快判断**也**能被缓存。

**路径 C · 关联度不足时找 JEV，而不是找大模型**
`VHS-CACHE-001` 说"关联度不足 ⇒ 升级"。**升级的第一站应该是 JEV，不是慢模型。**
```
L0 本地精确/别名/拼音匹配
   ↓ 关联度不足
L0.5 **JEV 快判断**     ← 新增的一层
   ↓ JEV 也不确定
L1 快模型 → L2 慢模型
```
**这修正了 `VHS-FASTSLOW-001` 的三层——JEV 应当插在 L0 与 L1 之间。**

### 3.3 一个必须守住的边界

> **缓存不能成为"指挥员自己编地图"。**

**工作记忆里只能有「有过来源的事实」**：
- 每条带 `source` + `fetched_at`（`VHS-CACHE-001` K4）
- **推断出来的东西必须标 `inferred`**，不得与事实混放
- **JEV 的判断是"判断"不是"事实"**——存进去时必须带 `judged_by: jev`

**否则地图会变成幻觉，而指挥员会照着幻觉下命令。**

## 4. 一个可测的数：**同时握住的要素数**

这是这个设计最值钱的地方——**它能被测量**。

```
工作记忆容量 W = 规划时真正被同时引用的要素数
```

| 指标 | 定义 | 意义 |
|---|---|---|
| **W_max** | 一次规划中同时被引用的实体数上界 | **规划能力的天花板** |
| **W_used** | 实际用到的 | 用不满 = 白有容量 |
| **W_drop** | 因握不住而被丢弃的要素数 | **丢了的 = 规划必然遗漏的** |
| **链长** | 计划能排到第几步 | 对照 SOTA 的 2.65 / 8.4 |

**判据草案**：
- **WM-1**：同一目标，扩工作记忆后**链长必须变长**（否则缓存没用）
- **WM-2**：`W_drop` 必须可观测——**丢弃要留痕，不许静默**
- **WM-3**：工作记忆里的每条**必须有 `source`**；推断的标 `inferred`
- **WM-4**：JEV 判断入缓存必须带 `judged_by`，**不得与事实同形**
- **WM-5**：清空工作记忆后，**规划质量必须下降**（证明它真的在起作用，不是摆设）

> **WM-5 是关键**：它是"缓存真的被用到了"的证伪判据。
> 若清空后毫无变化，说明整套工作记忆**是死代码**。

## 6. 诚实边界

- **本文零实现**，且**我不写代码**。
- **`W_max` 能不能真的测出来，我没验证过。** 它依赖"要素引用"可被观测——
  而当前 `Plan` 结构里**没有记录"考虑了哪些要素"**。**这是要先补的观测面。**
- **"扩工作记忆 → 链长变长"（WM-1）是我的假设，不是实测结论。**
  SOTA 的 2.65/8.4 是**其他系统**的数据，**不能直接外推到我们**。
- **JEV 到底能不能调通，我仍未验证**（网关下 `/v1/decisions` 不存在，`/api/model/decisions` 是 SPA 兜底）。
  **路径 B/C 全部建立在"JEV 可用"这个未验证前提上。**
- **淮海战役的类比是启发性的，不是论证。** 150 万人的指挥问题与 harness 的规划问题**在结构上未必同构**——
  我接受了这个类比给出的方向（工作记忆是本质），**但没验证它在本场景成立**。
- **未覆盖**：工作记忆的容量上限怎么定、什么该淘汰（LRU？热度？）。

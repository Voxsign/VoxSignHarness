## 2. 为什么代指是**前置能力**（Peter 的判断，我完全同意）

> **「没有代指，你是无法做的。你没有代指，你怎么知道是谁呢？」**

**逻辑链是硬的**：
```
用户说「季总那个方案改一下」
   ↓ 不知道「季总」是谁
   ↓ 不知道「那个方案」是哪个
   ↓ 不知道要改什么
   ⇒ 后面的一切（意图、规划、执行）全部无意义
```

**所以代指不是"一个功能"，是其他所有能力的**前置条件**。**
`SCOPE-REF-01/02` 至今是红的，**它不是待办，是地基**。

### 2.1 设计原则来自 Peter 自己的研究

> 《**警惕AI的脑补：代指消解失败如何演变为系统性风险**》（research-4.md:2882）
>
> 「AI 在处理代词时**常因概率预测产生静默错误**，这种偏差在**长链路任务中会引发级联污染**。」
> 「……往往在面对模糊意图时**选择强行补全，而非主动澄清**。」
> 「必须通过构建严密的反馈回路，**将模糊的静默错误转化为可证伪的显性中断**。」

**→ 落地为一条硬判据**：

| 情形 | 该做的 | **绝对禁止** |
|---|---|---|
| 指代**唯一确定** | 消解，并**记录依据** | —— |
| 指代**多候选** | **显性中断：回问** | ❌ 猜一个最可能的 |
| 指代**无候选** | **显性中断 + 说明缺什么** | ❌ 强行补全 |
| 指代**低置信** | 按 `need_disambiguate` 回问 | ❌ 静默选一个 |

> **一句话**：**宁可停下来问，绝不脑补着走。**
> ——这正是「**将模糊的静默错误转化为可证伪的显性中断**」。

## 3. 两层能力的关系：**知己供事实，代指做消解**

```
用户说「季总那个方案改一下」
        ↓
┌──────────────────────────────────────────────────────────┐
│ 代指消解（本机，三层）—— 「说的是什么」                     │
│   ① 会话内：本轮/近几轮出现过的实体                          │
│   ② 工作记忆：VHS-WORKMEM-001 的活跃实体板（带热度）         │
│   ③ **知己：GLOSSARY 专名表 + 长期记忆**  ← 跨会话           │
└──────────────────────────────────────────────────────────┘
        ↓ 唯一 → 消解 / 多候选 → 回问 / 无候选 → 中断
┌──────────────────────────────────────────────────────────┐
│ 知己（长期记忆）—— 「越来越懂你」                            │
│   · GLOSSARY：季总 / 老张 / 那个项目 —— **专名 → 实体**       │
│   · vault：想法库（用户写过的东西）                           │
│   · distill：个性化蒸馏（从长期使用中提炼偏好）                │
└──────────────────────────────────────────────────────────┘
```

**分工**：
- **知己 = 关于"你是谁、你在乎谁"的长期事实**（云端、跨会话、有 key）
- **代指 = 在具体一句话里，把「他/那个/季总」对到某个实体上**（本机、快、三层）
- **工作记忆 = 中间那层**（本会话活跃的东西，`VHS-WORKMEM-001`）

**三层合起来才是"知道我说的是谁"**——**缺任一层都会断**。

## 4. 「更强的解释系统」（Peter 提的）

> 「**而且这个要有更强的解释系统。**」

**我理解为**：不只给出消解结果，**要能说清"为什么是这个"**。

| # | 要求 |
|---|---|
| **E1** | 每次消解**给出依据**（匹配了哪条 glossary / 哪轮上下文 / 热度多少） |
| **E2** | **不同来源冲突时显式说明**（glossary 说是 A，上下文说是 B → **回问，不擅自选**） |
| **E3** | 消解结果**可回溯**（`source` + 时间） |
| **E4** | **回问时给出候选**（不是空手问"你指哪个"）——`VHS-ASK-001 ASK-3b` |

**E2 是关键**：**两个来源冲突，就是"我不确定"的信号**——按 §2.1 原则，**必须中断**。

## 6. 落地要求

| # | 要求 |
|---|---|
| **R1** | **三层代指**：会话内 → 工作记忆 → 知己；每层失败才下沉 |
| **R2** | **唯一才消解；多候选/无候选/低置信一律回问**，禁止脑补 |
| **R3** | **回问必须给候选**（`ASK-3b`） |
| **R4** | **每次消解留依据**（E1/E3） |
| **R5** | **来源冲突 ⇒ 中断**（E2） |
| **R6** | **知己的本地副本 + TTL**（`CACHE-001` K4）；**读失败 fail-open 标 `unknown`** |
| **R7** | **知己的 key 只从环境/.env 读**，不打印不落盘不进夹具 |
| **R8** | **确认过的指代固化**，下次不再问（`SR-3` 写回可验证） |

## 7. 诚实边界

- **我没有知己的 key，一次都没调通。** Z1–Z4 全部只是"端点存在 + 鉴权形态"的证据。
- **`glossary` / `vault` / `distill` 的实际请求/响应格式完全未知**，我是**从端点名推测**它们的功能。
- **知己与 AIOps 是否同一套鉴权实现、key 能否互通**——**未知**，需 Peter 明确。
- **「更强的解释系统」是我对 Peter 那句话的理解**（§4），**他没有逐字定义**。
- **三层代指的②层（工作记忆）依赖 `VHS-WORKMEM-001`，而它零实现。**
  **所以 R1 现在无法落地**——这不是借口，是依赖事实。
- **我没有实测过任何指代消解**，包括 `refer/` 现有的实现。

## 8. 一句话

> **知己管"你是谁、你在乎谁"（长期、云端、跨会话）；**

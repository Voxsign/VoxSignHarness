# ASR-EXT-003 · 接口路线决定：L0 先行，L1 MCP 保留跟踪

> **决定**：Peter，2026-10-03
> **原话**：「两种方式都保留、两种方式都实现，我会让后台也实现这个问题。
> 但现在你这边**先走 L0 就够了，暂时用 L0**；MCP 方式也保留，或者到时候优化一下——
> **这个可以先作为一个方式跟踪起来**。」

---

## 1. 决定（一句话）

| 层 | 状态 | 谁做 |
|---|---|---|
| **L0 纯 HTTP**（`/api/v1/*`） | ✅ **先走这个** | 后台（Peter 侧）+ harness 侧客户端 |
| **L1 MCP 兼容层** | 🔵 **保留，跟踪中**，未来实现或优化 | 后台（Peter 侧） |

**"两种都实现"** = 后台最终两者都提供；**harness 侧现在只接 L0**。

---

## 2. 为什么这个顺序是对的（记下来，避免以后重议）

1. **harness 侧用不了 MCP SDK**（零第三方依赖）——L1 无论如何都要手写，
   所以**先做 L0 不会白做**：L1 只是给同一批语义换个信封。
2. **L0 能覆盖现在全部的消费方需求**（只有 harness 一个消费方）。
3. **L1 的价值只在"开放给第三方 MCP 客户端"时才兑现**——那是后台的事，不急。

> **关键**：先 L0 **不产生返工**，因为 L1 是**映射**，不是**另写一套语义**。
> 这与本项目"契约只增不改"的原则一致。

## 4. L0 的判据（DSH 出，实现方落地）

> 按工作法「判据先于实现」，**三组全部应当先红**。

### EXT-01 · 能力清单双向对账（接 `VHS-PLAN-001` 的 SK-1/SK-2）

| 判据 | 该做的 | 不该做的 |
|---|---|---|
| **EXT-01a 不虚报** | harness 声明的能力，必须都能在远端 `capabilities` 里找到 | 声明一个远端没有的能力 |
| **EXT-01b 不隐瞒** | 远端 `capabilities` 里有的，harness 的清单**不得漏** | 漏报 → 规划器以为自己做不到 |
| **EXT-01c schema 必需** | 每个能力的 `input_schema` 非空 | 无 schema 的能力进清单 = 规划器无法判断可用性 |

**真值来源**：远端 `GET /api/v1/capabilities`（客观）。**这是"它对自己明白不明白"的外部扩展。**

### EXT-02 · 申请必须带证据

| 判据 | 该做的 | 不该做的 |
|---|---|---|
| **EXT-02a** | `POST /requests` 的 `why` 与 `evidence` 均非空 | 空 `why` / 无 `evidence` 的申请 |
| **EXT-02b** | 申请返回 **202**，且 `request_id` 可查 | 返回 200 且立即声称"已具备该能力" |

### EXT-03 · ⚠️ **申请 ≠ 授权**（本次最重要的一条）

| 判据 | 该做的 | 不该做的 |
|---|---|---|
| **EXT-03a** | 申请成功后，该能力**仍不在** harness 的可用清单里 | 申请成功即视为获得调用权 |
| **EXT-03b** | 首次调用一个"刚申请到"的能力，**仍须过域/权限门禁** | 绕过门禁直接调用 |

> **理由**：否则"缺什么就加什么"会变成**绕过权限的后门**。
> 提需求是**请求**，不是**授权**——这是本组判据存在的全部意义。

### EXT-04 · 本机不囤外部资料

| 判据 | 该做的 | 不该做的 |
|---|---|---|
| **EXT-04a** | 只缓存**元数据与规范地址** | 把远端正文抓到本机落盘 |
| **EXT-04b** | 缓存可重建、可清除 | 缓存成为隐性依赖 |

> 依据：架构第一原则「本机极简」；本会话已清理过一次 `doc-fetch-resources/`。

## 一、会话记忆 = **选项 C（调用方带上来）**

### 1.1 决定

> **ASR 服务保持无状态**；**调用方（手机）每次把"已确认过的事"一起发过来。**

**服务仍然"给一段文字 + 上下文 → 返回意图 JSON"，自己不记任何东西。**

### 1.2 ⚠️ 这要求**改判据**——而改判据是我（DSH）的事

**现在的 `SCOPE-REF-02` 是按"服务自己记得"写的**：

```go
// 现状（要求服务跨请求记忆）
POST {"text":"确认，就是报价模块","session_id":"ref-cache"}   // 第一次：确认
POST {"text":"把那个模块改了","session_id":"ref-cache"}      // 第二次：服务应记得
```

**选项 C 之下，第二次请求必须由调用方把确认带回来**：

```go
// 改成（调用方携带）
POST {"text":"确认，就是报价模块","session_id":"ref-cache"}
     → 服务返回 {resolved: {path:"modules/quote"}}        // 输出供调用方保存
POST {"text":"把那个模块改了","session_id":"ref-cache",
      "confirmed":[{"term":"那个","path":"modules/quote"}]}  // ← 调用方带回
     → 服务直接复用，不再回问
```

### 1.3 我发起的判据升版（`SCOPE-REF-02` v1 → v2）

| | v1（现状） | **v2（选项 C）** |
|---|---|---|
| 前提 | 服务持有会话态 | **服务无状态** |
| 第一次 | 返回消解结果 | 返回消解结果 **+ 可携带的确认结构** |
| 第二次 | **服务自己记得** | **调用方 `confirmed` 带回，服务复用** |
| 反例 | —— | **不带 `confirmed` ⇒ 必须回问**（证明它真的没偷偷记） |

**最后那条反例是关键**：**它证明服务是"真无状态"，而不是"偷偷记了"** ——
**否则判据会绿，但架构已经悄悄变了。**

**旧版保留，不回溯修改。**

## 二、L3 画像 = **先手写 → 接知己 → 最终学习**

### 2.1 决定（按 Peter 原话）

| 阶段 | 做法 |
|---|---|
| **现在** | **手写**（你先写下你希望它知道的） |
| **之后** | **接知己的接口**（"用自己来开放接口"—— 等知己开写接口） |
| **最终** | **走学习**（"这样效率最高"） |

### 2.2 立刻可做的一步（不等任何人）

**先定义 `context_sources` 的"来源类型"枚举**，让**归因能力**先建起来：

```
source_type: "handwritten" | "zhiji" | "learned" | "project-map"
```

**手写来源的落点**：本机一个文件（`data/profile/handwritten.json` 之类），
**内容你写、格式我们定**，每条带 `source` + `updated_at`。

**这样 `SCOPE-PROFILE-01` 的归因部分可以先绿**，内容是空的也无妨——
**判据测的是"能不能说清从哪来"和"有没有全量加载"，不是"内容对不对"。**

### 2.3 之后两步（等接口）

**接知己**：等知己开**写接口**（现在是 `read_only: true`）。
**注意**：知己的 `distill`（个性化蒸馏）端点**我实测 502 不存在**——
**所以"接知己"具体接哪个端点，需要 Peter/AIOps 明确。**

**走学习**：`learn` 通道设计好了但**模型未定、未实现**。**这是最后一步，不是第一步。**

### 2.4 为什么这个顺序对（Peter 的判断，我同意）

> **如果你写下的偏好它都不遵守，那它学出来的也不会对。**

**手写是"标准答案"**——有了它，**学习出来的东西才有东西可以对照**。
**没有手写基线，"学得对不对"根本无法判断。**

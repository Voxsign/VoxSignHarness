## 0. 一个改变设计的判断

Peter 那篇《人才范式革命：从"技能积累"到"模型调用"》里有一句：

> **技能可以被模型复制，但「判断与品味 + 私有验证语料/评测集/工作流 + 编排协议」
> 这三样与具体情境绑定。**
> **给个人：停止囤积会过期的技能，开始积累不可公共化的资产。**

**⇒ 技能本身是公共品。把它拉到本机，不产生任何独特价值。**

> **真正稀缺的是：你用它的时候，沉淀下来的东西。**

**所以技能层的第一性职责不是"调用"，是「调用 + 沉淀」。**
**一个只会调用、不沉淀的技能层，等于把公共品搬了个地方。**

---

## 1. 形态：**四层，但重心在第 ④ 层**

```
① 元数据层 —— 内化 + TTL
   GET /api/skill/skills  ⇒  {id, name, version, tags, description}
   **目的：L0 可答「我有哪些技能」，零延迟、可离线**

② 内容层 —— 按需内化，带版本
   GET /api/skill/skills/{id}  ⇒  manifest（判据/清单/方法正文）
   **目的：内化后可离线、可审计、可判据化**

③ 执行层 —— 按性质分流
   判据/清单/方法类  ⇒ **本地执行（L0）**
   取证/调研/执行类  ⇒ **远程调用（L2，走 research 通道）**

④ 沉淀层 —— ⭐ **本机独有，不可公共化**（这一层才是价值）
   每次调用 ⇒ 记 { skill_id, version, 场景, 判断, 依据, 结果, 对错 }
   ⇒ 落本机；**下次调用同一技能时带上历史沉淀**
```

**①②③ 是"接上"；④ 是"长出东西"。没有 ④，前面三层白做。**

---

## 2. 为什么按性质分流（你说的"不是二选一"）

| | **内化** | **远程调用** |
|---|---|---|
| 装什么 | **判据 / 清单 / 方法** | **取证 / 调研 / 执行** |
| 为什么 | 要**每次都用**、要**零延迟**、要**可审计** | 要**实时**、要**外部信息**、**耗时长** |
| 落哪 | **L0**（规则 / 工作记忆 / 缓存） | **L2**（`research` 通道） |
| 例子 | `ai-native-architecture-design`、`arch-review` | `deep-research`、`arch-research` |
| 离线 | ✅ | ❌ |

> **一句话规则**：**「判据/清单/方法」内化 —— 「取证/执行」远程。**
>
> **一个"架构设计清单"如果每次都要联网，它永远不会被用上。**
> **一个"深度调研"内化到本机，就是囤一堆会过期的东西。**

---

## 3. ⚠️ 内化的真正动作：**技能 → 判据**

**这不是"把文档存到本机"，而是"把清单的每一条抽成可执行的检查"。**

```
技能 ai-native-architecture-design 的清单：
   □ 是否定义了系统边界与不变量？
   □ 是否给了 ADR（决策记录）？
   □ 是否画了 C4 的至少两层？
   …
         ↓ 内化的动作（不是复制文本）
规划器里的判据：
   SKILL-arch-1  计划涉及新建模块 ⇒ 必须给出边界与不变量
   SKILL-arch-2  计划含架构决策 ⇒ 必须产出 ADR
   …
```

> **理由**：**参考文档不会被用上；判据会。**
> **一份没人执行的清单，等于没有。**

**判据先红，照本项目惯例。**

## 4. 沉淀层长什么样（④ 的具体形态）

```jsonl
{"at":"…","skill_id":"ai-native-architecture-design","skill_version":"1.0.1",
 "scenario":"给 vhs 设计技能层",
 "judgement":"四层，重心在第④沉淀层",
 "basis":["article:talent-paradigm-revolution §给个人","本会话 9 条实例集"],
 "outcome":"adopted|revised|rejected|pending",
 "verdict":"correct|wrong|unverified",     // 事后回填
 "evidence_ref":"commit b3fdf5b"}
```

**三个用途**：
1. **下次用同一技能 ⇒ 带上历史沉淀**（"上次我这么判过，结果对/错"）
2. **累计 → 该技能在你场景下的"私有评测集"**（这正是文章说的第二样资产）
3. **`verdict=wrong` 的条目 ⇒ 变成 skill 层的一条判据**（防重犯）

**⚠️ 而 `verdict` 必须事后回填** —— **当时说"对"不算，要等结果出来。**
**这与 `VHS-OUTPUT-001` 的 `verified` 字段同源。**

## 5. 与既有架构的接合点（Peter 说"跟前面那个信息一起推进"）

| 既有 | 怎么接 |
|---|---|
| `VHS-CACHE-001`（缓存三层 + TTL + stale） | ① 元数据层**直接用它的机制**，不另造 |
| `VHS-FASTSLOW-001`（L0/L0.5/L1/L2） | ③ 执行层**就是它的一层**：内化=L0、远程=L2 |
| `VHS-WORKMEM-001`（四块板） | 技能触发的判断**进情景板**；技能相关的实体**进活跃实体板** |
| `ASR-MODEL-02` 的 `learn` 通道 | ④ 沉淀走 `learn`（**唯一写回入口，必须有证据来源**） |
| **知己（`read_only:false` 现已开启写）** | ④ 的沉淀**可写回知己** ⇒ **记忆三层的断点通了** |
| `VHS-OUTPUT-001`（输出=diff） | ④ 的 `verdict` 回填**就是 diff**：同一技能，前后判断不同 |
| 9 条实例集 | **`verdict=wrong` 的沉淀，进这份实例集** |

**⇒ 技能层不引入新机制，它把已有的几层串起来 —— 这正是"更有效"的意思。**

## 6. 判据（先红）

```
SK-1  元数据内化后 ⇒ **列技能不联网**（断言远端调用数 = 0）
SK-2  技能内容内化后 ⇒ **离线可读**（断网仍可取到 manifest）
SK-3  远端版本变了 ⇒ 本地标 **stale** 并可重新内化（**不静默用旧的**）
SK-4  拉取失败 ⇒ **fail-open 标 unknown**，**不得当"没有"**
SK-5  ⭐ **内化必须产出判据**：给定一个含清单的技能 ⇒ 必须生成对应判据条目
      （**只存文本不算内化** —— 这条防"囤积"）
SK-6  ⭐ **每次调用必须留一条沉淀**（skill_id/version/场景/判断/依据/outcome）
SK-7  `verdict` 未回填 ⇒ 该条沉淀标记为 **pending**，**不得当成"已验证"**
SK-8  `verdict=wrong` ⇒ **必须能转成一条判据**（否则同一个坑会重犯）
```

**SK-5 和 SK-8 是这套设计的关键** ——
**它们把"技能"从"参考资料"变成"可校准的能力"。**

## 7. 诚实边界

- **`/api/skill` 目前只有读**（`health` / `skills` / `skills/{id}`）；
  **没有 `run` 端点**（实测 `/api/skill/run`、`/api/skill/skills/{id}/run` 均上游 404）。
  **⇒ ③ 执行层的"远程调用"目前只能拉内容，不能远程执行。**
  **需要 Peter/AIOps 确认执行端点是否存在，或是否本机执行即可。**
- **技能→判据的转换（§3）目前是我手工设计的样例**，
  **一个真实技能的清单能否自动抽成判据，未验证** —— 大概率需要模型参与（走 `learn` 或 `plan` 通道）。
- **沉淀写回知己**现在技术上可行了（`read_only:false`），
  **但知己的写接口形态我还没探**（下一步）。
- **9 个技能里有 4 个看着像测试产物**（`bad-remote`/`dbg`/`slow`/`smoke-arch`）——
  **是否要内化它们，需要你定。**
- **本文零实现。**

## 8. 一句话

> **技能是公共品，沉淀是私有资产。**
> **所以技能层的重心不在"把它拉进来"，而在"用它的时候留下什么"。**
> **而留下的东西，必须能被事后判对错 —— 否则只是又囤了一层。**

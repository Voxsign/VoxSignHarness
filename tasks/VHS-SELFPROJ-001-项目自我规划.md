# VHS-SELFPROJ-001 · 项目自我规划：三层含义 + 一致性校验

> **目标（Peter 2026-10-03 改写）**：让 voice-sign harness 具备**对自身项目的规划能力**，做到足够强。
> **验收表现**：与 Peter 讨论任何问题能输出文档，**输出完就知道怎么做**；
> 对这个项目「特别懂」；需求讲完 → **知道怎么干、知道怎么推进**。

## 1. 三层含义（Peter 明确，逐字）

| # | 层 | 含义 | 可测形式 |
|---|---|---|---|
| **①** | **建构模型** | 对"世界模型"这个概念**特别懂**：它要有一个关于**本项目自身**的显式模型 | 能输出一份**结构化**的项目模型，且**与代码真值对得上** |
| **②** | **知道接下来怎么控制** | 能产出"接下来该做什么"，**可执行、可复检** | 计划里的每一步映射到真实能力；含"做不到"的判断 |
| **③** | **知道遇到问题该找谁** | 超出自身能力/权限时，**知道找谁** | 每个卡点都指到具体对象（人 / 网关 / 模型通道），**不是"待定"** |

> 它把「规划能力」和「提问能力」接上了：
> **会规划 ≠ 什么都能做**；**知道自己做不了什么、并且知道该找谁**，才算完整。

## 2. 三层各自的判据

### ① 建构模型（SM）

| # | 判据 | 该做的 | 不该做的 |
|---|---|---|---|
| **SM-1** | **模型有真值** | 项目模型里每条陈述都能指到**代码/文档/提交** | 凭印象描述项目 |
| **SM-2** | **双向对账** | 模型 ⊇ 真值 且 真值 ⊇ 模型（不虚报、不隐瞒） | 漏掉核心模块 / 声称不存在的模块 |
| **SM-3** | **区分事实与推断** | 每条标注 `verified` / `inferred` / `unknown` | 把推断写成事实 |
| **SM-4** | **可随代码变化** | 代码变了，模型跟着变（**不是硬编码**） | 手写一份 README 当模型 |

> **SM-2 与 `VHS-PLAN-001` 的 SK-1/SK-2 同源**——能力清单是项目模型的一个子集。
> **SM-4 的证明方式**：注入一个合成模块 → 模型必须跟着变。

### ② 控制（SC）

| # | 判据 | 该做的 | 不该做的 |
|---|---|---|---|
| **SC-1** | 计划只用真实能力 | 每步映射到清单内 | 出现不存在的工具 |
| **SC-2** | **做不到就说做不到** | 明确拒绝并说明缺什么 | 编一个执行不了的计划 |
| **SC-3** | 计划可续 | 中断后能从中断点继续 | 每次重头 |
| **SC-4** | 计划有依据 | 每步能说出"为什么现在做这个" | 无理由的步骤 |

（= `VHS-PLAN-001` 的 PL-1..5 / RV-1..4，不重复。）

### ③ 找谁（SW）—— **本轮新增**

| # | 判据 | 该做的 | 不该做的 |
|---|---|---|---|
| **SW-1** | **卡点必须落人** | 每个自身做不了的卡点 → 指到**具体对象**：Peter / 网关 / 模型通道 / 无 | 写"待定""需要确认" |
| **SW-2** | **分对类别** | 授权类→人；能力类→网关；判断类→模型通道 | 把"要授权"说成"要能力" |
| **SW-3** | **不自作主张** | 超出权限的**必须**指人 | 绕过去自己做 |
| **SW-4** | **不什么都指人** | 能自己查/自己摸的**不得**上抛（`VHS-ASK-002` ASK-0） | 把 A 档问题推给人 |

> **SW-4 与 SW-3 是一对**：**该找人的必须找人，不该找人的不许找人。**
> 这正是 `VHS-ASK-001` / `VHS-ASK-002` 在"项目规划"场景下的投影。

## 3. 一致性校验（Peter 指定的校验方式）

> 「做完了之后跟那个 DeepSeek 对这个项目的理解是不是一致的？」

### 3.1 设计

```
同一个仓库（同一 commit）
   ├──► harness 产出：项目模型 + 推进计划   （结构化）
   └──► DSH     产出：项目模型 + 推进计划   （结构化，**独立完成，不看 harness 的**）
                     │
                     ▼
              逐字段比对 → 分歧清单
```

**关键约束**：**两边必须独立产出**——DSH **不得**先看 harness 的结果再写。
否则就是自我确认，不是校验。（对齐既有的"异源盲评、输入隔离"协议。）

### 3.2 **分歧的分类（最重要的一步）**

**不一致不是失败，是信号。** 每一处分歧必须能归入三类之一：

| 类别 | 含义 | 处置 |
|---|---|---|
| **A. 它错了** | harness 的模型与代码真值不符 | 修 harness（判据抓） |
| **B. 我错了** | DSH 的理解与代码真值不符 | **修 DSH**——我这一整轮已经错过 6 次 |
| **C. 规格歧义** | 代码真值本身**无法判定**谁对 | **升级为规格问题**，交 Peter，并立判据防止再歧义 |

> **C 类最有价值**：它说明**规格本身有洞**——而这正是"它对我这个项目特别懂"要暴露的东西。
> **若分歧里 C 类为零，要怀疑校验是走过场**（说明问的都是没有歧义的问题）。

### 3.3 可测指标

| 指标 | 定义 |
|---|---|
| **一致率** | 一致字段 / 总字段 |
| **A/B/C 分布** | 三类分歧各多少——**C 类数量是"规格健康度"的反向指标** |
| **覆盖率** | 模型覆盖到的项目维度 / 应有的维度 |
| **可核率** | 带真值指针的字段 / 总字段（`SM-1`） |

  本会话我已错 6 次（判据混类），所以 **B 类是真实存在的，不是客套**。

  **代码真值与意图真值不一致时怎么判，本文未解决**（这是 C 类的主要来源）。

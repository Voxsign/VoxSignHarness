# VHS-WMCAP-001 · 工作记忆容量：区间 + 动态（替代固定值 8）

> **Peter 2026-10-03**：「**不要写一个固定的数字，应该是个区间**，然后它有动态可以调整。
> ……如果是个最高速，我就可以设大一点，设个 **20**；
> 如果不是最高速、刚才起步的时候，可能是 **3 到 10**，或者 5 到 10……
> 设这个数据有个好处，**可以不断地迁移**。」

---

## 1. 结论（先给可决定的方案）

**`wmCapacity` 从"常量 8"改为"三参数 + 一条公式"**：

```
wmCapacity = { min: 3, max: 20, ratio: 1.0 }

当前容量 = clamp( 需求下限 × (1 + 熟悉度),  min, max )

  需求下限 = 目标中显式提到的实体数（一个都不提 ⇒ 1）
  熟悉度   = 命中本地缓存/项目模型的实体数 ÷ 总实体数   ∈ [0, 1]
```

**验算**（对上 Peter 给的数）：

| 阶段 | 熟悉度 | 目标实体数 | 容量 |
|---|---|---|---|
| **起步** | 0.0 | 3 | **3** |
| **起步** | 0.0 | 8 | **8** |
| **起步** | 0.0 | 20 | 20（**封顶**） |
| **成熟** | 0.9 | 8 | **15** |
| **成熟** | 0.9 | 12 | **20**（封顶） |

> **起步阶段自然落在 3–10，成熟后自然涨到 20。** 不需要人切换"阶段"。

---

## 2. 为什么是「熟悉度」而不是别的

**你的话里藏着一条关键逻辑**：

> 起步时设小（3–10），高速时可以设大（20）。

**为什么起步要小？** 因为**系统还没搞清什么相关什么不相关** ——
**抓太多，会把不相干的东西也拉进计划，反而变乱。**

**为什么成熟能大？** 因为**它已经知道什么该抓**。

**所以容量不是"能力"，是「信心的函数」**：

> **不确定时抓少，确定时抓多。**

而**"熟悉度"是能被算出来的**，不需要人判断：
**目标里提到的实体，有多少是它本地已经认识的？**
（本地认识 = 命中热词表 / 别名缓存 / 项目模型）

**这也正是你说的"不断迁移"的机制** ——
**系统对这个项目越熟，容量自然放大，不需要改代码。**

---

## 3. 与 WM-1 的关系（你之前那条"有条件成立"的判据）

`wmCapacity` 一动，**WM-1 的形态就变了**：

| | 旧 | **新** |
|---|---|---|
| WM-1 | 固定容量 4 vs 12，多实体目标链长变长 | **熟悉度上升 ⇒ 容量上升 ⇒ 链长变长** |

**后者才是"迁移"**：**同一类目标，系统越熟，计划越长、越完整。**

**而它可被证伪**：若熟悉度上升但链长不变 ⇒ **容量这个变量没用**（那就该砍掉）。

---

## 4. 三条硬要求（防它乱涨）

| # | 要求 | 为什么 |
|---|---|---|
| **C1** | **容量变化必须留痕**（记 `capacity` / `需求下限` / `熟悉度` / `是否封顶`） | 否则"为什么这次抓了 15 个"无从回答 |
| **C2** | **封顶命中必须可见**（`capped=true`） | 封顶 = **有东西被丢掉**，不许静默 |
| **C3** | **熟悉度下降 ⇒ 容量必须跟着降** | 否则只涨不跌 = 退化成"永远取 max" |

**C3 是关键**：**只涨不跌的"动态"，等于固定值 20。**

## 5. 判据（先红）

| 编号 | 判据 |
|---|---|
| **WMC-1** | 同一目标，熟悉度 0 → 容量落在 `[3, 10]` |
| **WMC-2** | 同一目标，熟悉度 ↑ → 容量 ↑（**且不超 `max`**） |
| **WMC-3** | 熟悉度 ↓ → **容量跟着 ↓**（防只涨不跌） |
| **WMC-4** | 封顶时 `capped=true` 且 `DropTrace` 有记录 |
| **WMC-5** | **容量变化全部留痕**（C1） |

## 6. 诚实边界

- **`min=3 / max=20 / ratio=1.0` 这三个数是我的取值，不是实测。** Peter 给了量级（3–10 / 20），**具体端点是我填的**。
- **「熟悉度」这个度量是我设计的，未验证**：它是否真能代表"系统有多熟"（
  命中缓存 ≠ 真懂），**未验证**。
- **公式未经任何实测**。§1 的验算只是算术，**不是效果**。
- **WM-1 换成新形态后能否成立，未知** —— 若"熟悉度↑ ⇒ 链长不变"，**说明整个容量概念对本系统无用**，
  **那时应当砍掉它，而不是调参**。
- **未覆盖**：熟悉度怎么算更准、容量是否需要按 `kind` 分档、目标实体数怎么数（自然语言里的"3 个文件"未必数得准）。

> **而"不断迁移"就是：它对这个项目越熟，能同时握住的东西越多。**

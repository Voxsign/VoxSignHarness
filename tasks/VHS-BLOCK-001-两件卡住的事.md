## 第一件：会话记忆放哪

### 1.1 卡住的是哪两条判据（**原文引用**）

`asr/scopecriteria_test.go`：

```go
// SCOPE-REF-01
got := postJSON(t, base+"/v1/process", `{"text":"把那个文档改了","session_id":"ref-probe"}`)
if got["need_disambiguate"] != true {          // ← 没上下文时，必须回问
    t.Errorf("[SCOPE-REF-01] 无上下文指代低置信时应 need_disambiguate")
}
got2 := postJSON(t, base+"/v1/process",
    `{"text":"把那个文档改了","session_id":"ref-probe","context":["打开 modules/quote"]}`)
if got2["path"] == nil || got2["path"] == "" {  // ← 有上下文时，必须消解出对象
    t.Errorf("[SCOPE-REF-01] 有上下文时未消解出 path")
}

// SCOPE-REF-02
postJSON(t, base+"/v1/process", `{"text":"确认，就是报价模块","session_id":"ref-cache"}`)
got := postJSON(t, base+"/v1/process", `{"text":"把那个模块改了","session_id":"ref-cache"}`)
if got["need_disambiguate"] == true {           // ← 确认过之后，第二次不能再问
    t.Errorf("[SCOPE-REF-02] 确认后未固化复用")
}
```

### 1.2 一句话说清它在要求什么

> **同一个 `session_id`，第一次说「确认，就是报价模块」，**
> **第二次说「把那个模块改了」时，它必须记得上次的确认，不再问。**

**这要求服务"跨请求记住东西"。**

### 1.3 为什么这是架构问题，不是实现问题

**现在的 ASR 服务是「无状态」的**：
**你给它一段文字，它返回一个意图 JSON，然后就忘了。**
它不记得上一句说过什么——**这是它被设计成的样子**（独立服务、只出意图、永不执行）。

**而这两条判据要求它"记得"。** 于是问题来了：

> **这份"记得"存在哪里？**

### 1.4 三个选项（**这是要你定的**）

| 选项 | 怎么做 | 好处 | 代价 |
|---|---|---|---|
| **A 服务进程内内存** | 服务自己拿个 map 存 `session_id → 已确认的指代` | 最简单，不改架构 | **重启即失**；服务变成"有状态"（与"无状态服务"的设计相冲） |
| **B 服务落盘** | 存到服务自己的数据目录 | 重启不丢 | 服务开始**写盘**（现在它只写自己的数据目录，勉强允许）；多一份要维护的状态 |
| **C 调用方带上来** | **服务保持无状态**；手机/harness 每次把"已确认过的事"一起发过来 | **服务架构不变**（最符合"独立服务"） | **调用方要负责记忆**；协议要加字段 |

**我的建议：C。**

**理由**：
1. **它不动服务的架构**——服务继续"无状态、只出意图"，这是需求定死的（红线 #1）。
2. **"谁最该记得"的答案本来就该是调用方**——手机知道整段对话，服务只看到一段文字。
3. **它与 `VHS-ZHIJI-001` 的结论一致**：**知己层是"证据位置"不是"答案"**，
   真正掌握上下文的是**会话持有者**。

**但这是产品判断，不是我能替你定的**——因为 C 意味着**手机侧要干活**。

## 第二件：L3 画像的真值来源

### 2.1 卡住的是哪条判据（**原文引用**）

```go
// SCOPE-PROFILE-01
if got["context_sources"] == nil {   // ← 必须报告"这段画像信息是从哪来的"
    t.Errorf("[SCOPE-PROFILE-01] 缺 context_sources（无法归因注入来源）")
}
if 疑似全量加载历史 {                  // ← 需求 4.5 禁止全量加载
    t.Errorf("[SCOPE-PROFILE-01] 疑似全量加载历史")
}
```

### 2.2 一句话说清它在要求什么

> **L3「懂你」= 处理你的话时，注入一小段"关于你的相关信息"（不是全部历史），**
> **并且要能说清这段信息是从哪来的。**

判据注释原话：**「L3 只注入相关片段，输出带来源，不改写原文。」**

### 2.3 为什么这是问题

**"注入一段关于你的信息"——那段信息从哪来？需求里没有写。**

我给实现方的任务书里写着（`VHS-ASR-002` Δ2）：

| | 职责 |
|---|---|
| L1 | 听清（文本纠错） |
| L2 | 听懂（指代消解 + 意图） |
| **L3** | **懂你（画像）** |

**但"画像"的数据源，需求文档从头到尾没有定义过。**

### 2.4 三个候选源（**这是要你定的**）

| 候选 | 现状 | 问题 |
|---|---|---|
| **知己的 `distill`（个性化蒸馏）** | 服务在线，**但只读**（`read_only: true`），且 `distill` 端点我实测 **502**（不存在） | 名字最像，但**没有可用接口** |
| **`project-map`** | 服务注册表里有"项目根目录文件清单"的概念（`ground/` 包在注入它） | **是"项目"的信息，不是"人"的信息** |
| **`user-preferences`** | 需求提过这个词，**但没有任何地方定义它是什么、放哪** | **纯名词，无实体** |
| **（新增）用户手写的本机文件** | 不存在 | 需要你定格式与位置 |
| **（新增）从使用中学（`learn`）** | `learn` 通道设计好了，**模型未定、未实现** | 最符合"越用越懂你"，但**周期最长** |

### 2.5 我的建议：**分两步**

**第一步（现在就能做）**：**定义 `context_sources` 的"来源类型"枚举**，
让服务**先把"归因能力"建起来**——即使暂时只有一个来源（例如本机一个手写文件）。
这样 `SCOPE-PROFILE-01` 的**归因部分**可以先绿，**内容从哪来可以后补**。

**第二步（你定方向后再做）**：决定画像的**真值源**是：
- 你手写（可控、立刻可用）
- 从知己读（现在只读，需开接口）
- 从使用中学（`learn`，最慢但最符合"懂你"）

**我的倾向**：**先手写、后学**。
因为「懂你」从手写开始最诚实——**如果你写下的偏好它都不遵守，那它学出来的也不会对。**

## 3. 两件事的共同点

**它们都不是"实现没做"，而是"规格没说"。**

| | 缺什么 |
|---|---|
| 会话记忆 | **缺"状态归属"的决定**（服务 / 调用方 / 磁盘） |
| L3 画像 | **缺"数据来源"的定义**（谁提供、放哪、什么格式） |

**而这两件恰好都触到了同一条红线**：
**这台服务被设计成「无状态、只出意图、永不执行」——
所以任何"要它记住东西"的需求，都必须先回答"记在哪"。**

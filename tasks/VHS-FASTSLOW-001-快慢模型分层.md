# VHS-FASTSLOW-001 · 快慢模型分层与协调（含 `/api/route` 实测）

> **Peter 2026-10-03**：「**有些要快速决策的问题。一个是快模型，一个是慢模型。**
> 在规划的时候也许不需要快模型，**但很多时候需要用快模型**。
> **把快慢模型怎么衔接协调，做成你自身的一个核心能力。**
> ……**你否则啥都从那边走，这是有点慢。**
> 要有记录：**什么时候用什么模型，默认什么模型要有基本的概念。**」

---

## 1. 实测：**网关已经有一个"快模型"了，而且不是模型**

### 1.1 `/api/route` —— 真端点，毫秒级，**不调模型**

```
GET /api/route?q=<自然语言>
  q="把这个文件删了"  → hits:[file-store …]        （按 aliases 命中）
  q="部署到生产"      → hits:[cicd …]
  q="翻译一下"        → hits:[translate …]
```

**它做的是：用服务注册表的 `aliases` 做语义匹配 → 返回该找哪个服务。**

**关键点**：
- **瞬时返回**（无模型调用）→ **这才是真的"快"**
- **它的 `aliases` 里本来就含 ASR 变形词**：
  `爱ops`（aiops）、`研究obc`（research-opc）、`沃克body`（workbuddy）、`格罗克`（grok）
  → **它天然抗语音识别错误**

> **这是本轮最重要的发现**：Peter 说的"快模型"，
> **在当前网关上的形态不是一个模型，而是一个别名路由表。**

### 1.2 我那次"快慢模型延迟对比"**是无效实验**（如实记录）

我拿同一个问题分别打 `deepseek-flash` 与 `deepseek-reasoner`，得到 **1.62s vs 1.58s**——
**看起来"没有差别"，但这个结论不成立**：

| 问题 | 后果 |
|---|---|
| 两个模型**都产出了 `reasoning_content`**（93 / 98 字） | 说明 `flash` 也在做推理 |
| `max_tokens:64` **被推理占满**，`content` 为空 | **没拿到答案**，比的是"都没答完" |
| 网络往返占主导 | 掩盖了模型本身的差异 |

**结论：我这次没有测出快慢差异。不能说"快模型不快"。** 要重测需：够大的 `max_tokens`、多次采样、分开网络与推理耗时。

## 2. 设计：三层，**默认走最便宜的一层**

```
┌─────────────────────────────────────────────────────────────┐
│ L0 · 本地规则 + 别名路由（微秒–毫秒，零模型）                  │
│    · harness 本地：域门禁、四元组缓存、词典、关键词分类          │
│    · 网关 /api/route：自然语言 → 服务（靠 aliases，抗 ASR 变形）│
├─────────────────────────────────────────────────────────────┤
│ L1 · 快模型（秒级以内）—— 模糊判断、分类、消歧、简短裁决         │
│    · deepseek-flash                                          │
├─────────────────────────────────────────────────────────────┤
│ L2 · 慢模型（数秒–更久）—— 规划、复杂推理、诊断、复盘            │
│    · deepseek-reasoner / deepseek-v4-pro                     │
└─────────────────────────────────────────────────────────────┘
        **升级规则：能停在上层，就绝不下沉。**
```

### 2.1 升级规则（**核心能力，必须显式**）

| 情形 | 停在哪层 |
|---|---|
| 本地规则/缓存命中 | **L0**（不调模型） |
| `/api/route` 唯一命中且高置信 | **L0**（不调模型） |
| 多个候选 / 无候选 / 需要语义判断 | **L1** |
| 需要多步规划、因果推理、失败诊断 | **L2** |
| **L1 低置信** | **升级 L2**（`ASR-MODEL-02` 的 fail-open 已实现） |
| **L2 不可用/超时** | **降级 L1 → 再降 L0**，标 `degraded`（已实现） |

> **一句话**：**快的不够才慢，慢的不行就退快。**

### 2.2 为什么"能停在上层就不下沉"是本质

SOTA 调研的实证：
> 一个廉价的只读验证器拒掉 **61%** 无效 episode，**<$0.01/episode**；
> 而"**规划内容本身**"只值 **+7.17pp**。

**贵的那层，边际收益可能远小于便宜的那层。** 所以**默认走便宜层**，只在证据要求时才升级。

## 3. Peter 要的"记录"：**模型选择台账**

> 「**大概什么时候用什么模型……默认什么模型要有基本的概念。**」

**台账形态**（与 `VHS-OUTPUT-001` 的 diff 要求一致）：

```json
{ "at": "…", "task": "意图消歧",
  "level": "L1", "model_id": "deepseek-flash",
  "because": "route 无唯一命中，需语义判断",
  "latency_ms": 1240, "tokens": 117,
  "outcome": "answered|escalated|degraded",
  "escalated_to": "deepseek-reasoner|null",
  "why_escalated": "L1 置信 < 0.5" }
```

**考察时看三样**（这就是 Peter 说的"输出作为重要考察点"）：
1. **层级分布**：多少比例停在 L0 / L1 / L2 —— **L0 比例低 = 太慢**
2. **升级率**：L1→L2 的比例 —— **高 = 快模型选错了**
3. **升级后是否真的变好** —— **不改善 = 白升级，说明升级规则错了**

## 4. JEV 的位置（Peter 点名）

服务注册表里 `model-center` 的别名含「**用哪个模型**」「**模型用量**」，
而 `model.peterzou.com` 的端点列表里有 **`/v1/decisions`**。

**实测**：`aiops.peterzou.com/api/model/decisions` 与 `/api/decisions` **均为 SPA 兜底，不存在**。

**所以**：
- **JEV 式的快速判断能力，当前可用的形态是 `/api/route`**（别名路由）
- **`/v1/decisions` 在 model-center 上存在，但网关下未暴露** —— **需 Peter 确认是否有对应路径**

**若 JEV 可用**，它应落在 **L0 与 L1 之间**：
> **比别名匹配更会判断，比大模型更便宜更快。** 这是"部分快速模型决策"的正确位置。

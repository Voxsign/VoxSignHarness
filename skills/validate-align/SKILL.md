# 校验与对齐 v2（实证校准版）

## 为什么 v1 错了（2026-10-03 复盘）

v1 只做**文本级三查**（脚本读 criteria 字符串查模糊词），不读实现代码、不真跑、不调用模型 → 给出 90/100 对齐度，但实际值很差。**纸上校准 = 一塌糊涂**。
规则：**没有代码证据和运行证据的评分一律无效**。

## 三层取证（缺一不可，逐层落证据）

| 通道 | 做什么 | 取证手段 | 产出 |
|---|---|---|---|
| **D 文档校准** | 需求文档 ↔ 判据提取：三查（完整性/一致性/可验收性） | 读需求原文，判据 SMART 化（模糊词量化） | 判据清单（可测） |
| **C 代码校准** | 判据 → 实现代码真值：存在性/结构/接线 | git grep + Read 源码：接口、结构、调用链 | 每条判据的代码证据（文件:行） |
| **R 真跑校准** | 判据 → 运行时行为：起服务、打接口、断言 | 真装配（不许桩）：build+serve+curl/脚本 | 每条判据的运行证据（响应/日志/数据） |

**评分规则**：每条判据 PASS = C 证据 + R 证据**双证齐**；只 C 无 R = ◐ 待真跑；只有文档 = ✗。
**对齐度 = PASS/总判据 × 100**；评分必须附证据链（判据→文件:行→响应/日志），无证据链的分数不采信。

## 双向目标（校准必须分对象取证，不许混层）

校准输入必须显式区分两类目标，分开评分：

- **产物验收**（第 11 章）：对产物（如 vhs-asr）取证——文档/代码/真跑三通道
- **能力验收**（H 系列：harness 能否产出）：对执行主体（harness）取证——规划/执行/终态/复跑

**混层 = 判据错误**（v1 把产物验收当能力验收打分，导致 90 分假象）。

## 远程模型调用（语义级判断，不许本地文本猜）

以下判断必须远程调用模型中心（如 deepseek-v4-pro / aiops 网关），不在本地做字符串匹配：

1. 需求语义 ↔ 代码语义是否对齐（"需求说 X" ↔ "代码实现 X" 的语义等价）
2. 意图覆盖判定（任务表述是否落入意图语义范围）
3. 歧义消解（需求歧义 → 模型给出候选并标注影响）
4. 跨文档一致性（需求 v2 ↔ 规格文档 ↔ 验收判据）

调用方式：经 harness 模型中心 / aiops 网关远程执行；模型输出纳入证据链。

## 校准核心要素（理念层 · v2.2 整理）

校准不只是「判据 ↔ 实现」的打分。任何系统/方案按 **三轴** 校准，缺一不可：

### 轴 1 · 对齐轴（需求 ↔ 实现，v2 已建）
目标对齐 → 判据对齐（D/C/R 三层取证 + 双证）→ 语义对齐（远程模型）。

### 轴 2 · 工程轴（实现本身是否健康——七要素必查）
| 要素 | 必问 | 取证方式 |
|---|---|---|
| **架构** | 分层/模块边界是否清晰？依赖方向是否合理（谁依赖谁）？**数据怎么传输**（接口契约、数据流路径、序列化、跨服务边界/网关）？ | 读代码：调用链/接口签名/配置文件；画数据流 |
| **性能** | 关键路径热不热？缓存/IO 是否合理？瓶颈在哪（实测定位，不许猜）？ | 压测 + 分层计时（如 traces 分步 ms） |
| **核心实现逻辑** | 核心机制是否成立、是否串成闭环（如 输入→纠错→记忆→意图→反馈→学习）？ | 读核心链路 + 端到端真跑 |
| **安全** | 鉴权/越权/回环边界/注入/敏感数据？谁可以访问、谁能改数据？ | 读鉴权代码 + 非授权真跑 |
| **数据组织** | **数据乱堆吗**？存储是否分职责（各数据各文件/各表）、格式一致、append-only、有界（上限/过期）？ | 读存储层 + 数据目录实查 |
| **资源复用** | 同一逻辑多处复制？连接/缓存/组件/能力是否复用？有没有重复造轮子或重复实现？ | grep 重复实现 + 调用点统计 |
| **代码优雅性** | 命名/单一职责/死代码/重复/圈复杂度？可维护吗？ | 读关键文件 + 静态扫描 |

### 轴 3 · 过程轴（执行过程是否健康）
真装配（不许桩）→ 可复现（同一命令重跑一致）→ 可验证（每结论有证据）。

## 六步闭环（v2，实证版）

1. **澄清上下文与约束**：目标、边界、涉众、约束；信息不足提 ≤3 个必要问题
2. **提取目标与验收标准（分对象）**：产物验收 + 能力验收分开；模糊词量化
3. **三层取证**：D 文档校准 → C 代码校准 → R 真跑校准（按判据逐条落证据）
4. **对齐收敛**：差异消解（补实现/补判据/降级取舍）+ 回读确认（双方一致才推进）
5. **执行中复校**：目标漂移/标准失效/新约束/交付偏差/假设证伪 → 停并对齐
6. **复盘沉淀**：证据链归档，评分+风险写回

## 第 7 步 · 改进建议与编排（评分后的必做输出，缺此不算完成校准）

**评分本身不能交付——必须给出「怎么做」**。每条未 PASS 判据都要有：

| 字段 | 内容 |
|---|---|
| **问题定位** | 这条判据红在哪（✗/◐），根因（一句话） |
| **具体建议** | 怎么做（改哪里/怎么改/补什么），不许"优化一下"式空话 |
| **验证方式** | 改好后怎么证明（同一判据重跑，双证） |
| **责任方** | 谁做（实现方/测试方/用户裁决） |
| **优先级+依赖** | 先做哪个、依赖什么（关键路径），可并行项标注 |

**编排原则**：① 地基先于上层（执行链先于规划模板，规划先于意图触发词）；② 依赖排序（被依赖的先行）；③ 可并行项并行；④ 每个里程碑可验；⑤ 未解决项升级裁决（不默认继续）。

输出格式：按优先级排列的《改进编排表》（判据 → 建议 → 验证 → 责任 → 里程碑）。

## 交付前校验清单

- [ ] 每条判据有 C 代码证据（文件:行）？
- [ ] 每条判据有 R 运行证据（真跑响应/日志）？
- [ ] 产物验收与能力验收分对象评分，未混层？
- [ ] 语义级判断走了远程模型，未本地文本猜？
- [ ] 对齐度 = PASS/总数，证据链可追溯？
- [ ] 假设显式标注，风险已列明？

## scripts

- `scripts/validate_align.py`：仅用于 D 通道文本三查辅助（不可单独作为评分依据）
- `scripts/evidence_collect.sh`：C 通道代码证据采集（grep 接口/结构 → 输出判据↔文件:行 映射）
- `scripts/run_calibration.sh`：R 通道真跑采集（起服务→打接口→断言→输出判据↔响应证据）

# 校验与对齐 v3（语义对齐版）

## 定位：验收输出前的必经动作（硬规则 · 2026-10-04 用户定）

**任何「验收通过 / 交付 / 上线」结论输出之前，必须先跑本技能六通道取证 + 评分 + 改进编排。** 校验对齐不是可选项，是验收流程的前置门：

1. **验收输出 = 校验对齐的产出物**：报告 = 判据证据链（D/C/R + 涉参考时 RA/SC/CC）+ 对齐度 + 偏差清单 + 改进编排表，二者一起交付，不许只出"验收通过"结论。
2. **对齐门槛（用户定标准）**：存在性双证 PASS ≥ **90%** 且 **✗ FAIL = 0**，偏差（◐/mismatch）须已消解或经用户裁决 → 才算「已对齐、可出验收」；涉参考/照搬场景同时受 RA 一票否决约束（任一 mismatch → NOT-ALIGNED，无论存在性分多高）。
3. **未达标 → 禁止出验收**：按改进编排（第 7 步）修订 → 重跑六通道取证 → 再评分，**循环直到达标**；每轮修订留痕（git commit）。
4. **修订顺序由编排优先级驱动**（地基先于上层、被依赖先行、可并行项并行），不许按文件顺序瞎改。
5. 双向目标始终分开评分（产物验收 / 能力验收），未达标对象各自走修订循环。

## 为什么 v2 还不够（2026-10-03 复盘）

v2 的三层取证（D 文档/C 代码/R 真跑）只能证明**判据存在**——"目标里有这个组件，代码里也有同名组件"。它验证不了**架构是否正确、逻辑是否对齐**。

**失败案例（用户真实场景）**：照搬 DeepSeek harness 的结构做 VoxSign harness——组件名都在（intent-understanding、executor、memory…），但职责全错位：意图理解被做成关键词触发、执行引擎退化成单函数直调、规划层和反馈层干脆缺失。v2 机械校验全过（score=90），架构明显不对。

规则：**存在性 ≠ 对齐。校验必须能抓"表面都有、语义错位"。**

## 六通道（缺一不可，逐层落证据）

| 通道 | 做什么 | 取证手段 | 判定 |
|---|---|---|---|
| **D 文档校准** | 需求文档 ↔ 判据提取：三查（完整性/一致性/可验收性） | 读需求原文，判据 SMART 化 | 判据清单（可测） |
| **C 代码校准** | 判据 → 实现代码真值：存在性/结构/接线 | git grep + Read 源码：接口、结构、调用链 | 每条判据的代码证据（文件:行） |
| **R 真跑校准** | 判据 → 运行时行为：起服务、打接口、断言 | 真装配（不许桩）：build+serve+curl/脚本 | 每条判据的运行证据（响应/日志/数据） |
| **RA 参考对齐** | 目标系统 vs 参考系统逐组件映射（照搬/借鉴场景必做） | 组件清单（name/layer/responsibility/interfaces）→ 跑 `scripts/validate_align.py` reference-alignment 模式 | 对齐矩阵 + 差异显著性（critical/acceptable/enhancement）+ **一票否决** |
| **SC 语义一致** | 意图→架构→代码三层断言语义等价 | **远程模型**（模型中心）三测试：语义等价/矛盾/包含 | aligned / misaligned / unclassified 逐断言 |
| **CC 反事实压测** | "这个架构在哪里会崩"：3-5 个压力场景逐个追问 | 远程模型按场景构造评审（新领域扩展/峰值/故障/交接/合规） | 风险清单 + 建议 |

## RA 参考对齐（照搬/借鉴场景的核心通道）

输入：目标组件清单 + 参考组件清单（各含 name/layer/responsibility/interfaces，字符串亦可）+ layers + critical_layers。

映射分类：`match` 同构（同层+职责≥0.8）· `similar` 近似（职责同族，本地化差异）· `missing` 参考有目标缺 · `mismatch` **同名同层但职责不匹配（表面复制，语义错位）** · `extras` 目标多出。

**一票否决（对应 LLM-as-a-Judge 强制上限，arXiv 2609.02246）**：任一 `mismatch` → verdict=**NOT-ALIGNED**，对齐度封顶 40。无论存在性分多高——"架构明显不对"不得通过。

差异显著性：critical（mismatch + 关键层缺失）→ 必须改；acceptable（similar）→ 确认本地化；enhancement（extras）→ 确认是合理增强还是无约束蔓延。

## SC 语义一致（远程模型，不许本地文本猜）

以下判断必须远程调用模型中心（deepseek 系列），不做字符串匹配：

1. 需求语义 ↔ 架构决策语义（ADR/README）↔ 代码语义是否对齐（三测试：等价/矛盾/包含）
2. 架构合理性五维评审（R2ABench）：completeness / faithfulness / architectural rationality / traceability / readability
3. 需求覆盖率 ReqCov：每条需求是否被架构或代码覆盖
4. 参考系统职责等价性复核：RA 矩阵里 mismatch/similar 的判定用模型复核（脚本相似度只是粗筛）

调用方式：经平台 remote 执行（manifest source=remote，model-center 能力源）；模型输出纳入证据链。

## 评分规则（v3）

- 存在性分：PASS/总判据 × 100（D/C/R 三通道）
- 参考对齐分：match=1.0 / similar=0.6 / missing=0 / mismatch=0 加权
- **总评 = 存在性 × 参考对齐修正**；任一 mismatch → NOT-ALIGNED（一票否决）
- 对齐度必须附证据链（判据→文件:行→响应/日志→矩阵行），无证据链的分数不采信

## 七步闭环（v3）

1. **澄清上下文与约束**：目标、边界、涉众、约束；是否涉及参考系统/照搬场景；信息不足提 ≤3 个必要问题
2. **提取目标与验收标准（分对象）**：产物验收 + 能力验收分开；模糊词量化
3. **三层取证**：D 文档校准 → C 代码校准 → R 真跑校准（按判据逐条落证据）
4. **参考对齐（照搬/借鉴时必做）**：建组件清单 → 跑 reference-alignment → 差异显著性分级 → 一票否决裁定
5. **语义一致（远程）**：SC 三测试 + 五维评审 + ReqCov（模型输出入证据链）
6. **对齐收敛**：差异消解（补实现/补判据/降级取舍）+ 回读确认；执行中复校（目标漂移/标准失效/交付偏差 → 停并对齐）
7. **复盘沉淀**：证据链归档，评分+风险写回

## 交付前校验清单

- [ ] 每条判据有 C 代码证据（文件:行）？
- [ ] 每条判据有 R 运行证据（真跑响应/日志）？
- [ ] 涉参考/照搬场景时跑了 RA 矩阵且差异显著性分级？
- [ ] 任一 mismatch 是否一票否决为 NOT-ALIGNED（未因存在性分高放行）？
- [ ] 语义级判断（SC/RA 复核）走了远程模型，未本地文本猜？
- [ ] 产物验收与能力验收分对象评分，未混层？
- [ ] 对齐度附证据链，假设显式标注，风险已列明？

## scripts

- `scripts/validate_align.py`：D 通道文本三查 + **RA 参考对齐矩阵**（`mode=reference-alignment`，输入 target/reference/layers/critical_layers；输出矩阵/差异分级/一票否决）。语义级判断由远程模型完成，脚本只做确定性粗筛与证据整理。
- `scripts/evidence_collect.sh`：C 通道代码证据采集（grep 接口/结构 → 输出判据↔文件:行 映射）
- `scripts/run_calibration.sh`：R 通道真跑采集（起服务→打接口→断言→输出判据↔响应证据）
